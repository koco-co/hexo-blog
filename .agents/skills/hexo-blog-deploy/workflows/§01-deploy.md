# 显式部署工作流

每次调用都完整读取 `rules/release-safety.md`。本流程不会修改文章、配置、主题或 CI 来消除阻塞项。

## Phase 1：解析请求

1. 确认任务是发布准备、执行本地部署，还是执行 GitHub Actions 路由。
2. 若用户未指定路由，根据请求和实时环境提出推荐，但在确认前只执行共同的只读预检。
3. 从 `_config.yml` 读取部署类型、远程和分支，并只展示脱敏值。
4. 记录当前请求是否已经明确授权本次实际部署；“看起来可以了”“准备好后告诉我”不算授权。

完成信号：`intent` 为 `prepare` 或 `execute`，`route` 为 `local` 或 `ci`，授权状态明确。

## Phase 2：运行预检

按顺序执行：

```bash
node .agents/skills/hexo-learn-topic/scripts/audit.mjs project --json
node .agents/skills/hexo-learn-topic/scripts/audit.mjs lint --json
node .agents/skills/hexo-learn-topic/scripts/audit.mjs release --route local --json
```

CI 路由将最后一条命令的 `local` 改为 `ci`。

1. 保留审计退出码；退出码非零表示发布阻塞，不得用文字判断覆盖。
2. lint 必须为 `status: pass`；任一具体文件错误都先交回维护流程修复并重跑。再核对报告中的 Node、Hexo、目标、注入资源、敏感字段位置和 Git 状态摘要。
3. 不读取或展示敏感字段值，也不列出 `.deploy_git` 中可能带私人信息的具体未跟踪文件名。
4. 任何阻塞项存在时直接进入 Phase 6，输出“未执行部署”。

完成信号：机械预检为通过或仅含不影响所选路由的已知警告。

## Phase 3：构建与预览

1. 运行 `npm run build`，不先执行 `npm run clean`。
2. 构建后重新运行全仓库 lint，确认插件写回的 `abbrlink` 完整且唯一，目录、标签和图片仍全部通过。
3. 如果本次候选发布包含内容、布局、样式或前端功能变化，启动 `npm run server` 并用浏览器验证受影响的真实路由。
4. 至少检查目标页面、首页入口和移动视口；涉及 PJAX 时检查站内跳转；涉及第三方服务时检查失败降级。
5. 完成后停止本次启动的服务。

完成信号：构建成功，发布级内容审计通过，适用的真实页面验收通过。

## Phase 4：最终授权门禁

1. 向用户展示所选路由、脱敏远程、分支、构建结果、页面结果和剩余风险。
2. `prepare` 任务在此停止并生成报告。
3. `execute` 任务只有在当前请求已经明确授权本次动作时继续；否则请求一次明确确认。
4. 用户的确认只覆盖展示的目标和命令，不包含清理、强推、主题修复、CI 修改或仓库权限变化。

完成信号：实际发布授权与精确目标一一对应。

## Phase 5：执行并验证

### Local 路由

1. 运行 `npm run deploy`，记录退出码和脱敏后的必要输出。
2. 不进入 `.deploy_git/` 手工提交或清理来补救失败。

### CI 路由

1. 仅执行已确认的既有工作流触发方式。
2. 获取真实工作流运行结果；源码推送成功不等于 Actions 或 Pages 发布成功。

### 线上验证

1. 使用 `_config.yml` 的公开站点 URL，打开本次变更涉及的页面。
2. 验证页面可访问、关键内容或功能已更新，并检查资源和控制台错误。
3. 区分缓存未刷新、构建未包含、远程发布失败和产品行为失败。
4. 无法访问网络或站点时标记未验证，不再次部署。

完成信号：命令、远程发布和线上页面分别获得实际证据。

## Phase 6：交付

1. 使用 `templates/deployment-report.template.md`。
2. 完整执行 `checklists/deployment-acceptance.md`。
3. 列出已验证、未验证、阻塞和实际外部副作用。
4. 若任何发布动作未发生，明确写明“未执行部署”。

失败路径：预检、构建、授权、部署或线上验证任一失败时停止当前阶段，不自动清理、重试或扩张修复范围。
