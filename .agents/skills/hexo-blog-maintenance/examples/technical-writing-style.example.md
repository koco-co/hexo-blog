## 正文片段

### 重复送达

<!-- concept-story:start -->

河湾镇的木匠托信使向仓库订一车木料。仓管照信发了货，又让信使带回收条。归途中暴雨冲走了收条，木匠等不到消息，只好再送一封内容相同的信。第二天，两车木料停在了门口，两笔货款也记到了他的账上。

木匠要求仓管：“内容一样的信，就别再发货了。”仓管却摇头：“你下个月若真想再买一车，难道也不算？”相同的字句，可能是旧事的催问，也可能是新生意。

他们改了一个约定：每笔新生意先编一个单号，催问时沿用原号。仓管只有一位，每次办完一笔才接下一笔；他把单号、木料数量和发货收条一起记进账册。再见到相同单号时，先核对数量，再抄回已有收条，不另发一车。

{% mermaid %}
flowchart TD
  A[单号甲：订一车] --> B[记账并发货]
  B --> C[收条在路上丢失]
  C --> D[仍带单号甲来询问]
  D --> E[查账后重抄收条]
{% endmermaid %}

雨仍会下，信使仍可能跑两趟；改变的是第二次送信不再带来第二车货。若木匠要追加一车，就写新单号；若拿旧单号把一车改成两车，仓管会请他说明，而不会猜测。

木匠终于分清了两件事：消息来了几遍，与一笔生意生效几遍，并不是同一个数。

<!-- concept-story:end -->

{% note primary flat %}
这里建立的是请求的幂等性：在约定的识别范围与有效期内，同一操作被重复提交，不会产生额外的预期业务副作用。故事用“单号识别同一笔生意”实现这一目标；它不是幂等性的唯一实现方式，也不意味着请求只传输或执行了一次。
{% endnote %}

| 故事元素 | 技术对象 | 对应关系 |
| --- | --- | --- |
| 木匠与信使 | 调用方与消息传输 | 没收到响应，不能判断服务端是否已经完成 |
| 每笔生意的单号 | 请求幂等键 | 重试沿用标识，新业务意图使用新标识 |
| 账册与收条 | 去重记录与已保存结果 | 识别已处理请求，避免再次产生业务效果 |
| 旧单号改数量 | 同一键携带不同参数 | 应检查冲突，不能把新意图当成重试 |

{% note warning flat %}
故事假设一位仓管连续处理，账册不会丢。真实系统存在并发、崩溃和记录过期：“检查单号—业务变更—保存结果”需要协调一致，不能凭一张内存表保证跨进程或跨服务的效果。幂等也不保证重试最终成功；不同接口对响应内容的约定可以不同。
{% endnote %}

### 验证

{% note info flat %}
下面只演示单进程、顺序调用中的意图识别。先预测三个返回值：第二次同号请求会不会新增订单，内容相同但换号是否算新订单？这里用内存字典观察结果，不模拟网络或持久化故障。
{% endnote %}

```python
receipts = {}
orders = []


def order(request_id, quantity):
    if request_id in receipts:
        old_quantity, receipt = receipts[request_id]
        if old_quantity != quantity:
            raise ValueError("同一单号不能改变数量")
        return receipt  # 同一业务意图的重试，返回已保存结果
    orders.append(quantity)
    receipt = f"order-{len(orders)}"
    receipts[request_id] = (quantity, receipt)
    return receipt


print(order("request-a", 1))
print(order("request-a", 1))
print(order("request-b", 1))  # 内容相同，但这是新的业务意图
print(orders)
try:
    order("request-a", 2)
except ValueError as error:
    print(error)
```

```text
order-1
order-1
order-2
[1, 1]
同一单号不能改变数量
```

{% note primary flat %}
同号同参数调用复用了结果，换号创建了新订单，同号改参数则被拒绝。若把“追加订单”放到检查单号之前，重试又会增加副作用；若清空记录后再次调用，原来的识别能力也会消失。把情境换成重复提交预约时，仍要先区分“重试原预约”和“新增一次预约”。
{% endnote %}

## 闪卡解析片段

精简回答：重试不应让同一业务操作产生额外效果；能否重试须遵守接口的幂等约定。

解析：想象预约已创建，但确认消息丢了。再次提交相同预约标识时，服务端识别已处理请求，避免新增一条预约。新预约要用新标识；同标识修改日期属于参数冲突，不能默认为旧请求。重复消息可能仍然到达，幂等约束的是业务效果。这个短情境不依赖正文人物；真实系统还要处理并发、记录持久化与有效期，不能把内存查重当成完整保证。

## 技术问答片段

问题：幂等是否意味着请求只会执行一次？

回答：不意味着。幂等约束的是同一业务意图重复提交后的预期业务效果，不是网络只传输一次，也不是服务端代码只运行一次。比如预约已经创建但响应丢失，客户端沿用原请求标识重试时，服务端可以返回已保存的结果，而不再创建第二条预约；换用新标识则表示新的业务意图。这个结论依赖接口约定的识别范围、记录一致性和有效期，并不能单独保证重试最终成功。

这段回答先让读者拿到可复述的判断，再用机制和具体情境解释，最后限制结论范围。正式文章只保留自然答案，不增加用于展示写作步骤的栏目。

## 故障与选型片段

场景：客户端偶尔收不到预约接口的响应，但服务端可能已经完成写入。团队正在讨论是否对所有失败请求自动重试。

自然分析可以写成：

> 目前能观察到的是响应丢失，不能由此判断预约没有创建；真正的约束是重复提交可能产生第二条预约。因此不应先把所有失败统一改成自动重试，而应区分可安全重试的读取操作与会产生业务副作用的写入操作。预约写入若要重试，需要为同一业务意图沿用稳定标识，并让服务端一致地保存和复用处理结果。这样会增加标识存储、冲突检查和过期策略的复杂度，但能避免用超时换来重复预约。验证时应模拟“服务端完成写入、响应在返回途中丢失”，确认同一标识的重试只保留一条预约，换用新标识才创建新预约。

这段分析先建立可观察现状与约束，再给出建议、取舍和验证方法；没有把“超时”直接等同于“服务端未执行”。

## 项目经历片段

以下事实是专门用于演示表达方式的合成夹具，不代表作者或读者的真实经历：某发布流程曾因缓存产物未更新造成回滚，回答者负责质量门禁，随后增加产物哈希核对和小流量验证，使同类失败率从 8% 降至 1%，平均回滚时间从 30 分钟降至 5 分钟。

自然回答可以写成：

> 一次发布后，部分实例继续使用旧缓存产物，现有门禁却只检查了进程是否启动。我负责补齐发布质量门禁，先对比构建产物与部署实例的哈希，确认问题不在服务进程，而在产物一致性；随后把哈希核对放到切流前，并增加小流量验证和自动回滚条件。同类发布失败率从 8% 降到 1%，平均回滚时间从 30 分钟缩短到 5 分钟。复盘后我们还把“进程存活”和“版本正确”拆成两类证据，避免健康检查再次掩盖产物错误。
