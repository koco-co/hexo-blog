# 技术文章文风规范

本文件是当前博客技术文章正文的唯一文风规范。它适用于普通技术文章、系统课程、概念解释、操作说明和闪卡解析；随笔、诗词等非技术内容保留自身文体。课程的篇章职责、标签覆盖和发布门禁仍由 `hexo-learn-topic` 的课程合同负责。

## 1. 先让读者看见问题

从读者能观察的现象、要完成的操作或需要判断的对象进入主题，再解释术语和机制。遇到抽象、反直觉、易混淆或需要多步因果推理的概念，默认先用故事建立理解，按第 3.1 节组织；操作步骤和风险说明保持直接。定义只有在能帮助读者继续推理时才出现，不连续罗列概念，也不先给一张大表再补背景。

一段文字围绕一个动作、因果关系或判断展开。主题变化时用自然过渡、简短标题、列表、表格、代码或图示重新组织，不让同一段同时承担定义、步骤、例外和总结。

## 2. 用因果关系组织解释

技术解释至少让读者知道“发生了什么”和“为什么会这样”。涉及状态、调用链或失败过程时，继续说明关键步骤、可观察结果和适用边界。不要只换一种说法重复结论，也不要用术语堆叠代替推理过程。

叙述应当像一位熟悉主题的工程师在带读者分析问题：准确、克制、自然。可以使用“先看运行结果”“这里真正改变的是……”等连接句，但不要机械重复“首先、其次、最后”，也不要把“直觉类比”“状态变化”“判断边界”等教学动作做成每篇固定出现的栏目。

### 2.1 按任务安排信息顺序

先判断这一段要帮助读者完成什么，再安排信息顺序；不能让同一套次序覆盖所有正文和问答。

- 回答技术原理、给出观点，或在概念故事、真实案例和替代推演结束后进入正式技术解释时，先直接给出核心判断，再说明原因或机制，用具体例子、输入输出或证据落地，最后补充反例和适用边界。无需故事的简单概念可以直接采用这一次序；答案已经足够短时不机械复述结论。
- 分析故障、比较方案或提出建议时，先交代可观察现状和真正造成困难的约束，再收束需要判断的问题，给出建议、依据、主要取舍和验证方式。面试口头回答时间有限时可以先报结论，再补齐这条分析链。
- 复述项目和行为经历时，只保留理解行动所需的背景与本人职责，把篇幅集中在本人采取的关键行动、选择理由、可核对结果和后续复盘。只能使用用户提供或现有资料能够证明的经历；事实不足时先补充信息，不能代写成亲历事件。合成教学案例必须明确其虚构性质。
- 组织较长章节时，一个段落组只服务一个上位判断，后续依据按互不混淆的理由、步骤或证据归组；同一事实不在多个分组中换词重复。摘要、选型和决策内容通常先给核心判断；概念故事仍可按第 3.1 节延迟揭示正式名称。

这些顺序是写作时的内部组织方法，不是公开模板。公开文章的全部可见文案，包括标题、摘要、正文和图注，不得出现相关表达模型的名称、模型缩写、步骤代号或用于暴露组织流程的标签；不把这些环节固定成 H2/H3，也不为了闭合形式添加无信息量的开头或总结。最终文字应让读者自然看见判断、因果、证据和边界，而不是看见作者套用了某种格式。

## 3. 选择真正有帮助的表达

辅助表达按理解困难选择，不按数量或模板凑齐：

- 代码适合展示输入、关键动作和可观察结果。关键行写解释原因的注释；只给语法、没有注释或输出的代码不能替代说明。
- 表格适合精确比较多个字段或行为。两个简单事实用一句话更清楚时不建表。
- Mermaid、时间线和图表适合关系、流程、状态、层级和真实数据。图后保留文字结论与失败边界。
- 真实截图用于界面状态和错误证据；AI 插画或分镜用于故事中的情境、角色选择及结果，精确关系仍优先代码图表。图片必须有替代文本，正文保留等价结论；生成图不能冒充截图、实测或史实。
- 类比只负责建立初步直觉，随后回到真实技术对象，并明确类比从哪里开始不再成立。不要让类比代替机制。

同一个解释不必同时使用代码、表格、图片和类比。选择其中最能降低理解成本的方式即可。

### 3.1 难点的故事入口

故事放在对应概念的开头，不是整篇文章只安排一次的装饰性引言。先在预案中指出读者具体会卡在哪里，再决定情境和理解路径；相互关联的概念可以延续同一组角色与规则，不为每个术语另起一则寓言。

按以下因果顺序设计，环节可以自然融合，不把它们写成固定 H2/H3：

1. 让角色带着目标进入一个有约束的情境，使读者先看见问题；虚构情境不能写成真实事件或实验记录。
2. 让角色尝试、选择并承担后果。关键转折可让读者预测结果，再用事件、分镜或图表展示原因；不能只给技术名词换上人物名字。
3. 临近故事结尾才揭示概念或机制，保留读者自己发现联系的机会。章节标题可以保留正式术语，不为制造悬念改乱目录；开场提示和图片不要抢先给出完整答案。
4. 故事后直接给出准确技术解释，把关键角色、规则、动作与结果对应到真实对象。对应项较多时使用表格；说明隐喻在哪里失效，不能由故事类推出未经证明的技术结论。
5. 用真实案例、可运行的小实验、反例或新情境问题检验迁移：读者能否不用人物名字解释机制，并判断条件变化后的结果。

故事长度由因果链需要决定，不设固定字数、人物数或图片数；删去不改变理解的对白与背景，避免把技术文本墙换成故事文本墙。保持成年读者适用的语言和原课程深度，不因使用寓言降低准确性，也不把默认读者改成研究生。

纯语法查询、直接操作、危险命令和简短事实不强制故事化。隐喻会扭曲机制或增加理解负担时，改用可视化推演、真实案例或小实验，并在预案说明选择依据；不能以“不适合故事”为由退回连续定义。

### 3.2 故事与视觉的分工

故事主线默认直接可读，图表、插图和标签在帮助推理的位置穿插。AI 分镜表现情境与转折；Mermaid 表现准确关系或状态；表格用于隐喻对照和精确比较；真实截图与运行结果承担证据。数据图须有真实数据，虚构故事中的数值不能包装成实测趋势。

时间线只呈现有时间意义的演进，页签只呈现真正平行的方案，隐藏答案只用于可选预测或自测。必要情节、概念揭示、关键对应、命令和风险不能要求逐个点击才能理解；延迟揭示不等于隐藏结论或延后安全提示。

系统课程允许有明确边界的故事自然段，标记与审计范围只由 `../hexo-learn-topic/rules/published-article-contract.md` 第 2.1 节定义。标记本身不证明内容具有教学价值。AI 图片的生成、落盘和验收按 `workflows/§06-local-images.md`，没有生成能力时调整已确认预案，不伪造图片或悄悄留下缺失资源。

## 4. 保持书面而不僵硬

- 使用具体动词和技术对象，少用“进行处理”“相关内容”“某种机制”等空泛表达。
- 术语首次影响理解时就地解释，后文保持同一名称；无需把常见术语反复翻译。
- 标题负责定位，正文负责讲清原因、条件和边界；标题不承担完整答案。
- 避免“本文将”“如下所示”“为了方便大家”等写作过程话术，也不使用夸张口号、撒娇式提示或刻意幼化的比喻。
- 总结只收束真正需要保留的判断，不逐段复述正文。

自然表达不是口语化聊天。事实、命令、风险和限制仍应直接、准确，不能为了语气轻松模糊技术边界。

## 5. 闪卡回答与解析

`answer` 给出便于主动回忆的精简结论；`explanation` 负责让读者理解这个结论为什么成立。解析应当脱离正文仍能读懂，并根据问题复杂度交代：

- 结论成立的原因或机制；
- 关键步骤、状态变化或因果链；
- 容易误判的边界、反例或类比失效位置。

抽象或复杂问题还必须选择至少一种能把概念落到具体对象上的辅助表达，例如带注释代码、输入输出、比较表、文字流程、本地图片或有边界的类比。简单事实题在结论、原因和边界已经能够独立讲清时按需使用例子或对照，不为满足形式强行扩写。不得用固定字数、段落数或栏目数代替内容判断。

解析不得只重复答案、只列术语、只给无注释代码，或给出没有说明适用边界的类比。插件支持的 Markdown 富内容可以直接写入解析；Butterfly 标签、Tag Plugins Plus 标签和 Mermaid 不嵌套进闪卡。

故事化不改变卡片结构：`answer` 仍直接给出精简结论，`explanation` 可用自包含的短情境解释机制，再说明对应与边界；不复制正文长寓言、不要求读者记得正文人物，也不使用故事豁免标记。

### 5.1 术语与诊断证据

面试题、排障题或包含命令、日志、系统报告的解析，至少完成一次“术语—用途—证据—边界”检查：

- 缩写、命令、日志和诊断工件在首次影响理解的位置给出中文含义，并说明它观察或改变的对象；例如不能只写 `ANR` 或 `logcat`，却要求读者自行猜测。
- 诊断工具或证据分别说明“用来做什么”“直接能证明什么”和“不能单独推出什么”。`logcat` 是时间线线索，`dumpsys` 是系统状态快照，`traces` 是线程调用栈，这些都不能单独替代根因判断。
- 解释至少闭合一条“现象 → 可能机制 → 观察证据 → 结论边界”的链路；多个候选原因要给出能区分它们的最小证据。
- 命令或示例要交代输入、关键动作和预期观察点；没有真实运行结果时使用示例输出或判断目标，不伪造实测结论。

这组检查用于降低理解成本，不要求每张卡都加表格、代码或固定栏目；简单事实题仍以最短的独立解释为准。

## 6. 复习密度与迁移

`常见问题` 不设固定题数上限。题数由文章知识密度、易混淆边界和长期复习价值决定；能够在正文直接消除的误解不重复制卡，彼此高度重叠的问题应合并。

新建或本次编辑的文章立即执行本规范。编辑已有文章时，同一篇中的所有原始 `flashcard` 定义一起复查和升级；`flashcard_ref` 只继承原始定义，不复制修改。未进入当前修改范围的历史卡片作为待迁移内容报告，不阻断无关文章或全仓库检查。全部历史卡片完成迁移后，才单独确认是否升级为全仓库强制语义门禁。

## 7. 审查判断

审查信息顺序时按当前读者任务判断：技术回答是否尽快给出核心判断并由机制、证据和边界支撑；故障或选型是否交代可观察现状、约束、建议、取舍和验证；项目经历是否区分背景、本人行动、结果与复盘。不得因为环节齐全就接受重复结论、虚构经历或生硬的模板标签。

故事规则只应用于本次授权创作或改写的内容；更新 Skill 不自动授权历史文章迁移，也不要求用标记包住旧段落以补齐形式。

审查时先读完整段落或解析，不凭某个词、字数或是否出现表格判断质量。以下任一情况都需要改写：

- 读者知道结论，却仍不知道原因或过程；
- 示例缺少输入、关键动作、输出或失败表现；
- 视觉、代码或类比没有承担正文无法更清楚表达的信息；
- 段落依赖正文外的上下文才能理解；
- 固定教学栏目压过了主题本身的自然结构；
- 故事情节不体现机制、隐喻对应失真，或读者只能复述情节却不能判断新情境；
- 故事标记覆盖普通解释、整章或整篇，或图表、开场提示过早泄露需要推理的答案；
- 语气幼稚、夸张、过度口语化或像自动生成的步骤模板。

通过信号是：读者能够沿着文字复述对象、机制、证据和边界，并知道下一步如何验证，而不是只记住一句结论。
