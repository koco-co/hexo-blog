# 技术文章文风规范

本文件是当前博客技术文章正文的唯一文风规范。它适用于普通技术文章、系统课程、概念解释、操作说明和闪卡解析；随笔、诗词等非技术内容保留自身文体。课程的篇章职责、标签覆盖和发布门禁仍由 `hexo-learn-topic` 的课程合同负责。

## 1. 先让读者看见问题

从读者正在观察的现象、要完成的操作或需要判断的对象进入主题，再解释术语和机制。定义只有在能帮助读者继续推理时才出现，不连续罗列概念，也不先给一张大表再补背景。

一段文字围绕一个动作、因果关系或判断展开。主题变化时用自然过渡、简短标题、列表、表格、代码或图示重新组织，不让同一段同时承担定义、步骤、例外和总结。

## 2. 用因果关系组织解释

技术解释至少让读者知道“发生了什么”和“为什么会这样”。涉及状态、调用链或失败过程时，继续说明关键步骤、可观察结果和适用边界。不要只换一种说法重复结论，也不要用术语堆叠代替推理过程。

叙述应当像一位熟悉主题的工程师在带读者分析问题：准确、克制、自然。可以使用“先看运行结果”“这里真正改变的是……”等连接句，但不要机械重复“首先、其次、最后”，也不要把“直觉类比”“状态变化”“判断边界”等教学动作做成每篇固定出现的栏目。

## 3. 选择真正有帮助的表达

辅助表达按理解困难选择，不按数量或模板凑齐：

- 代码适合展示输入、关键动作和可观察结果。关键行写解释原因的注释；只给语法、没有注释或输出的代码不能替代说明。
- 表格适合精确比较多个字段或行为。两个简单事实用一句话更清楚时不建表。
- Mermaid、时间线和图表适合关系、流程、状态、层级和真实数据。图后保留文字结论与失败边界。
- 截图和图片适合界面状态、真实错误或代码图表无法准确表达的对象。图片必须有替代文本，正文保留等价结论。
- 类比只负责建立初步直觉，随后回到真实技术对象，并明确类比从哪里开始不再成立。不要让类比代替机制。

同一个解释不必同时使用代码、表格、图片和类比。选择其中最能降低理解成本的方式即可。

## 4. 保持书面而不僵硬

- 使用具体动词和技术对象，少用“进行处理”“相关内容”“某种机制”等空泛表达。
- 术语首次影响理解时就地解释，后文保持同一名称；无需把常见术语反复翻译。
- 标题负责定位，正文负责讲清原因、条件和边界；标题不承担完整答案。
- 避免“本文将”“如下所示”“为了方便大家”等写作过程话术，也不使用夸张口号、撒娇式提示或刻意幼化的比喻。
- 总结只收束真正需要保留的判断，不逐段复述正文。

自然表达不是口语化聊天。事实、命令、风险和限制仍应直接、准确，不能为了语气轻松模糊技术边界。

## 5. 闪卡回答与解析

`answer` 给出便于主动回忆的精简结论；`explanation` 负责让读者理解这个结论为什么成立。解析应当脱离正文仍能读懂，并根据问题复杂度交代：

- 结论成立的原因或机制；
- 关键步骤、状态变化或因果链；
- 容易误判的边界、反例或类比失效位置。

抽象或复杂问题还必须选择至少一种能把概念落到具体对象上的辅助表达，例如带注释代码、输入输出、比较表、文字流程、本地图片或有边界的类比。简单事实题在结论、原因和边界已经能够独立讲清时按需使用例子或对照，不为满足形式强行扩写。不得用固定字数、段落数或栏目数代替内容判断。

解析不得只重复答案、只列术语、只给无注释代码，或给出没有说明适用边界的类比。插件支持的 Markdown 富内容可以直接写入解析；Butterfly 标签、Tag Plugins Plus 标签和 Mermaid 不嵌套进闪卡。

## 6. 复习密度与迁移

`常见问题` 不设固定题数上限。题数由文章知识密度、易混淆边界和长期复习价值决定；能够在正文直接消除的误解不重复制卡，彼此高度重叠的问题应合并。

新建或本次编辑的文章立即执行本规范。编辑已有文章时，同一篇中的所有原始 `flashcard` 定义一起复查和升级；`flashcard_ref` 只继承原始定义，不复制修改。未进入当前修改范围的历史卡片作为待迁移内容报告，不阻断无关文章或全仓库检查。全部历史卡片完成迁移后，才单独确认是否升级为全仓库强制语义门禁。

## 7. 审查判断

审查时先读完整段落或解析，不凭某个词、字数或是否出现表格判断质量。以下任一情况都需要改写：

- 读者知道结论，却仍不知道原因或过程；
- 示例缺少输入、关键动作、输出或失败表现；
- 视觉、代码或类比没有承担正文无法更清楚表达的信息；
- 段落依赖正文外的上下文才能理解；
- 固定教学栏目压过了主题本身的自然结构；
- 语气幼稚、夸张、过度口语化或像自动生成的步骤模板。

通过信号是：读者能够沿着文字复述对象、机制、证据和边界，并知道下一步如何验证，而不是只记住一句结论。
