# 视觉丰富文章工作流

本工作流为 AI 新建文章和已有文章的整体视觉重构生成可确认的编排方案。它负责理解路径、文章结构、视觉角色和标签组合；教学方法遵循 `rules/technical-writing-style.md`；事实核对、Front Matter、正文写作与验证继续由 `workflows/§01-authoring.md` 负责。

## Phase 1：识别文章结构与视觉机会

1. 确认标题、目标读者、内容范围、文章类型、事实来源和资源公开边界。
2. 将正文主线拆成读者任务，例如理解概念、比较选项、完成步骤、观察关系、查看补充细节和继续阅读外部资料。
   - 对抽象、反直觉、易混淆和多步推理的难点，先记录卡点，再按技术文风规范设计概念开头的故事；不适合故事时说明替代推演或实验。操作步骤和安全提示不强行寓言化。
3. 读取 `references/butterfly-built-in-tags.md`；计划使用 Tag Plugins Plus 时同时读取 `references/butterfly-tag-plugins-plus.md`。
4. 以当前主题和插件源码为能力上限，不根据官网截图或历史文章假设本项目支持某个标签。

完成信号：每个拟规划章节都有明确读者任务，可用标签、配置门禁和资源边界已查明。

## Phase 2：形成视觉编排预案

1. 使用 `templates/article-visual-plan.template.md`，在对话中输出预案，不创建文件。
2. 按 `templates/article-visual-plan.template.md` 逐正文块写明内容目的、视觉角色、拟用标签、选择理由、依赖与失败降级；课程文章同时对照 `../hexo-learn-topic/rules/published-article-contract.md`。
   - 难点计划写明情境、选择与后果、揭示位置、隐喻映射和失效边界、迁移验证，以及图像帮助理解哪一步。课程故事标记按公开合同第 2.1 节设置，不作为标签数量。
   - 使用 Mermaid 流程图时，按 `references/butterfly-built-in-tags.md` 的内容密度规则注明 `LR` 或 `TD/TB` 及理由。
3. 默认按“每个有意义正文块都有渲染角色”进行视觉编排，主动评估以下角色，并组合所有与内容真实匹配的不同能力：
   - 开篇定位、结论、提示或风险：`note`、`tip`、`label`；
   - 平台、方案、代码或配置切换：`tabs`、`subtabs`；
   - 时间、步骤和演进过程：`timeline`；
   - 架构、关系、状态与数据：`mermaid`、`chartjs`、`progress`；
   - 补充细节、答案和长配置：`folding`、`hideToggle`、`hideBlock`；
   - 需要进入长期复习队列的 FAQ、面试题和自测：`flashcard`、`flashcard_ref`；
   - 操作入口和扩展阅读：`btn`、`btns/cell`、`link`、`linkgroup`；
   - 图片、相册和媒体：`gallery`、`galleryGroup`、`image`、`carousel`、`audio`、`video`；
   - 行内强调和术语注释：`label`、`kbd`、`bubble`、`nota`、`emp`。
4. 不设置固定标签数量；课程文章的结构内容与有界故事自然段按公开正文合同保留 Markdown，其他解释性正文块必须明确对应块级标签并通过审计；内容不支持某种角色时不虚构比较、数据、媒体或外部资源。
5. 避免单一组件连续主导文章。多个章节承担相近任务时，先检查能否用更贴合语义的不同表达；不能时保留一致结构并说明理由。
6. 核心结论、关键步骤、必要命令和风险直接展示；直接可见不等于必须在故事之前揭晓机制。故事主线连续可读，折叠与隐藏能力只承载片段外的可选预测、自测或补充。
7. 依赖网络、配置或脚本的标签必须写明普通正文、链接或静态内容降级；需要新增资源、改配置或上传外部文件时标记为待单独授权。

完成信号：预案形成连贯阅读主线和多样视觉节奏，每个标签都有真实信息目的，没有用组件填充空内容。

## Phase 3：等待用户确认

1. 展示完整预案，并明确说明确认前不会创建或修改文章。
2. 用户要求调整时，只修订受影响章节、标签、依赖或降级方式，再次展示完整预案。
3. 只有用户明确确认当前预案后，才返回 `workflows/§01-authoring.md` 创建或修改文章。
4. 用户取消、暂缓或未确认时停止写入，保留预案作为当前对话中的未实施方案。

完成信号：用户已明确确认一份完整、无冲突的当前预案。

## Phase 4：按确认预案写作

1. 按预案中的难点理解路径写故事、真实解释与验证，再插入已确认标签；AI 插图仅在确认范围内按 `workflows/§06-local-images.md` 生成并验收，不自动扩成系列封面重做。
2. 使用 `workflows/§04-tag-plugins-plus.md` 核对所有者、源码语法、容器闭合、配置和外部依赖。
3. 不因实现方便把多种标签缩减为单一 `note` 或 `folding`；也不为保留种类而写入与主题无关的内容。
4. 实施中若需要改变章节职责、标签组合、外部依赖或失败降级，先输出修订预案并等待确认。仅修正不改变视觉行为的语法错误不需要重新确认。

完成信号：文章结构和视觉角色与确认预案一致，正文脱离装饰仍可连续理解。

## Phase 5：对照预案验收

1. 在机械审计和 Hexo 构建后，逐节比较最终文章与确认预案，核对故事因果、揭示位置和真实映射，并用新情境检查迁移；标记有效或故事有趣不能替代机制正确性。
2. 使用 `checklists/maintenance-acceptance.md` 的“视觉丰富文章”“标签外挂”“视觉与可访问性”部分。
3. 在桌面和移动视口检查视觉节奏、长内容、展开状态和组件组合；Mermaid 使用 `LR` 时额外检查文字是否缩小、节点是否拥挤以及正文是否横向溢出，任一出现则改为 `TD/TB`；在明暗主题下检查文字、边框、图表和状态可辨认性。
4. 对网络卡片、远程媒体和脚本型标签验证失败降级；未执行的状态明确列为未验证。
5. 交付时列出实际使用的标签、与预案的差异、用户确认依据和页面证据。

失败路径：预案未确认、标签不受当前源码支持、配置关闭、资源不可公开、构建失败或真实页面不可读时停止交付；重新规划或修复后重跑受影响步骤。
