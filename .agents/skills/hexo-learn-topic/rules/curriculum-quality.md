# 课程路线与拆篇规则

## 1. 零基础路线

零基础表示不假设读者理解术语、工具链、运行模型和项目结构。路线仍应复用用户已经具备且经过确认的环境事实，不把已知内容机械重复成新文章。

前置分为：开始前必须具备、课程中补齐、可选拓展。只有第一类缺失会阻断路线。

## 2. 路线结构

路线从“为什么需要”进入“如何使用”，再到“如何工作、如何验证、如何排错和如何扩展”。开源项目默认继续到架构、核心调用链、测试与二次开发，但不强制 Patch。

每个阶段必须说明输入、学习成果、依赖、文章集合和完成判断。不得用“入门、进阶、高级”代替实际知识职责。

## 3. 文章拆分

- 第一轮学习大纲中的每个学习主题必须足够宽、名称简短且可以直接成为文章主题；不得先用宽泛主题组获得确认，再在第二轮暗中拆成多篇文章；
- `N` 个已确认学习主题必须一一对应 `N` 篇主题文章，文章标题固定为 `主题(序号)学习主题原名`，不得擅自拆分、合并、改写或遗漏学习主题；确需调整时返回第一轮，重新展示受影响的学习主题和文章安排并取得确认；
- 系列总数只能是 `N+1`、`N+2` 或 `N+3`：一篇 `主题(一)入门路线` 必选；一篇 `主题(序号)进阶路线` 可选；一篇结尾文章可选，且只能在 `主题(序号)综合实战`、`主题(序号)项目实战`、`主题(序号)知识总结` 中选择一个；
- 能形成完整项目时选择“项目实战”，适合跨主题场景或排障时选择“综合实战”，偏理论且没有合理实战时选择“知识总结”；可选进阶篇排在全部主题文章之后，可选实战或总结排在系列最后；
- 每篇只有一个主问题、一个唯一知识归属和一个可观察成果；
- 一篇覆盖一个足够宽的学习维度，不按单个 API 或单一功能点拆成短文；
- 文件名与标题保持简短，统一使用 `主题(序号)主题.md` 与 `主题(序号)主题` 格式；第一篇固定为 `主题(一)入门路线`，详细范围写入单行 `description`；
- 大纲写到足以暴露机制、示例、失败边界和验证的 H2/H3 粒度；
- 过长或过短说明第一轮学习主题粒度不合适，不得在第二轮直接拆分或合并文章；返回第一轮调整学习主题并重新确认；
- 交叉知识只设一个主归属，其他文章通过前置或链接引用；
- 文章依赖必须无环，阅读顺序不能依靠发布日期猜测；课程编号、文章依赖、篇内章节、示例步骤和练习都按知识依赖顺序排列。
- 低频、平台特定或明显超出常规主线的能力可以在第一轮学习大纲中汇总为最多一篇“进阶路线”，并在入门路线中标记为可选，不让核心项目依赖该篇。

## 4. 现有文章复用

复用前检查版本、零基础可读性、机制深度、完整示例、视觉、FAQ、自测和来源。全部满足才可直接纳入；否则在第二次确认中给出升级旧文或新建课程文章的影响，不未经确认修改旧文。

## 5. 知识负载与结构平衡

文章地图不能只证明官方能力“有归属”，还要证明归属适合学习。逐篇建立知识职责与负载审查：

- 一个主问题：全文能用一句话说明读者要解决的任务，不能用“了解全部功能”代替；
- 一个可观察成果：读者能够产出、判断、解释或修复某个结果，而不是只“知道概念”；
- 一个主心智模型：同一篇可以包含多个相关机制，但不能让两个互不依赖的核心模型争夺主线；
- 一条主操作链：安装、配置、运行、验证和排错可以形成闭环；无关的第二条工具链应进入其他主题或已确认进阶篇；
- 一个失败边界集合：失败项必须服务于主问题，不把所有历史故障堆入一篇。

出现下列任一信号时标记“疑似过载”，不能只靠增加 H2 或折叠内容掩盖：

- 需要分别建立两个以上互不依赖的核心心智模型；
- 同一篇包含多条可以独立完成的操作链或项目；
- H2 主要按 API、命令或配置键平铺，读者任务不清楚；
- 大量低频能力只能用名称清单或超长参考表容纳；
- 贯穿案例无法覆盖多数核心章节，只能不断更换场景。

出现下列任一信号时标记“疑似过轻”：

- 主题只对应单个 API、命令、配置键或术语；
- 只有定义和基本调用，没有机制、组合使用、失败边界与验证；
- 内容无法形成独立学习成果，必须依附下一篇才有意义。

负载判断不使用硬性字数、H2 数量或标签数量。疑似信号触发后回看知识依赖、主问题和学习成果：能在不改变第一轮主题的前提下重新分组 H2/H3 就在文章地图中调整；需要拆分、合并或改名学习主题时返回第一轮重新确认。

API、命令和配置项按读者任务、生命周期或失败模型分组，不按字母或源码导出顺序铺开。低频、平台特定和专项能力只进入已确认进阶路线，并按能力组说明用途、进入条件和选择边界，不能形成没有解释的名称仓库。

课程级审查还要建立文章间边界：每项交叉知识只有一个主解释位置，其他文章只给解决当前任务所需的短桥接和链接；不得重复完整定义、安装过程、通用配置、FAQ 或同一道闪卡。

## 6. 完整性证据

覆盖处置账本以 `rules/research-policy.md` 的官方能力全集为左表，逐项记录：稳定标识、对象或主题、来源、版本状态、处置、主文章、目标章节、理由和验证状态。处置只能是：

- `核心详解`：主线常用能力，正文解释机制、示例、边界和验证；
- `正文简述`：需要识别或偶尔使用，正文说明用途、选择边界和指向；
- `进阶路线`：低频、平台特定或专项能力，归入已确认的可选进阶篇；
- `弃用迁移`：弃用、Discouraged 或常见旧接口，正文说明替代项和迁移边界；
- `明确不纳入`：与课程语言绑定、运行器或目标无关，必须给出可复核理由，不能用来隐藏常用能力。

前四类正文处置必须且只能指定一个主文章与目标章节；`明确不纳入` 必须没有主文章和目标章节，但必须保留来源与可复核理由，只由 Curriculum Reviewer 审核，不进入单篇文章合同。官方稳定标识集合与账本稳定标识集合必须完全相等，且 `官方仅有`、`账本仅有`、重复与未处置均为 0。无来源条目、无理由排除或版本状态不明均为阻塞项。

Reviewer 必须从官方索引独立复算全集并与账本做全量差集，不得抽样，不得只检查作者已经列出的条目。覆盖账本服务于课程设计和查漏，不扩张成掌握度、作答或复习数据库，也不要求把每个 API 拆成独立文章。
