白盒测试从代码结构和控制流补充测试设计，覆盖率衡量“执行到了哪里”，不直接证明业务规则正确。本篇用一个有短路条件的资格函数手工推导语句与分支覆盖，再说明为什么仍需黑盒用例。

代码基础

条件与分支

先识别语句、条件、分支和短路求值。and/or 可能在左侧已经决定结果时不执行右侧表达式，因此“写在同一行”不等于“两个条件都被观察”。

短路求值

这段代码至少有两个判定：会员是否启用、借阅数是否小于 3，以及库存是否大于 0。要观察第二个条件的独立影响，必须准备能让第一个条件为真和为假的输入；当会员未启用时，借阅数可能根本没有被求值。

为了把短路事件单独记录下来，再看一个最小的 evaluate(a,b,c) 教学函数。它的五个可执行语句是两个条件判断和三个返回语句；can_borrow 只用于说明业务代码中的短路，后面的控制流和百分比都针对 evaluate，不混用两个函数。真实工具可能按不同口径统计函数定义、条件和分支，因此先记录执行轨迹，再解释百分比。

用例 输入 (a,b,c) 实际求值轨迹 返回值 覆盖意图
W1 (True, True, False) a=T、b=T，短路表达式为真；第二个 if 未执行 allow 通过主路径，c 尚未观察
W2 (False, True, True) a=F 后跳过 b；继续求值 c=T review 覆盖 a 的假和 c 的真
W3 (False, False, False) a=F 后跳过 b；继续求值 c=F deny 覆盖最终拒绝；b 仍未求值
W4 (True, False, False) a=T、b=F；继续求值 c=F deny 补 b 的假并观察第二个判定
W5 (True, True, True) a=T、b=T，直接返回，c 未求值 allow 说明满足前置条件时后续条件不可达
W6 (False, True, False) a=F 后跳过 b；继续求值 c=F deny 与 W1/W2 配对观察 a、c 的独立影响
W7 (True, False, True) a=T、b=F；继续求值 c=T review 说明 b 为假时仍可能进入 c 分支

因此 W1～W3 已经让五条语句都执行，a、c 都取到真/假，但 b 只观察到真；W4 补齐 b 的假和缺失的控制流边。W1 与 W4 只改变 b 且让首个判定由真变假，W1 与 W6 只改变 a（对照中 b 因短路未求值），W2 与 W6 只改变 c 且让第二个判定由真变假，这三对构成 evaluate 的 MC/DC 独立影响示例。本篇只展示推导，不宣称工具或业务达到 MC/DC。

在这个结构化函数中，按本篇教学模型，分支出口和返回语句一一对应，所以走过四个判定出口会同时走过五条可执行语句；这是本例的严格包含关系，不是所有工具报告的通用分母。工具若排除不可达代码、异常路径或函数定义，分母会变化，报告必须写清口径。输入赋值组合按调用者传入的元组统计，完整求值组合只统计 a、b 都实际读取的轨迹，三条件组合则把 c 也纳入八种输入元组；三者不能互换，未求值条件不能冒充已覆盖。

覆盖计算

指标 计算方式 能说明 不能说明
语句覆盖 执行语句数 / 可执行语句数 哪些语句运行过 条件的每个结果是否出现
分支覆盖 已执行分支 / 分支总数 if/else 路径是否走过 输入是否代表业务边界
条件覆盖 条件真/假结果是否出现 子条件结果的变化 组合关系是否完整
MC/DC 每个条件能独立影响判定 高完整性场景的独立影响 业务需求和外部依赖

例如只用“启用会员、借阅数 1、库存 1”可能命中 True 路径，但没有执行三个拒绝分支。覆盖率报告应和测试输入、版本及排除规则一起保存，不能只贴一个百分比；在 evaluate 中，W1-W3 的 (a,b) 输入赋值命中 3/4，W1-W4 的实际完整求值只命中 TT、TF 两种，即 2/4；把 c 加入后，W1-W4 只覆盖 4/8 个三条件输入元组。分母和“是否实际求值”必须写在报告中，不能把传入值冒充已观察结果。

条件与组合

未求值条件

用例 enabled borrowed < 3 stock > 0 结果 观察
B1 T T T True 全部条件为真
B2 T T F False 库存分支

B6 F — T False enabled 为假，借阅数和库存输入都未求值

独立影响

判定 基准用例 对照用例 只改变的已求值条件 判定结果变化
a and b W1 (T,T,F) W4 (T,F,F) b：T→F allow→deny
a and b W1 (T,T,F) W6 (F,T,F) a：T→F；b 在对照中未求值 allow→deny
c W2 (F,T,T) W6 (F,T,F) c：T→F；b 在两侧均未求值 review→deny

表中的“—”表示该条件在此用例中未求值，不是把它当作任意真或假。要达到条件覆盖，需要额外设计能让每个已求值条件分别取真和假；要达到 MC/DC，还要证明只改变一个条件就能改变整体判定。

业务边界

覆盖率局限

白盒覆盖发现代码路径缺口，黑盒方法验证需求、输入域、状态和用户结果。代码可能完整覆盖了“库存大于 0”的判断，却把业务上限写错为 3；因此覆盖率应作为风险导航，与需求追踪、边界和状态用例一起解释。

需求与实现 黑盒边界预期 结构覆盖可能出现的假象
最多可借 5 本；实现却写成 < 3 当前数为 2、3、4、5 且有库存时应允许；6 时拒绝 a、b、c 的真假和返回语句都可被覆盖，但当前数 4/5 仍错误返回拒绝

白盒测试的价值是较早暴露未执行分支、死代码、错误条件组合和异常处理缺口，并为风险排序提供客观证据。反例：can_borrow 把业务上限误写成 3 而需求规定最多 5 时，即使 enabled、borrowed 和 stock 的每个分支都走过，代码仍可能“全覆盖”；黑盒用例必须补借阅数 2、3、4、5、6 的边界和最终用户结果。这里记录 noMC/DCclaim：文章给出 MC/DC 配对推导，但没有运行覆盖工具或声称达到认证级指标。

现象 可能的误读 更稳的行动
语句 100% 以为没有 Bug 检查断言、规则、数据和异常路径
分支 100% 以为组合穷尽 检查条件交互、状态和外部依赖
低覆盖 直接补无意义脚本 先定位高风险未覆盖代码和不可达原因
报告有排除项 认为指标可比 说明版本、范围、排除理由和变化

黑白盒互补

白盒覆盖回答“代码路径是否执行”，黑盒用例回答“输入、状态和用户结果是否符合需求”。同一借阅规则可以用白盒分支覆盖检查拒绝路径，再用黑盒边界、权限和并发用例检查真实业务；两者都通过也只能说明已验证范围内的风险降低，不能推出无缺陷。

Q01中频
#测试基础#覆盖率#质量证据
问题:

为什么 100% 覆盖仍可能有 Bug？

回答：

覆盖率只说明执行路径，不能证明断言有效、业务规则完整、输入真实或外部依赖正确。

解析：

测试只调用函数而不检查返回值也能提高语句覆盖；错误的预期同样可能让测试通过。即使语句、分支都覆盖，需求可能漏了锁定状态，数据库事务可能错误，接口字段可能不符合契约。覆盖率应帮助寻找未执行区域，再与黑盒边界、状态、集成证据和业务验收共同判断。

短路求值导致右侧条件未执行时，覆盖率该怎么算？

点击查看答案
Q02中频
#测试基础#短路求值#条件覆盖
问题:

短路求值导致右侧条件未执行时，覆盖率该怎么算？

回答：

把未求值条件与“已求值为假/真”区分记录；它不应被伪装成已经覆盖的真假分支。

解析：

在 enabled and borrowed < 3 中，enabled 为假时右侧不会执行。报告通常按工具的分支/条件口径计算，但设计者要理解该路径没有观察右侧副作用或结果。补一条 enabled 为真、borrowed 达到上限的用例，才能真正执行并覆盖右侧假分支；若依赖短路是安全要求，也要写成明确的断言。

语句覆盖和分支覆盖是什么关系？

点击查看答案
Q03中频
#测试基础#语句覆盖#分支覆盖
问题:

语句覆盖和分支覆盖是什么关系？

回答：

在同一可执行结构、采用同一排除口径时，语句覆盖关注语句是否执行，分支覆盖关注控制流出口是否都走过；100% 分支覆盖会包含 100% 语句覆盖，但反向不成立。分支覆盖仍不等于条件组合、MC/DC 或业务完整。

解析：

一条只走 True 的路径可能执行 if 内语句，却没有走 else 分支；因此语句覆盖可以很高而分支覆盖仍不足。反过来，在本篇这种每个分支出口都落到可执行返回语句的结构中，分支全覆盖会同时覆盖语句；复杂控制流若存在不可执行边、异常边或工具排除项，仍必须以实际报告口径为准。分支覆盖也不自动覆盖多条件的独立影响、边界数据、状态迁移和外部失败。报告时写清指标口径、可执行代码范围和排除项，并把缺口转成有业务理由的测试。
