本文把整门课程收束成可复用的面试和排障工作流：先画完整访问链路，再根据现象选择证据，最后说明结论的适用范围。传统链路是 DNS → TCP → TLS → HTTP，现代链路是 DNS → QUIC（集成 TLS 1.3）→ HTTP/3。

综合题方法

五段式回答

遇到“网页为什么打不开”“HTTP 请求经历了什么”“TCP 和 QUIC 怎么选”时，不要从背诵协议名开始：

  1. 现象：明确是解析失败、连接拒绝、握手超时、证书错误、HTTP 状态还是业务内容错误；
  2. 假设：只提出当前证据支持的最小假设，例如“DNS 没有返回地址”；
  3. 证据：选择能证伪假设的工具输入、时间线、字段或日志；
  4. 结论：说明已验证到哪一层，以及故障边界在哪里；
  5. 下一步：给出最小、只读、可恢复的后续检查。
    flowchart TD
  OBS[现象] --> HYP[最小假设]
  HYP --> TEST[选择可证伪证据]
  TEST --> RESULT{证据支持吗}
  RESULT -->|否| HYP2[更新假设，不扩大操作]
  HYP2 --> TEST
  RESULT -->|是| CONC[带边界的结论]
  CONC --> NEXT[下一层或修复前的最小验证]

进阶主题的共同边界

DSCP/QoS、组播、动态路由、WebDAV 和状态注册表都可能出现在真实系统中，但它们不应被用来替代主线证据。先回答“当前请求是否有地址、连接、加密和 HTTP 响应”，再决定是否进入扩展协议。

经典请求链路

双端时序

    sequenceDiagram
  participant B as 浏览器/客户端
  participant R as DNS Resolver
  participant S as TCP/TLS/HTTP 服务
  B->>R: 查询 example.test 的地址
  R-->>B: A/AAAA 地址
  B->>S: TCP SYN
  S-->>B: SYN-ACK
  B->>S: ACK
  B->>S: TLS 1.3 ClientHello + SNI/ALPN
  S-->>B: ServerHello + Certificate + Finished
  B->>S: HTTP request
  S-->>B: HTTP status + fields + content

每一步能观察什么

阶段 客户端证据 服务端/抓包证据 失败时不要越界
DNS resolver 地址、A/AAAA、耗时 DNS query/response、NXDOMAIN/SERVFAIL 没有地址就不要分析目标 TCP
TCP connect 成功/拒绝/超时 SYN、SYN-ACK、RST、重传、四元组 TCP 成功不代表 TLS/HTTP 成功
TLS 版本、证书、ALPN、校验错误 ClientHello、ServerHello、证书链、alert 证书成功不代表业务认证通过
HTTP 方法、状态、缓存/CORS、内容 请求字段、响应字段、网关/上游日志 404/502 是 HTTP 结果，不是 DNS 错误

经典链路的可复现入口

复现时先使用公共示例或本地固定夹具，记录命令版本、目标、时间和脱敏后的输出：

命令输出未在本文预先伪造。真实结果可能受解析器、目标站点、网络策略和客户端构建选项影响；报告中应粘贴最小必要字段，并隐藏 Cookie、Authorization 和内部地址。

现代请求链路

传输和应用的关系

    sequenceDiagram
  participant B as 浏览器/客户端
  participant R as DNS Resolver
  participant H as HTTPS/HTTP2 服务
  participant Q as QUIC/HTTP3 服务
  B->>R: 查询 example.test 的地址
  R-->>B: A/AAAA 地址
  B->>H: 先建立经典 HTTPS 请求
  H-->>B: 响应中的协议提示（如 Alt-Svc）
  B->>Q: UDP Initial + QUIC ClientHello
  Q-->>B: QUIC handshake + TLS 1.3 参数
  B->>Q: HTTP/3 HEADERS/DATA on request stream
  Q-->>B: HTTP/3 HEADERS/DATA
  Note over B,Q: 其他 stream 的丢包不必阻塞所有应用 stream

与经典链路对照

观察项 经典链路 现代链路
传输入口 TCP 443 UDP 443 常见，但以服务端和路径配置为准
安全握手 TLS 运行在 TCP 之上 QUIC 集成 TLS 1.3 握手和密钥保护
并发 HTTP/2 stream 共享 TCP 按序交付 HTTP/3 stream 使用 QUIC 的独立传输语义
回退 可从 h2 回到 HTTP/1.1 HTTP/3 失败可能回退到 TCP 上的 h2/h1
证据难度 TLS/HTTP 字段较容易由工具解析 QUIC 加密、UDP 策略、浏览器支持需额外确认

现代链路的验证边界

curl --http3 只有在本机 curl 编译支持 HTTP/3 且目标服务提供时才有意义；浏览器的协议选择还受到 Alt-Svc、缓存、代理、UDP 可达性和回退状态影响。看到最终请求使用 h2，不能证明服务端没有 h3；看到 UDP 包，也不能证明 HTTP/3 已经完成。

失败场景

夹具对照

下面四个主线场景沿用相同的证据边界，本文只保留对照关系，不复制 (七) 中的六段夹具操作：

夹具 预期停在哪一层 面试式结论
.invalid DNS 失败 DNS 没有目标地址，因此没有目标 TCP/HTTP 证据
loopback 未监听端口 TCP 地址可用但没有监听，通常快速拒绝；没有 HTTP 状态
自签名 HTTPS TLS TCP 建立后证书信任/主机名校验失败；-k 只是临时降低校验
固定 304/502/504 HTTP 已收到 HTTP 响应，继续看缓存字段、网关路径和上游证据

从现象到下一条证据

    flowchart TD
  P[页面失败] --> N{DNS 有地址?}
  N -->|否| N1[查 resolver、NXDOMAIN/SERVFAIL、DNS 抓包]
  N -->|是| T{TCP/QUIC 建立?}
  T -->|否| T1[查 SYN/RST/UDP、路由和策略]
  T -->|是| S{TLS 校验/协议成功?}
  S -->|否| S1[查 SAN、信任链、SNI、ALPN、alert]
  S -->|是| H{HTTP 状态/内容正常?}
  H -->|否| H1[查状态、缓存、CORS、代理和上游日志]
  H -->|是| OK[进入应用业务与性能分析]

回答失败题时，要先说“我目前已验证到哪一层”，再说“下一层还没有证据”。这是比“应该是防火墙”“重启服务就好”更可靠的面试和生产沟通方式。

进阶边界

DSCP/QoS、组播、动态路由、WebDAV 和状态注册表的概念、用途与进入条件统一放在“进阶路线”。综合实战只保留“是否需要进入扩展协议”的判断，不在这里重新解释这些机制。

Q01高频
#计算机网络#DNS#递归
问题:

递归解析器与权威服务器在一次 DNS 查询中分别做什么？

回答：

客户端通常请求递归解析器代为查找；权威服务器负责给出自己负责区域的最终记录。

解析：

递归解析器可能沿根、顶级域和权威链路迭代查询，并使用缓存缩短后续路径。

Q02高频
#计算机网络#TCP#三次握手

TCP 三次握手分别确认什么？

点击查看答案
Q02高频
#计算机网络#TCP#三次握手
问题:

TCP 三次握手分别确认什么？

回答：

客户端 SYN 提供客户端 ISN；服务端 SYN-ACK 确认客户端 ISN 并提供服务端 ISN；客户端 ACK 确认服务端 ISN，双方进入已建立状态。

解析：

三次的关键是双向初始序列空间和回程可达性。握手成功不代表应用已经完成 TLS、HTTP 或业务认证。

Q03高频
#计算机网络#tcpdump#Wireshark#过滤器

tcpdump 捕获过滤器和 Wireshark 显示过滤器有什么区别？

点击查看答案
Q03高频
#计算机网络#tcpdump#Wireshark#过滤器
问题:

tcpdump 捕获过滤器和 Wireshark 显示过滤器有什么区别？

回答：

tcpdump 在采集时用 BPF 减少写入的数据，Wireshark 在已捕获数据上按协议字段筛选；两者语法和证据阶段不同。

解析：

例如 tcpdump 使用 host/tcp port，Wireshark 使用 ip.addr/tcp.port/tcp.stream。先用宽过滤器确认包存在，再逐步收窄。

Q04高频
#计算机网络#HTTP#状态码

HTTP 状态码 2xx、3xx、4xx、5xx 如何按层次解释？

点击查看答案
Q04高频
#计算机网络#HTTP#状态码
问题:

HTTP 状态码 2xx、3xx、4xx、5xx 如何按层次解释？

回答：

2xx 表示成功处理，3xx 表示重定向或条件结果，4xx 表示请求/客户端上下文问题，5xx 表示服务端或网关处理失败。

解析：

状态码只能证明 HTTP 层的观察结果。DNS 失败、TCP 拒绝、TLS 证书错误通常没有 HTTP 状态码，应先区分是否收到响应。

Q05高频
#计算机网络#TLS 1.3#握手

TLS 1.3 握手要完成哪些核心目标？

点击查看答案
Q05高频
#计算机网络#TLS 1.3#握手
问题:

TLS 1.3 握手要完成哪些核心目标？

回答：

协商密码与密钥交换参数，建立受保护的握手和应用流量密钥，并通过证书/签名让客户端验证服务端身份。

解析：

TLS 负责加密传输和端点认证机制，不负责 HTTP 方法或业务授权。0-RTT 虽减少等待，但早期数据要考虑重放。

Q06高频
#计算机网络#QUIC#UDP#TLS 1.3

QUIC 为什么不能简单理解为“没有连接的 UDP”？

点击查看答案
Q06高频
#计算机网络#QUIC#UDP#TLS 1.3
问题:

QUIC 为什么不能简单理解为“没有连接的 UDP”？

回答：

QUIC 在 UDP 上实现了连接 ID、确认、丢包恢复、拥塞控制、独立流和加密，并集成 TLS 1.3 握手。

解析：

UDP 只是 QUIC 的数据报封装入口。HTTP/3 依赖 QUIC 的传输能力，因此“使用 UDP”不等于没有可靠性或安全状态。

Q07高频
#计算机网络#HTTP/3#QPACK

HTTP/3 和 QPACK 的关系是什么？

点击查看答案
Q07高频
#计算机网络#HTTP/3#QPACK
问题:

HTTP/3 和 QPACK 的关系是什么？

回答：

HTTP/3 把 HTTP 语义映射到 QUIC stream/frame，QPACK 用于压缩 HTTP 字段，适配 QUIC 的并发流模型。

解析：

QPACK 是压缩，不是加密；机密性和完整性来自 QUIC 的 TLS 1.3 密钥保护。动态表和引用阻塞仍可能影响延迟。

Q08高频
#计算机网络#DNS#TCP#TLS#HTTP

如何区分 DNS 失败、TCP 拒绝、TLS 证书失败和 HTTP 502？

点击查看答案
Q08高频
#计算机网络#DNS#TCP#TLS#HTTP
问题:

如何区分 DNS 失败、TCP 拒绝、TLS 证书失败和 HTTP 502？

回答：

DNS 失败没有目标 IP，TCP 拒绝没有建立连接，TLS 失败通常 TCP 已建立但证书/握手未通过，502 则说明某个 HTTP 网关已经返回响应。

解析：

错误字符串可能随客户端变化，必须结合 DNS 查询、SYN/RST、TLS 握手和响应头判断，不要把所有现象称为“网络不通”。

自测时任选一条链路，分别写出：目标名称/地址、连接入口、握手字段、应用协议、失败证据、下一条只读验证。若答案只剩“网络有问题”，说明还没有回到证据层。

旧笔记中的易错结论

旧式绝对化表述 迁移后的回答
HTTP 总是运行在 TCP 上 HTTP/1.1/2 常见于 TCP，HTTP/3 运行在 QUIC；先区分语义与承载
HTTP/2 消除了队头阻塞 它缓解应用层队头阻塞，TCP 丢包仍影响连接；QUIC stream 进一步改变传输边界
TLS 只靠静态 RSA 传 premaster 以 TLS 1.3 临时密钥交换和密钥调度为主，旧版本仅作迁移背景
502 就是后端挂了 502 是网关观察到上游无效响应，需沿网关/上游时间线定位
看到 102 就是普通处理中 102 属 WebDAV 历史语境，先查规范和客户端支持
抓包文件可以随便共享 抓包是敏感证据，必须限制范围、脱敏、精确清理并记录验证层级

Q10高频
#计算机网络#QUIC#TCP#回退

QUIC 的 UDP 失败后会自动变成 TCP 吗？

点击查看答案
Q10高频
#计算机网络#QUIC#TCP#回退
问题:

QUIC 的 UDP 失败后会自动变成 TCP 吗？

回答：

不会由 UDP 协议本身自动转换。是否回退到 HTTP/2 或 HTTP/1.1 由客户端、浏览器、服务器和部署提示共同决定。

解析：

验证时记录协议提示、UDP 可达性、QUIC 错误和最终协商结果，不能把回退当作传输层自动行为。

Q11高频
#计算机网络#HTTP#502#504#排障

看到 502/504 还能继续抓 TCP 吗？

点击查看答案
Q11高频
#计算机网络#HTTP#502#504#排障
问题:

看到 502/504 还能继续抓 TCP 吗？

回答：

可以，但问题已经至少到达某个 HTTP 网关；还要检查客户端到网关以及网关到上游的两段链路。

解析：

只在客户端重复抓包可能看不到真正故障段，应同时看网关到上游的 DNS、TCP、TLS 和超时日志。
