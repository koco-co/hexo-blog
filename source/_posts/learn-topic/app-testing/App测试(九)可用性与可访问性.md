{% note primary flat %}
可用性看用户能否完成任务、理解反馈并从错误中恢复；可访问性进一步要求不同视觉、听觉、运动和认知能力的用户能用自己的输入方式完成同一目标。两者都要以真实任务和可观察证据收尾。
{% endnote %}

{% course_series %}

## 任务可用性

{% note info flat %}
选一条从启动到核心结果完成的真实旅程，记录第一次尝试、误操作、停顿、求助和恢复。不要只测熟悉 App 的顺利路径。
{% endnote %}

### 主旅程

| 阶段 | 用户动作 | 观察点 | 工件 |
| --- | --- | --- | --- |
| 进入 | 启动并找到功能 | 入口是否可发现 | 起点截图、计时 |
| 输入 | 填写和修改数据 | 标签、键盘和错误提示 | 操作录屏 |
| 提交 | 确认并等待结果 | 状态反馈、重复提交 | 请求时间线 |
| 完成 | 找到结果或下一步 | 成功是否可理解 | 结果截图 |
| 恢复 | 故意输入错误 | 内容保留、重试和返回 | 失败与恢复记录 |

### 任务时间线

{% timeline 一次任务的可用性, blue %}
<!-- timeline 起点 -->
固定账号、数据、设备和目标，把任务目标用用户语言写出。
<!-- endtimeline -->
<!-- timeline 首次尝试 -->
不提示操作顺序，让执行者独立完成并记录停顿、回退和误触。
<!-- endtimeline -->
<!-- timeline 反馈 -->
检查加载、成功、错误和空状态是否告诉用户下一步。
<!-- endtimeline -->
<!-- timeline 恢复 -->
输入错误、断网或返回后，验证数据保留和重新进入路径。
<!-- endtimeline -->
<!-- timeline 结论 -->
将观察转换为可复现问题、影响范围和建议修复。
<!-- endtimeline -->
{% endtimeline %}

{% note warning flat %}
如果只有作者本人能顺利完成任务，先把它标为可用性风险。重新用新手、空数据和错误输入复验，直到入口、反馈和恢复都能被独立理解。
{% endnote %}

## 视觉可达性

### 显示设置

| 设置 | 检查 | 失败表现 |
| --- | --- | --- |
| 字体放大 | 文本重排和滚动 | 截断、重叠或按钮不可见 |
| 显示缩放 | 触控区和图标 | 点击范围偏移 |
| 深色模式 | 前景/背景和图片 | 对比不足、信息消失 |
| 高对比度 | 边界、焦点和状态 | 仅靠颜色表达 |
| 横竖屏 | 布局与焦点 | 内容跳位或输入丢失 |

{% note info flat %}
对比度工具只能筛出候选问题，不能代替真实任务。状态颜色、错误图标、文字提示和焦点样式应共同表达同一个结论。
{% endnote %}

### 动态文本

1. 将系统字体调大，重走输入、滚动和提交。
2. 检查文本是否被裁剪、遮挡或必须水平滚动。
3. 观察错误提示是否与输入控件保持关联。
4. 恢复默认设置后确认页面不会保留错误的缓存尺寸。

## 语义可达性

{% mermaid %}
flowchart TD
  A[视觉控件] --> B[语义节点]
  B --> C[角色与名称]
  B --> D[状态与值]
  C --> E[辅助技术可读]
  D --> E
  E --> F[用户完成任务]
  E -->|缺少语义| G[定位或理解失败]
{% endmermaid %}

{% note info flat %}
语义树失效时仍按控件→角色/名称→状态/值→辅助技术朗读→任务结果检查。可见文字存在，不代表读屏器能获得同样的信息。
{% endnote %}

### 名称与状态

| 控件 | 应暴露 | 典型问题 |
| --- | --- | --- |
| 图标按钮 | 可执行动作名称和 enabled 状态 | 只有装饰性 content description |
| 输入框 | 标签、提示、错误和当前值 | 焦点后无法知道用途 |
| 复选框 | checked、可点击和说明 | 只读文字没有状态 |
| 列表项 | 角色、标题、摘要和操作 | 多个节点读成一段无意义文本 |
| 加载控件 | busy 或进度含义 | 视觉转圈但无朗读反馈 |

### 语义实验

1. 用无障碍扫描工具检查可点击控件、文本对比度和触控区域。
2. 用层级查看或辅助技术读出同一页面。
3. 将朗读结果与用户要完成的任务逐句对照。
4. 修复后保存修复前后语义树或扫描报告。

{% note warning flat %}
扫描器没有报错不代表任务可访问。它通常不能判断朗读顺序、业务文案是否清晰、动态状态是否及时更新，必须加入人工辅助技术复验。
{% endnote %}

## 辅助技术

### TalkBack

| 动作 | 观察点 | 通过条件 |
| --- | --- | --- |
| 连续滑动浏览 | 节点顺序和分组 | 顺序符合任务逻辑 |
| 双击激活 | 控件名称和状态 | 能执行且反馈明确 |
| 编辑输入 | 标签、错误和键盘 | 可定位并修正 |
| 返回与弹窗 | 焦点落点 | 不困在不可见区域 |

{% note primary flat %}
用 TalkBack 完成一次完整任务，不要只朗读首页。任务中途出现焦点跳到装饰图、弹窗关闭后焦点丢失或结果未朗读，都应保留操作顺序和屏幕状态。
{% endnote %}

### 其他输入

| 输入方式 | 适合验证 | 风险 |
| --- | --- | --- |
| 外接键盘 | 焦点顺序、快捷键和提交 | 焦点不可见或循环 |
| 开关控制 | 可聚焦、可激活和状态反馈 | 小控件难以选择 |
| 语音输入 | 编辑、纠错和确认 | 结果不可读或被截断 |
| 放大手势 | 局部阅读和定位 | 页面被放大后控件出界 |

## 替代输入

### 焦点顺序

1. 从页面顶部开始，只用键盘或辅助技术移动焦点。
2. 标记视觉顺序、语义顺序和业务顺序不一致的位置。
3. 检查弹窗打开、关闭和页面返回后的焦点落点。
4. 对不可操作的装饰节点确认不会抢占焦点。

### 触控与手势

{% note info flat %}
触控目标应在常见设备和显示缩放下可命中；需要拖拽、长按或多指操作时，提供可发现的替代入口，不把复杂手势作为唯一完成方式。
{% endnote %}

## 缺陷证据

| 字段 | 示例 | 价值 |
| --- | --- | --- |
| 任务 | 用读屏完成登录并查看结果 | 明确用户目标 |
| 输入 | TalkBack、键盘或放大设置 | 明确能力条件 |
| 步骤 | 每次焦点移动和选择 | 可复现失败 |
| 预期 | 节点名称、顺序和状态 | 明确可访问契约 |
| 实际 | 朗读缺失、焦点跳转或截断 | 描述用户影响 |
| 工件 | 录屏、语义树、截图和系统设置 | 支撑修复与复验 |

{% note warning flat %}
报告无障碍缺陷时描述任务阻断和替代路径，不只写“没有 content description”。同一个技术原因对不同用户可能造成无法发现、无法理解或无法操作三种不同影响。
{% endnote %}

## 常见问题

{% flashcard basic id:app-testing-content-description deck:"App测试" priority:1 tags:"可访问性,语义" %}
--- question
为什么给图标补了 content description，仍不能说明无障碍测试通过？
--- answer
还要验证角色、朗读顺序、状态变化、焦点和完整任务是否可完成。
--- explanation
`content description` 是给 TalkBack 等辅助技术读取的文字名称；它解决“这个图标叫什么”，却不自动补齐控件角色、状态和操作结果。比如“收藏”图标还要让辅助技术知道它是按钮、当前是否已选中，点击后焦点是否仍在合理位置。名称可能被重复朗读、放在错误顺序或遗漏 `selected/checked` 状态，因此应使用辅助技术完成主旅程，并保留语义树 (辅助技术看到的控件结构) 和结果证据。
{% endflashcard %}

{% flashcard basic id:app-testing-focus-order deck:"App测试" priority:2 tags:"可访问性,焦点" %}
--- question
焦点顺序错乱应该怎样复验？
--- answer
从已知起点只用键盘或 TalkBack 按任务顺序移动焦点，记录每一步的节点、状态和预期。
--- explanation
焦点顺序是键盘或 TalkBack 移动控件的顺序，不一定等于屏幕上的视觉顺序。修复后要从固定起点按用户任务逐步移动，复验弹窗打开/关闭、返回页面、错误提示和动态列表更新；焦点不能落到装饰节点或跳过必填控件。失败时保存录屏和语义树 (辅助技术看到的控件结构)，这样才能说明用户在哪一步被阻断。
{% endflashcard %}
