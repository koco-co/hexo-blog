{% note warning flat %}
同一个登录失败，既可以被记录成“按钮没有反应”，也可以被拆成用户损失、可观察证据和责任边界。测试策略的价值，就是把这种观察转换成可执行的测试组合和明确的发布判断。
{% endnote %}

{% course_series %}

## 移动测试边界

{% note warning flat %}
本篇只讨论 Android App 的发布质量闭环。黑盒验证用户可见行为，灰盒验证系统状态和证据；两者互相补强，但都不能替代专业安全评估或产品验收。
{% endnote %}

### 黑盒与灰盒

{% note info flat %}
用同一个失败登录场景对照两种视角，避免把内部日志直接当成用户结论。
{% endnote %}

| 视角 | 观察对象 | 最小证据 | 不能直接推出 |
| --- | --- | --- | --- |
| 黑盒 | 输入、按钮、错误提示、页面转移 | 操作步骤、录屏或截图、实际提示 | 不能证明服务端没有收到请求 |
| 灰盒 | 请求结果、前台 Activity、进程和日志 | 时间戳、logcat、状态快照 | 不能替用户判断提示是否可理解 |
| 组合 | 用户现象与内部状态是否一致 | 同一时间线上的两组证据 | 不能跳过需求和隐私边界 |

{% note primary flat %}
如果灰盒证据改变了黑盒预期，例如日志显示请求成功但界面仍提示失败，应先回到需求和状态定义，而不是直接把日志当成“测试通过”。
{% endnote %}

### 团队职责

{% note primary flat %}
把问题交给能够补齐证据的人，RACI 才有实际作用。
{% endnote %}

| 工作项 | 产品 | 开发 | 测试 | 安全或运维 |
| --- | --- | --- | --- | --- |
| 验收口径 | A | C | R | C |
| 可测性入口 | C | A/R | C | C |
| 风险证据 | C | C | A/R | C |
| 高风险专项 | C | C | R | A/R |
| 发布签字 | A | C | R | C |

{% note info flat %}
表中 A 表示最终负责，R 表示执行，C 表示提供咨询。一个缺陷如果没有唯一的 A，就先暂停流转并补齐所有者。
{% endnote %}

## 质量风险

{% note primary flat %}
风险不是“严重或不严重”的印象，而是影响范围、发生可能、可探测性和恢复成本的组合。评分只是排序工具，必须能回指具体旅程和证据。
{% endnote %}

### 用户旅程

{% note info flat %}
先把顺利路径和被打断路径放在同一张表里，再决定测试深度。
{% endnote %}

| 状态 | 关键动作 | 可能损失 | 需要观察 |
| --- | --- | --- | --- |
| 未启动 | 冷启动 App | 入口不可见、数据丢失 | 启动结果和首屏时间 |
| 未登录 | 提交凭据 | 无法进入核心功能 | 错误提示、重试和输入保留 |
| 已登录 | 完成核心操作 | 订单或内容状态错误 | 服务端结果与界面状态 |
| 被打断 | 来电、通知、旋转或切后台 | 回到错误页面 | 中断前后的状态一致性 |
| 会话失效 | 返回 App | 重复操作或越权 | 重新认证和数据清理 |
| 已退出 | 清理会话 | 下一用户看到旧数据 | 账号、缓存和后台任务 |

### 风险矩阵

{% note info flat %}
示例分值使用 1～5 排序，不把分值本身当成质量结论。
{% endnote %}

| 场景 | 影响 I | 可能 P | 探测难度 D | 恢复成本 R | 优先级依据 |
| --- | ---: | ---: | ---: | ---: | --- |
| 登录后展示他人数据 | 5 | 2 | 4 | 5 | 安全和隐私后果高，优先人工与灰盒核对 |
| 弱网重复提交 | 4 | 4 | 3 | 4 | 可能造成重复业务，优先状态机与网络切换 |
| 普通列表样式错位 | 2 | 3 | 1 | 1 | 兼容矩阵抽样覆盖即可 |

{% note warning flat %}
如果不同场景被打成同一优先级，说明评分没有帮助决策，应补充用户损失或重新定义等级。
{% endnote %}

## 测试分层

{% note primary flat %}
测试层级按反馈速度和环境保真度组合，而不是按工具名称排列。越靠近真实设备，能观察的系统行为越多，成本和诊断难度也越高。
{% endnote %}

{% mermaid %}
flowchart TD
  A[静态检查与单元] --> B[组件与 API]
  B --> C[少量 UI 回归]
  C --> D[模拟器与真机应用测试]
  D --> E[候选版本与人工探索]
  E -->|发现回归| B
  E -->|发现设备差异| D
{% endmermaid %}

{% note info flat %}
图失效时，仍可按“静态/单元 → 组件/API → UI → 设备应用 → 候选版本”理解顺序；失败回路表示回到能最快定位问题的层级。
{% endnote %}

### 反馈速度

| 层级 | 典型触发 | 适合发现 | 失败后的动作 |
| --- | --- | --- | --- |
| 静态与单元 | 每次提交 | 类型、纯逻辑和边界条件 | 在合并前修复 |
| 组件与 API | 合并前 | 组件协作、协议和数据映射 | 保留请求与响应证据 |
| UI 回归 | 合并前或每日 | 页面状态和少量主旅程 | 记录设备与构建 |
| 应用测试 | 合并后 | 真实进程、权限和系统行为 | 回到 ADB 证据链 |
| 候选版本 | 发布前 | 设备差异、探索性缺陷和残余风险 | 暂停发布或签收风险 |

### 环境保真度

| 环境 | 能观察什么 | 不足以证明什么 |
| --- | --- | --- |
| JVM 或假对象 | 业务逻辑和错误分支 | 真实渲染、权限和厂商行为 |
| 模拟器 | API 版本、尺寸、系统入口 | 厂商功耗、真实传感器和射频 |
| 本地真机 | 性能、硬件和系统打断 | 大规模设备分布 |
| 云真机 | 设备组合和远程回归 | 本地网络、专用外设和隐私数据 |

{% note warning flat %}
模拟器结果不能直接替代电量、厂商 ROM 或专用硬件结论；这类判断要转到真机复验。
{% endnote %}

## 用例设计

{% note info flat %}
用例的最小单位不是一个按钮，而是一个状态转移：给出前置状态、触发动作、预期状态和证据。组合覆盖先排除不可能的组合，再保留高风险组合。
{% endnote %}

### 状态转换

| 当前状态 | 触发 | 目标状态 | 必留证据 |
| --- | --- | --- | --- |
| 未登录 | 提交有效凭据 | 已登录 | 响应结果、页面和会话状态 |
| 未登录 | 拒绝权限或凭据 | 未登录 | 错误提示、输入保留规则 |
| 认证中 | 超时或断网 | 未登录或可重试 | 超时提示和请求终止 |
| 已登录 | Token 失效 | 会话失效 | 清理范围和重新登录入口 |
| 会话失效 | 重新认证 | 已登录 | 原任务是否可恢复 |

{% note warning flat %}
出现没有入边的状态，或出现无法恢复的状态，说明状态图缺少用例。
{% endnote %}

### 组合覆盖

| 维度 | 候选值 | 先排除 |
| --- | --- | --- |
| API 级别 | 最低支持、当前主流、最新预览 | 不支持的系统版本 |
| 设备形态 | 手机、平板、折叠屏 | 产品明确不支持的形态 |
| 权限 | 首次、拒绝、已授权 | 功能不会触发的权限 |
| 网络 | 在线、离线、切换 | 任务不产生网络请求的步骤 |
| 账号 | 新用户、已有数据、会话失效 | 与目标旅程无关的账号 |

{% note info flat %}
两两组合适合削减矩阵规模，但支付、隐私和数据迁移等高风险组合要手工补回。
{% endnote %}

## 缺陷与门禁

{% note warning flat %}
测试结果只有在证据可复现、风险有负责人、退出条件已满足时才具有发布意义。缺少指标时，结论应是暂停，而不是默认通过。
{% endnote %}

### 证据标准

| 字段 | 示例 | 缺失后的影响 |
| --- | --- | --- |
| 构建 | 版本号和变更范围 | 无法确认缺陷属于哪个候选 |
| 设备 | 型号、系统、API 和连接方式 | 无法判断兼容性边界 |
| 账号 | 脱敏后的角色和数据前置 | 复现路径可能不同 |
| 步骤 | 从干净状态开始的动作 | 开发无法按同一顺序复现 |
| 预期/实际 | 可观察的差异 | 缺陷描述只能停留在感受 |
| 原始工件 | 截图、日志、录屏或报告 | 无法验证结论来源 |

### 退出准则

1. 清点 P0/P1 未解决项，并确认每一项都有处置决定。
2. 检查高风险旅程的通过率、失败样本和回归范围。
3. 确认稳定性运行、设备矩阵和自动化报告均有可回查工件。
4. 把已知风险、影响范围、缓解方案和负责人写入发布记录。
5. 任一关键指标缺失时暂停签字，补齐数据后重新评审。

## 常见问题

{% flashcard basic id:app-testing-risk-vs-coverage deck:"App测试" priority:1 tags:"策略,风险" %}
--- question
为什么不能用“测试用例数量”直接代表 App 测试覆盖率？
--- answer
数量没有说明风险、状态和设备组合是否被覆盖。
--- explanation
覆盖率要回答“哪些风险在什么条件下被验证”，而不是“写了多少条用例”。同一条顺利路径可以在多个设备上重复，却仍遗漏拒绝、断网和进程死亡。

| 维度 | 需要回答的问题 |
| --- | --- |
| 风险 | 哪些用户损失最严重？ |
| 状态 | 哪些状态转移和恢复路径被验证？ |
| 环境 | 哪些系统、形态和硬件差异会改变结果？ |
| 证据 | 失败能否由另一位成员复现？ |

因此，发布判断应同时看风险矩阵、状态覆盖、设备矩阵和证据完整性；数量只能作为工作量指标。
{% endflashcard %}
