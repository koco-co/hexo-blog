{% note info flat %}
本文把“页面打不开”拆成可验证的证据链：浏览器看到什么，curl 能否复刻，DNS 是否解析，TCP 或 QUIC 是否建立，TLS 是否通过，HTTP 是否返回，以及代理和缓存是否改变了结果。每个结论都标明已经看到的证据和仍未验证的边界。
{% endnote %}

## 证据分层

### 一条请求的证据链

{% note info flat %}
“页面打不开”不是协议层结论。可以用下面的顺序把它拆开：
{% endnote %}

{% mermaid %}
flowchart TD
  START[用户现象：页面打不开/变慢] --> DNS{DNS 有响应吗}
  DNS -->|否| DFAIL[名称解析失败或超时]
  DNS -->|是| TCP{TCP/QUIC 建立了吗}
  TCP -->|否| TFAIL[拒绝、超时、路径或策略]
  TCP -->|是| TLS{TLS/证书/ALPN 通过了吗}
  TLS -->|否| TLSFAIL[证书、主机名、协议协商或加密错误]
  TLS -->|是| HTTP{有 HTTP 响应吗}
  HTTP -->|否| HFAIL[连接后无响应、代理或应用等待]
  HTTP -->|是| APP[按状态码、缓存、CORS、业务内容继续分析]
{% endmermaid %}

{% note info flat %}
不同工具能看到不同证据：
{% endnote %}

| 工具/位置 | 擅长回答 | 不足 |
| --- | --- | --- |
| 浏览器 DevTools | 浏览器最终发了什么、耗时、缓存、CORS、协议 | 不一定展示完整底层包和服务端内部路径 |
| curl verbose | 可脚本化复刻 DNS/TCP/TLS/HTTP 的客户端时间线 | 默认不执行浏览器同源策略、扩展、Cookie 隔离 |
| tcpdump | 在接口处捕获原始包的方向、端口、握手和重传 | 需要权限、正确接口和过滤器；加密内容不可直接阅读 |
| Wireshark | 解析包字段、stream、TLS/HTTP 专家信息 | 分析结果依赖完整捕获、时间戳和卸载影响 |
| 服务端/代理日志 | 上游选择、应用异常、超时和网关路径 | 没有客户端原始请求就可能缺少入口证据 |

### HTTP 状态与网络错误

{% note info flat %}
如果 Network 面板有 404、502 或 504，通常说明某个 HTTP 服务已经返回了响应；如果显示 net::ERR_NAME_NOT_RESOLVED、连接拒绝、TLS 证书错误，则可能没有 HTTP 状态码。一个排障报告必须把两类证据分开。
{% endnote %}

## DevTools 与 curl

### DevTools 请求瀑布

{% note info flat %}
Chrome Network 面板的 Timing/Waterfall 可以帮助划分等待：排队、代理、DNS、初始连接、TLS、发送请求、等待响应首字节、内容下载。名称和浏览器版本可能变化，但分析原则稳定：先定位最长阶段，再用 curl、抓包和服务端日志验证。
{% endnote %}

{% mermaid %}
flowchart LR
  QUEUE[排队/浏览器调度] --> DNS[DNS]
  DNS --> CONNECT[TCP 或 QUIC 建连]
  CONNECT --> TLS[TLS 握手]
  TLS --> SEND[发送请求]
  SEND --> WAIT[等待响应首字节]
  WAIT --> DOWNLOAD[下载内容]
{% endmermaid %}

{% note info flat %}
Headers、Payload、Response 和 Initiator 各有用途：
{% endnote %}

| 面板区域 | 先看什么 | 常见结论 |
| --- | --- | --- |
| Headers | URL、方法、状态、请求/响应字段、重定向 | 请求是否带了预期 Host、Cookie、Origin、缓存字段 |
| Payload | 请求体的编码和字段 | Content-Type 与实际内容是否匹配 |
| Response/Preview | 服务端实际返回内容 | 错误来自网关、应用还是浏览器解析 |
| Timing | 阶段耗时和等待 | DNS、连接、TLS、TTFB、下载哪个阶段异常 |
| Initiator | 谁触发请求 | 页面脚本、资源依赖、重试或重定向来源 |
| HAR | 可导出的结构化时间线 | 复盘前必须删除凭据、Cookie、查询参数和内部地址 |

### HAR 验证

{% note info flat %}
HAR 是浏览器导出的 JSON 交换格式，适合保存请求/响应、Timing、缓存、重定向和 Initiator 的结构化证据；它不是 pcap，也不包含服务端完整日志。建议按下面步骤导出最小证据：
{% endnote %}

1. 在 Network 面板勾选 Preserve log，清除无关请求并复现一次问题；
2. 选中目标请求，确认 Headers、Payload、Response、Timing 和 Security 面板已经记录；
3. 使用当前 Chrome 版本对应的 `Export HAR (sanitized)` 或 `Save all listed as HAR (sanitized)` 导出到临时目录；如果界面仍显示旧名称，选择等价的 HAR 导出项，不要导出未脱敏的 content；
4. 在副本中删除 Cookie、Authorization、Set-Cookie、查询参数、请求体中的个人数据、内部 Host/IP 和 Response content，再分享脱敏副本；
5. 用 pcap 的四元组/时间戳和服务端请求 ID 对照 HAR，说明浏览器看到的阶段是否能在网络包/服务日志中找到。

{% note info flat %}
验证 HAR 时至少检查 `log.entries[].request`、`response`、`timings`、`serverIPAddress` 和 `startedDateTime` 等标准/常见字段是否符合本次复现。`requestId` 是 Chrome DevTools 可能附加的私有可选关联字段，不是跨浏览器 HAR 的必备字段；只有导出结果确实包含它时，才把它与 DevTools 事件关联。缺少某字段只能说明导出/浏览器版本边界，不能推断服务端没有该事件。实验结束后删除原始 HAR 和响应体，只保留脱敏副本。
{% endnote %}

### curl 的最小证据集

~~~bash
# 只看响应头，不保留响应体
curl -sS -D - -o /dev/null --connect-timeout 5 https://example.com/

# 观察 TLS、重定向和请求响应方向；敏感字段不要直接复制到公开日志
BODY_FILE="$(mktemp -t http-body.XXXXXX)"
curl -sS -v -L --max-time 15 https://example.com/ -o "$BODY_FILE"
rm -f "$BODY_FILE"

# 复刻浏览器可能使用的 Origin/Accept 形状；值只使用测试域名
curl -sS -v -H 'Origin: https://app.example.test' -H 'Accept: application/json' https://api.example.test/status

# 用指定 ETag 观察条件请求；ETag 必须来自自己的测试夹具
curl -sS -D - -H 'If-None-Match: "fixture-v1"' http://127.0.0.1:18081/cache
~~~

{% note info flat %}
`-v` 会输出连接和字段证据，`-D -` 输出响应头，`-L` 会跟随重定向并改变请求链，`-o` 把响应体导出到指定文件。命令成功只说明该客户端在当前环境完成了请求，不等于浏览器、其他网络或所有用户都成功。
{% endnote %}

## 抓包与过滤

### 两类过滤器

{% note info flat %}
tcpdump 在捕获时用 BPF 过滤器减少写入的包；Wireshark display filter 在已经捕获的数据上筛选和解析。错误地把一种语法放到另一种工具中，会造成“抓不到包”或“过滤器无效”。
{% endnote %}

| 目的 | tcpdump 捕获过滤器 | Wireshark 显示过滤器 |
| --- | --- | --- |
| 只抓某主机 HTTPS | `host 203.0.113.10 and tcp port 443` | `ip.addr == 203.0.113.10 && tcp.port == 443` |
| 只抓 DNS | `port 53` | `dns` |
| 只看 TLS 握手 | 捕获阶段可用 `tcp port 443` 粗筛 | `tls.handshake` |
| 只看某 TCP 流 | `tcp port 443` 后用编号关联 | `tcp.stream eq 0` |
| 旧笔记中的源地址写法 | `src host 203.0.113.10` | `ip.src == 203.0.113.10` |

{% note info flat %}
`ip.scr` 不是 Wireshark 的源地址字段，`ip.src` 才是；但过滤器是否有包还取决于 IPv6、隧道、NAT 和实际抓包点。先用宽过滤器确认流量存在，再逐步收窄。
{% endnote %}

### 安全的最小抓包

~~~bash
# 先确认接口，示例中的 en0 需要替换为你明确授权的接口
tcpdump -D

# 只抓少量、限定主机和端口的包；不把整个接口长时间写盘
sudo tcpdump -ni en0 -c 40 -s 128 'host 203.0.113.10 and tcp port 443'

# 若必须保存到临时 pcap，使用精确临时目录并在分析后删除
CAPTURE_DIR="$(mktemp -d -t net-capture.XXXXXX)"
trap 'rm -rf "$CAPTURE_DIR"' EXIT
sudo tcpdump -ni en0 -c 80 -w "$CAPTURE_DIR/trace.pcap" 'host 203.0.113.10 and port 443'
wireshark "$CAPTURE_DIR/trace.pcap"
~~~

{% note info flat %}
抓包可能包含 Cookie、Authorization、查询参数、内网地址和用户数据；`-s 128` 只能减少每包捕获长度，不能保证没有敏感信息。共享前要在隔离副本上脱敏或只分享字段截图；实验结束后精确删除文件并确认没有把路径加入脚本或日志。
{% endnote %}

## 安全场景

{% note info flat %}
下面六个场景都是“先预检查、再运行、最后清理”的教学夹具。本文只提供可复现步骤和预期证据，不把它们写成已经在当前机器执行过的输出。
{% endnote %}

### DNS 失败

{% note info flat %}
`.invalid` 是专门用于无效示例的保留顶级域。命令不连接真实业务站点，也不修改本机 DNS 配置：
{% endnote %}

~~~bash
curl -v --connect-timeout 3 --max-time 5 http://does-not-exist.invalid/
~~~

{% note info flat %}
预期可能看到名称解析失败或解析超时，具体错误取决于本机解析器和网络策略。证据层是 DNS；通常不会有 TCP SYN，也不会有 HTTP 状态码。如果环境把 `.invalid` 拦截到测试解析器，必须以 `dig` 和抓包验证，而不是把某个错误字符串当成规范输出。
{% endnote %}

### 端口未监听

{% note info flat %}
先检查端口是否已被其他进程占用，不要直接终止未知 PID：
{% endnote %}

~~~bash
lsof -nP -iTCP:18080 -sTCP:LISTEN
curl -v --connect-timeout 2 http://127.0.0.1:18080/
~~~

{% note info flat %}
只有在 `lsof` 没有输出且你确认没有并发实验时，才把它当作“未监听端口”夹具。预期是 loopback TCP 连接快速被拒绝，客户端可能显示 connection refused；这不是 DNS 失败，也不是 HTTP 503，因为请求没有到达 HTTP 服务。
{% endnote %}

{% note info flat %}
如果端口已有监听，请换一个明确的临时端口，而不是 kill 该 PID。实验结束只需要停止自己启动的进程，不能按端口模糊清理其他服务。
{% endnote %}

### 自签名 HTTPS

{% note info flat %}
这个场景验证 TLS 证书校验，不把证书安装进系统信任库。使用临时目录、精确 PID 和退出清理：
{% endnote %}

~~~bash
LAB_DIR="$(mktemp -d -t net-tls.XXXXXX)"
SERVER_PID=
cleanup_tls() {
  if [ -n "${SERVER_PID:-}" ]; then
    kill "$SERVER_PID" 2>/dev/null || true
  fi
  rm -f "$LAB_DIR/key.pem" "$LAB_DIR/cert.pem" "$LAB_DIR/server.log"
  rmdir "$LAB_DIR" 2>/dev/null || true
}
trap cleanup_tls EXIT
if lsof -nP -iTCP:18443 -sTCP:LISTEN >/dev/null 2>&1; then
  echo "port 18443 is already in use; choose another isolated port"
  exit 1
fi

openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout "$LAB_DIR/key.pem" -out "$LAB_DIR/cert.pem" -days 1 \
  -subj '/CN=localhost' \
  -addext 'subjectAltName=DNS:localhost,IP:127.0.0.1'

openssl s_server -accept 18443 -cert "$LAB_DIR/cert.pem" \
  -key "$LAB_DIR/key.pem" -www >"$LAB_DIR/server.log" 2>&1 &
SERVER_PID=$!
ready=false
for attempt in 1 2 3 4 5; do
  if curl -k -sS -o /dev/null --connect-timeout 1 https://localhost:18443/; then
    ready=true
    break
  fi
  sleep 0.2
done
if [ "$ready" != true ]; then
  echo "TLS fixture did not become ready; inspect $LAB_DIR/server.log" >&2
  exit 1
fi

# 不提供信任例外：预期证书不受本机信任库信任
curl -v --connect-timeout 3 https://localhost:18443/

# 仅把本次临时证书作为单次请求的 CA：预期可以完成校验
curl -v --cacert "$LAB_DIR/cert.pem" https://localhost:18443/
~~~

{% note info flat %}
预期证据是 TCP 建连成功、TLS 握手到达证书校验阶段；第一次 curl 因信任链失败，第二次使用显式 `--cacert` 成功。SAN 同时覆盖 localhost 和 127.0.0.1，避免把 Common Name 当作现代主机名校验的唯一依据。若本机 `openssl` 不支持 `-addext`，应改用等价的临时 SAN 配置，但不降低校验或修改全局信任库。
{% endnote %}

### HTTP 错误夹具

{% note info flat %}
下面的 Python 夹具只绑定 loopback，故意返回固定响应，帮助区分“收到 HTTP 错误”与“网络连接失败”。它模拟状态码，不代表真实反向代理已经观察到上游故障：
{% endnote %}

~~~bash
FIXTURE_DIR="$(mktemp -d -t net-http.XXXXXX)"
SERVER_PID=
cleanup() {
  if [ -n "${SERVER_PID:-}" ]; then
    kill "$SERVER_PID" 2>/dev/null || true
  fi
  rm -f "$FIXTURE_DIR/server.py" "$FIXTURE_DIR/server.out"
  rmdir "$FIXTURE_DIR" 2>/dev/null || true
}
trap cleanup EXIT
if lsof -nP -iTCP:18081 -sTCP:LISTEN >/dev/null 2>&1; then
  echo "port 18081 is already in use; choose another isolated port"
  exit 1
fi
cat > "$FIXTURE_DIR/server.py" <<'PY'
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
import sys

class Handler(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"

    def do_OPTIONS(self):
        if self.path != "/cors":
            self.send_response(405)
            self.send_header("Allow", "GET, OPTIONS")
            self.send_header("Content-Length", "0")
            self.end_headers()
            return
        self.send_response(204)
        self.send_header("Access-Control-Allow-Origin", "https://app.example.test")
        self.send_header("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
        self.send_header("Access-Control-Allow-Headers", "authorization, content-type")
        self.send_header("Vary", "Origin")
        self.end_headers()

    def do_GET(self):
        if self.path in ("/keep-alive", "/framing"):
            body = (self.path.lstrip("/") + " fixture\n").encode("ascii")
            self.send_response(200)
            self.send_header("Content-Type", "text/plain; charset=utf-8")
            self.send_header("Content-Length", str(len(body)))
        elif self.path == "/chunked":
            self.send_response(200)
            self.send_header("Content-Type", "text/plain; charset=utf-8")
            self.send_header("Transfer-Encoding", "chunked")
            self.end_headers()
            for chunk in (b"hello", b" world\n"):
                self.wfile.write(f"{len(chunk):X}\r\n".encode("ascii"))
                self.wfile.write(chunk + b"\r\n")
            self.wfile.write(b"0\r\n\r\n")
            return
        elif self.path == "/cache":
            body = b"fixture-cache-v1\n"
            if self.headers.get("If-None-Match") == '"fixture-v1"':
                body = b""
                self.send_response(304)
            else:
                self.send_response(200)
            self.send_header("Content-Type", "text/plain; charset=utf-8")
            self.send_header("Cache-Control", "max-age=0, must-revalidate")
            self.send_header("ETag", '"fixture-v1"')
            if body:
                self.send_header("Content-Length", str(len(body)))
        elif self.path == "/fixed-502":
            body = b"synthetic gateway bad response\n"
            self.send_response(502)
            self.send_header("X-Fixture-Path", "gateway-to-upstream")
            self.send_header("X-Upstream-Status", "invalid")
            self.send_header("Content-Length", str(len(body)))
        elif self.path == "/fixed-504":
            body = b"synthetic upstream timeout\n"
            self.send_response(504)
            self.send_header("X-Fixture-Path", "gateway-timeout")
            self.send_header("Retry-After", "3")
            self.send_header("Content-Length", str(len(body)))
        elif self.path == "/cors":
            body = b""
            self.send_response(204)
            self.send_header("Access-Control-Allow-Origin", "https://app.example.test")
            self.send_header("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
            self.send_header("Access-Control-Allow-Headers", "authorization, content-type")
            self.send_header("Vary", "Origin")
        else:
            body = b"not found\n"
            self.send_response(404)
            self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, fmt, *args):
        sys.stderr.write("fixture: " + (fmt % args) + "\n")

server = ThreadingHTTPServer(("127.0.0.1", 18081), Handler)
server.serve_forever()
PY
python3 "$FIXTURE_DIR/server.py" >"$FIXTURE_DIR/server.out" 2>&1 &
SERVER_PID=$!
ready=false
for attempt in 1 2 3 4 5; do
  if curl -sS -o /dev/null http://127.0.0.1:18081/cache; then
    ready=true
    break
  fi
  sleep 0.2
done
if [ "$ready" != true ]; then
  echo "fixture did not become ready; inspect $FIXTURE_DIR/server.out" >&2
  exit 1
fi

curl -sS -D - -o /dev/null http://127.0.0.1:18081/cache
curl -sS -D - -H 'If-None-Match: "fixture-v1"' http://127.0.0.1:18081/cache
curl -sS -D - http://127.0.0.1:18081/keep-alive http://127.0.0.1:18081/framing
curl -sS -D - http://127.0.0.1:18081/chunked
curl -sS -D - http://127.0.0.1:18081/fixed-502
curl -sS -D - http://127.0.0.1:18081/fixed-504
~~~

{% note info flat %}
预期能看到固定 ETag/Cache-Control、条件请求的实现结果以及合成的 502/504。真实 502/504 排查仍需查看网关的上游连接、DNS、TLS、响应格式和超时日志；夹具只验证客户端如何读取状态和响应头。
{% endnote %}

### HTTP/2 夹具

{% note info flat %}
HTTP/2 的流控、RST_STREAM、GOAWAY 和动态表大小需要服务端主动控制；下面的 loopback Node.js `http2` 夹具它不会把公共站点的偶然行为当作实验结果，也不会把测试证书安装到系统信任库。
{% endnote %}

~~~bash
H2_DIR="$(mktemp -d -t net-h2.XXXXXX)"
H2_PID=
cleanup_h2() {
  if [ -n "${H2_PID:-}" ]; then
    kill "$H2_PID" 2>/dev/null || true
  fi
  rm -f "$H2_DIR/key.pem" "$H2_DIR/cert.pem" "$H2_DIR/server.js" "$H2_DIR/server.log"
  rmdir "$H2_DIR" 2>/dev/null || true
}
trap cleanup_h2 EXIT
if lsof -nP -iTCP:18444 -sTCP:LISTEN >/dev/null 2>&1; then
  echo "port 18444 is already in use; choose another isolated port"
  exit 1
fi

openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout "$H2_DIR/key.pem" -out "$H2_DIR/cert.pem" -days 1 \
  -subj '/CN=localhost' \
  -addext 'subjectAltName=DNS:localhost,IP:127.0.0.1'

cat > "$H2_DIR/server.js" <<'NODE'
const fs = require("node:fs");
const http2 = require("node:http2");

const port = Number(process.env.H2_PORT || 18444);
const headerTableSize = Number(process.env.H2_HEADER_TABLE_SIZE || 4096);
const server = http2.createSecureServer({
  key: fs.readFileSync(process.env.H2_KEY),
  cert: fs.readFileSync(process.env.H2_CERT),
  allowHTTP1: false,
  settings: { enablePush: false, headerTableSize }
});

server.on("stream", (stream, headers) => {
  const path = headers[":path"] || "/";
  if (path === "/small") {
    stream.respond({ ":status": 200, "content-type": "text/plain", "content-length": "6" });
    stream.end("small\n");
    return;
  }
  if (path === "/slow") {
    const total = 1024 * 1024;
    let sent = 0;
    stream.respond({ ":status": 200, "content-type": "application/octet-stream", "content-length": String(total) });
    const write = () => {
      if (stream.destroyed) return;
      if (sent >= total) { stream.end(); return; }
      const chunk = Buffer.alloc(Math.min(16384, total - sent), 0x61);
      sent += chunk.length;
      if (stream.write(chunk)) setTimeout(write, 10);
      else stream.once("drain", () => setTimeout(write, 10));
    };
    write();
    return;
  }
  if (path === "/reset") {
    stream.respond({ ":status": 200 });
    stream.close(http2.constants.NGHTTP2_CANCEL);
    return;
  }
  if (path === "/goaway") {
    stream.respond({ ":status": 200 });
    stream.end("goaway\n", () => stream.session.goaway(http2.constants.NGHTTP2_NO_ERROR, stream.id));
    return;
  }
  if (path === "/headers") {
    stream.respond({ ":status": 200, "x-demo": "repeat", "cache-control": "no-store" });
    stream.end("headers fixture\n");
    return;
  }
  stream.respond({ ":status": 404, "content-length": "10" });
  stream.end("not found\n");
});

server.listen(port, "127.0.0.1", () => console.error(`h2 fixture listening on ${port}; headerTableSize=${headerTableSize}`));
NODE

H2_KEY="$H2_DIR/key.pem" H2_CERT="$H2_DIR/cert.pem" node "$H2_DIR/server.js" >"$H2_DIR/server.log" 2>&1 &
H2_PID=$!
H2_URL="https://localhost:18444"
ready=false
for attempt in 1 2 3 4 5; do
  if curl --http2 --cacert "$H2_DIR/cert.pem" -sS -o /dev/null "$H2_URL/small"; then
    ready=true
    break
  fi
  sleep 0.2
done
if [ "$ready" != true ]; then
  echo "h2 fixture did not become ready; inspect $H2_DIR/server.log" >&2
  exit 1
fi

curl --http2 --cacert "$H2_DIR/cert.pem" -sS "$H2_URL/small"
curl --http2 --cacert "$H2_DIR/cert.pem" --parallel -sS "$H2_URL/slow" "$H2_URL/small" -o /dev/null
curl --http2 --cacert "$H2_DIR/cert.pem" -v -sS "$H2_URL/reset" -o /dev/null
curl --http2 --cacert "$H2_DIR/cert.pem" -v -sS "$H2_URL/goaway" -o /dev/null
curl --http2 --cacert "$H2_DIR/cert.pem" -H 'x-demo: repeat' -sS "$H2_URL/headers" -o /dev/null
~~~

{% note info flat %}
`/slow` 用响应背压帮助观察 `WINDOW_UPDATE`，`/reset` 产生单流重置，`/goaway` 产生连接级关闭信号，`H2_HEADER_TABLE_SIZE=0` 与默认 `4096` 的两次启动可用于对照 SETTINGS 和 HPACK 动态表边界。停止第一进程后，可在同一 shell 用下面的后台重启形态完成第二次对照，并更新 trap 使用的 PID：
{% endnote %}

~~~bash
kill "$H2_PID" 2>/dev/null || true
wait "$H2_PID" 2>/dev/null || true
H2_HEADER_TABLE_SIZE=0 H2_KEY="$H2_DIR/key.pem" H2_CERT="$H2_DIR/cert.pem" \
  node "$H2_DIR/server.js" >"$H2_DIR/server.log" 2>&1 &
H2_PID=$!
ready=false
for attempt in 1 2 3 4 5; do
  if curl --http2 --cacert "$H2_DIR/cert.pem" -sS -o /dev/null "$H2_URL/small"; then
    ready=true
    break
  fi
  sleep 0.2
done
[ "$ready" = true ] || { echo "h2 restart failed; inspect $H2_DIR/server.log" >&2; exit 1; }
~~~

{% note info flat %}
当前环境没有 `nghttp` 时，curl 仍可验证协商、并发请求和错误路径，逐 frame 证据则记录为 NOT VERIFIED。实验结束由 trap 精确停止自己的进程并删除临时证书。
{% endnote %}

### TLS 终止

{% note info flat %}
为了验证“客户端到代理”和“代理到上游”是两条链路，下面的夹具在 loopback 上同时启动一个明文上游和一个 TLS 终止入口。它只返回合成的 502，不代表真实网关故障；日志中的两条腿必须分别记录。
{% endnote %}

~~~bash
PROXY_DIR="$(mktemp -d -t net-proxy.XXXXXX)"
PROXY_PID=
cleanup_proxy() {
  if [ -n "${PROXY_PID:-}" ]; then
    kill "$PROXY_PID" 2>/dev/null || true
  fi
  rm -f "$PROXY_DIR/key.pem" "$PROXY_DIR/cert.pem" "$PROXY_DIR/proxy.py" "$PROXY_DIR/proxy.log"
  rmdir "$PROXY_DIR" 2>/dev/null || true
}
trap cleanup_proxy EXIT
if lsof -nP -iTCP:18082 -sTCP:LISTEN >/dev/null 2>&1 || lsof -nP -iTCP:18445 -sTCP:LISTEN >/dev/null 2>&1; then
  echo "port 18082 or 18445 is already in use; choose another isolated port"
  exit 1
fi

openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout "$PROXY_DIR/key.pem" -out "$PROXY_DIR/cert.pem" -days 1 \
  -subj '/CN=localhost' \
  -addext 'subjectAltName=DNS:localhost,IP:127.0.0.1'

cat > "$PROXY_DIR/proxy.py" <<'PY'
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from http.client import HTTPConnection
import ssl
import sys
import threading
import os

class Upstream(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"
    def do_GET(self):
        body = b"synthetic upstream failure\n"
        self.send_response(502)
        self.send_header("X-Upstream-Status", "invalid")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)
    def log_message(self, fmt, *args):
        sys.stderr.write("upstream: " + (fmt % args) + "\n")

class Proxy(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"
    def do_GET(self):
        upstream = HTTPConnection("127.0.0.1", 18082, timeout=3)
        upstream.request("GET", self.path, headers={"X-From-Proxy": "1"})
        response = upstream.getresponse()
        body = response.read()
        self.send_response(response.status, response.reason)
        for name, value in response.getheaders():
            if name.lower() not in {"connection", "transfer-encoding", "content-length", "server", "date"}:
                self.send_header(name, value)
        self.send_header("X-Proxy-Leg", "tls-to-plain")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)
        upstream.close()
    def log_message(self, fmt, *args):
        sys.stderr.write("proxy: " + (fmt % args) + "\n")

upstream_server = ThreadingHTTPServer(("127.0.0.1", 18082), Upstream)
proxy_server = ThreadingHTTPServer(("127.0.0.1", 18445), Proxy)
context = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
context.load_cert_chain(os.environ["PROXY_CERT"], os.environ["PROXY_KEY"])
proxy_server.socket = context.wrap_socket(proxy_server.socket, server_side=True)
threading.Thread(target=upstream_server.serve_forever, daemon=True).start()
proxy_server.serve_forever()
PY
PROXY_CERT="$PROXY_DIR/cert.pem" PROXY_KEY="$PROXY_DIR/key.pem" python3 "$PROXY_DIR/proxy.py" >"$PROXY_DIR/proxy.log" 2>&1 &
PROXY_PID=$!
for attempt in 1 2 3 4 5; do
  status="$(curl --cacert "$PROXY_DIR/cert.pem" -sS -o /dev/null -w '%{http_code}' https://localhost:18445/fixed-502 || true)"
  if [ "$status" = 502 ]; then break; fi
  sleep 0.2
done
if [ "$status" != 502 ]; then
  echo "TLS proxy fixture did not become ready; inspect $PROXY_DIR/proxy.log" >&2
  exit 1
fi
curl --cacert "$PROXY_DIR/cert.pem" -sS -D - https://localhost:18445/fixed-502 -o /dev/null
curl -sS -D - http://127.0.0.1:18082/fixed-502 -o /dev/null
~~~

{% note info flat %}
第一条请求同时经过 TLS 客户端→代理和明文代理→上游，响应中的 `X-Proxy-Leg: tls-to-plain` 与代理日志是拓扑证据；第二条只直接访问上游，用来对照。若启动失败或两条日志无法关联，应记录 NOT VERIFIED，不能用两个独立的公共请求代替同一条代理链路。
{% endnote %}

## 证据链、脱敏与清理

### 成功和失败的对照表

| 现象 | 证据链定位 | 最小下一步 |
| --- | --- | --- |
| `.invalid` 名称解析失败 | DNS 前置阶段 | `dig`、解析器日志、DNS 抓包 |
| loopback connection refused | TCP 入口没有监听 | `lsof`、`ss -lnt`、本机 TCP 错误 |
| 自签名证书失败 | TCP 成功，TLS 校验失败 | `openssl s_client`、SAN、信任库和 SNI |
| 502/504 有响应头 | HTTP 已到达网关/夹具 | 网关到上游的 DNS/TCP/TLS/超时日志 |
| 瀑布等待很久后成功 | DNS、连接、TLS 或 TTFB 阶段慢 | 对照 curl Timing、抓包时间戳和服务日志 |
| curl 成功而 Fetch 失败 | 浏览器策略或请求上下文差异 | Origin、预检、Cookie、缓存和协议版本 |

### 抓包安全和清理

{% note info flat %}
抓包前：
{% endnote %}

- 只在自己拥有或明确获准的接口、主机和时间窗口内采集；
- 用 `-c` 限制包数、用主机/端口过滤，必要时限制 snaplen；
- 记录测试目标、开始时间、接口和过滤器，不记录凭据；
- 对 Cookie、Authorization、查询参数、用户数据和内网地址建立脱敏清单。

{% note info flat %}
抓包后：
{% endnote %}

- 只保留回答问题所需的最小字段或截图；
- 对 pcap、HAR、临时证书、私钥、服务日志使用精确文件路径清理；
- 只停止自己保存的 PID，先确认进程命令行和启动时间；
- 不修改系统信任库、全局 DNS、路由或防火墙作为“实验清理”；
- 在报告中说明哪些层已验证、哪些层只是推测。

## 排障复习

{% note info flat %}
先写出“现象 → 证据层 → 下一条验证”的链条，再查看答案。排障卡片的目标不是记住某个错误字符串，而是避免跨层归因。
{% endnote %}

{% flashcard basic id:CN-DIAG-001 deck:"计算机网络" priority:1 tags:"DevTools,瀑布" %}
--- question
DevTools Network 的 Timing/Waterfall 应如何定位慢点？
--- answer
先按 DNS、连接、TLS、发送、等待首字节、下载等阶段找最长耗时，再用 curl、抓包和服务端日志验证。
--- explanation
瀑布是浏览器视角，不自动证明服务端或网络根因。要结合 Headers、Initiator、协议版本、缓存和上游日志，明确证据边界。
{% endflashcard %}

{% flashcard basic id:CN-DIAG-002 deck:"计算机网络" priority:1 tags:"curl,复现" %}
--- question
curl -v、-D -、-L 分别提供什么证据？
--- answer
-v 输出客户端连接/TLS/请求响应方向，-D - 输出响应头，-L 跟随重定向并产生后续请求链。
--- explanation
curl 默认不是浏览器，通常不执行同源策略。使用 -L 后必须记录每一跳方法、状态、Location 和凭据处理，避免只看最终响应。
{% endflashcard %}

{% flashcard basic id:CN-DIAG-003 deck:"计算机网络" priority:1 tags:"tcpdump,Wireshark,过滤器" %}
--- question
tcpdump 捕获过滤器和 Wireshark 显示过滤器有什么区别？
--- answer
tcpdump 在采集时用 BPF 减少写入的数据，Wireshark 在已捕获数据上按协议字段筛选；两者语法和证据阶段不同。
--- explanation
例如 tcpdump 使用 host/tcp port，Wireshark 使用 ip.addr/tcp.port/tcp.stream。先用宽过滤器确认包存在，再逐步收窄。
{% endflashcard %}

{% flashcard basic id:CN-DIAG-004 deck:"计算机网络" priority:1 tags:"DNS,TCP,TLS,HTTP" %}
--- question
如何区分 DNS 失败、TCP 拒绝、TLS 证书失败和 HTTP 502？
--- answer
DNS 失败没有目标 IP，TCP 拒绝没有建立连接，TLS 失败通常 TCP 已建立但证书/握手未通过，502 则说明某个 HTTP 网关已经返回响应。
--- explanation
错误字符串可能随客户端变化，必须结合 DNS 查询、SYN/RST、TLS 握手和响应头判断，不要把所有现象称为“网络不通”。
{% endflashcard %}

{% flashcard basic id:CN-DIAG-005 deck:"计算机网络" priority:1 tags:"抓包,安全,证据链" %}
--- question
抓包和 HAR 分享前后最重要的安全边界是什么？
--- answer
只采集获准范围，限制接口/主机/包数，脱敏 Cookie、Authorization、查询参数和内部地址，完成后精确清理文件和自己启动的进程。
--- explanation
抓包成功不等于可以公开。报告应保留最小证据、记录过滤器和验证层级，不修改全局信任库、DNS 或权限来制造通过结果。
{% endflashcard %}

## 常见问题

{% flashcard_ref id="CN-DIAG-003" %}
{% flashcard_ref id="CN-DIAG-004" %}

{% flashcard basic id:CN-DIAG-FAQ-001 deck:"计算机网络" priority:1 tags:"curl,浏览器,CORS" %}
--- question
为什么 curl 成功而浏览器失败？
--- answer
两者的请求上下文不同。浏览器还会执行同源策略、CORS 预检、Cookie SameSite、缓存、扩展和证书策略。
--- explanation
应从 DevTools 的 Origin、方法、请求头和 Timing 复刻，而不是只复制 URL。
{% endflashcard %}

{% flashcard basic id:CN-DIAG-FAQ-002 deck:"计算机网络" priority:1 tags:"HTTP,502,网关" %}
--- question
502 一定是后端服务挂了吗？
--- answer
不一定。502 是某个网关观察到上游响应无效的 HTTP 结果，问题可能在网关到上游的 DNS、TCP、TLS、分帧或代理配置。
--- explanation
必须查看网关和上游的对应时间线；客户端收到 502 不能单独定位上游哪一步失败。
{% endflashcard %}

{% flashcard basic id:CN-DIAG-FAQ-003 deck:"计算机网络" priority:1 tags:"tcpdump,抓包,证据" %}
--- question
tcpdump 没有抓到包，说明客户端没有发送吗？
--- answer
不能。接口、命名空间、权限、捕获点、过滤器、硬件卸载和流量走向都可能导致观察不到。
--- explanation
先用 `tcpdump -D`、宽过滤器和接口状态确认观察位置，再得出发送与否的结论。
{% endflashcard %}

{% flashcard basic id:CN-DIAG-FAQ-004 deck:"计算机网络" priority:2 tags:"抓包,权限,信任库" %}
--- question
为什么不建议用 777 或改系统信任库做实验？
--- answer
宽权限会扩大实验副作用，系统信任库会让后续真实校验失去基线。
--- explanation
临时目录、单次 `--cacert`、精确 PID 和最小权限足以完成验证，不需要修改全局安全边界。
{% endflashcard %}

{% flashcard basic id:CN-DIAG-FAQ-005 deck:"计算机网络" priority:1 tags:"HTTPS,抓包,TLS" %}
--- question
抓包能直接看到 HTTPS 的 URL 和 JSON 吗？
--- answer
通常不能直接看到 TLS 保护的应用内容；可以看到 IP、端口、握手元数据和时序。
--- explanation
可见范围取决于抓包点、TLS 终止位置和合法的解密材料；不要为了看内容导出生产私钥。
{% endflashcard %}
