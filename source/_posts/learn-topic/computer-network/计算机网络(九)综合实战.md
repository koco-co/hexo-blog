## 综合题准备：现象、假设、证据和结论

### 五段式回答

遇到“网页为什么打不开”“HTTP 请求经历了什么”“TCP 和 QUIC 怎么选”时，不要从背诵协议名开始：

1. **现象**：明确是解析失败、连接拒绝、握手超时、证书错误、HTTP 状态还是业务内容错误；
2. **假设**：只提出当前证据支持的最小假设，例如“DNS 没有返回地址”；
3. **证据**：选择能证伪假设的工具输入、时间线、字段或日志；
4. **结论**：说明已验证到哪一层，以及故障边界在哪里；
5. **下一步**：给出最小、只读、可恢复的后续检查。

{% mermaid %}
flowchart TD
  OBS[现象] --> HYP[最小假设]
  HYP --> TEST[选择可证伪证据]
  TEST --> RESULT{证据支持吗}
  RESULT -->|否| HYP2[更新假设，不扩大操作]
  HYP2 --> TEST
  RESULT -->|是| CONC[带边界的结论]
  CONC --> NEXT[下一层或修复前的最小验证]
{% endmermaid %}

### 进阶能力的共同边界

DSCP/QoS、组播、动态路由、WebDAV 和状态注册表都可能出现在真实系统中，但它们不应被用来替代主线证据。先回答“当前请求是否有地址、连接、加密和 HTTP 响应”，再决定是否进入扩展协议。

## 经典链路：DNS → TCP → TLS → HTTP

### 双端时序

{% mermaid %}
sequenceDiagram
  participant B as 浏览器/客户端
  participant R as DNS Resolver
  participant S as TCP/TLS/HTTP 服务
  B->>R: 查询 example.test 的地址
  R-->>B: A/AAAA 地址
  B->>S: TCP SYN
  S-->>B: SYN-ACK
  B->>S: ACK
  B->>S: TLS 1.3 ClientHello + SNI/ALPN
  S-->>B: ServerHello + Certificate + Finished
  B->>S: HTTP request
  S-->>B: HTTP status + fields + content
{% endmermaid %}

### 每一步能观察什么

| 阶段 | 客户端证据 | 服务端/抓包证据 | 失败时不要越界 |
| --- | --- | --- | --- |
| DNS | resolver 地址、A/AAAA、耗时 | DNS query/response、NXDOMAIN/SERVFAIL | 没有地址就不要分析目标 TCP |
| TCP | connect 成功/拒绝/超时 | SYN、SYN-ACK、RST、重传、四元组 | TCP 成功不代表 TLS/HTTP 成功 |
| TLS | 版本、证书、ALPN、校验错误 | ClientHello、ServerHello、证书链、alert | 证书成功不代表业务认证通过 |
| HTTP | 方法、状态、缓存/CORS、内容 | 请求字段、响应字段、网关/上游日志 | 404/502 是 HTTP 结果，不是 DNS 错误 |

### 经典链路的可复现入口

复现时先使用第七篇中的公共示例或本地固定夹具，记录命令版本、目标、时间和脱敏后的输出：

~~~bash
dig +noall +answer example.com A
curl -sS -v --http1.1 https://example.com/ -o /tmp/classic-body.txt
openssl s_client -connect example.com:443 -servername example.com -alpn h2,http/1.1 </dev/null
~~~

命令输出未在本文预先伪造。真实结果可能受解析器、目标站点、网络策略和客户端构建选项影响；报告中应粘贴最小必要字段，并隐藏 Cookie、Authorization 和内部地址。

## 现代链路：DNS → QUIC → HTTP/3

### 传输和应用的关系

{% mermaid %}
sequenceDiagram
  participant B as 浏览器/客户端
  participant R as DNS Resolver
  participant Q as QUIC/HTTP3 服务
  B->>R: 查询 example.test 的地址
  R-->>B: A/AAAA 地址与可能的协议提示
  B->>Q: UDP Initial + QUIC ClientHello
  Q-->>B: QUIC handshake + TLS 1.3 参数
  B->>Q: HTTP/3 HEADERS/DATA on request stream
  Q-->>B: HTTP/3 HEADERS/DATA
  Note over B,Q: 其他 stream 的丢包不必阻塞所有应用 stream
{% endmermaid %}

### 与经典链路对照

| 观察项 | 经典链路 | 现代链路 |
| --- | --- | --- |
| 传输入口 | TCP 443 | UDP 443 常见，但以服务端和路径配置为准 |
| 安全握手 | TLS 运行在 TCP 之上 | QUIC 集成 TLS 1.3 握手和密钥保护 |
| 并发 | HTTP/2 stream 共享 TCP 按序交付 | HTTP/3 stream 使用 QUIC 的独立传输语义 |
| 回退 | 可从 h2 回到 HTTP/1.1 | HTTP/3 失败可能回退到 TCP 上的 h2/h1 |
| 证据难度 | TLS/HTTP 字段较容易由工具解析 | QUIC 加密、UDP 策略、浏览器支持需额外确认 |

### 现代链路的验证边界

`curl --http3` 只有在本机 curl 编译支持 HTTP/3 且目标服务提供时才有意义；浏览器的协议选择还受到 Alt-Svc、缓存、代理、UDP 可达性和回退状态影响。看到最终请求使用 h2，不能证明服务端没有 h3；看到 UDP 包，也不能证明 HTTP/3 已经完成。

## 四类失败夹具与面试回答

### 夹具对照

四个场景来自第七篇，本文只复用其边界，不复制整段操作：

| 夹具 | 预期停在哪一层 | 面试式结论 |
| --- | --- | --- |
| `.invalid` DNS 失败 | DNS | 没有目标地址，因此没有目标 TCP/HTTP 证据 |
| loopback 未监听端口 | TCP | 地址可用但没有监听，通常快速拒绝；没有 HTTP 状态 |
| 自签名 HTTPS | TLS | TCP 建立后证书信任/主机名校验失败；`-k` 只是临时降低校验 |
| 固定 304/502/504 | HTTP | 已收到 HTTP 响应，继续看缓存字段、网关路径和上游证据 |

### 从现象到下一条证据

{% mermaid %}
flowchart TD
  P[页面失败] --> N{DNS 有地址?}
  N -->|否| N1[查 resolver、NXDOMAIN/SERVFAIL、DNS 抓包]
  N -->|是| T{TCP/QUIC 建立?}
  T -->|否| T1[查 SYN/RST/UDP、路由和策略]
  T -->|是| S{TLS 校验/协议成功?}
  S -->|否| S1[查 SAN、信任链、SNI、ALPN、alert]
  S -->|是| H{HTTP 状态/内容正常?}
  H -->|否| H1[查状态、缓存、CORS、代理和上游日志]
  H -->|是| OK[进入应用业务与性能分析]
{% endmermaid %}

回答失败题时，要先说“我目前已验证到哪一层”，再说“下一层还没有证据”。这是比“应该是防火墙”“重启服务就好”更可靠的面试和生产沟通方式。

## 进阶能力的边界

### DSCP 与 QoS 标记

DSCP 位于 IP 服务质量字段，表达流量分类/转发处理意图；它不是带宽保证，也不是加密认证。标记是否被保留、队列是否按标记配置、运营商是否重写，都要在具体路径上验证。抓包中看见 DSCP 值，只能证明包带了标记，不能证明获得了某种时延或带宽。

### IPv4 组播

IPv4 组播让一个发送者面向组地址发送，接收者通过组成员关系加入；它不同于广播，也不是自动跨所有路由器传播。交换机、IGMP、路由协议和边界策略决定组播是否有效。测试时应使用授权的隔离组地址和明确 TTL，避免产生不可控的跨网流量。

### OSPF 与 BGP 概览

OSPF 常用于自治系统内部的链路状态路由，BGP 用于自治系统之间以及更广泛的策略路由。它们影响的是路由控制平面，不是 TCP 三次握手的替代品。遇到“某个前缀走错路”时，先看路由表和下一跳，再根据网络权限进入邻居、策略、前缀通告和收敛证据。

### WebDAV、102 与状态注册表

WebDAV 扩展了 HTTP 的资源管理方法和属性语义，102 Processing 是其历史语境中的处理中状态；它们不能被当作普通 API 的通用状态/方法约定。使用新方法或状态时，应查规范和 IANA 注册表，并说明客户端、代理和服务端是否真正支持。

### 课程扩展和审计版本

继续扩展课程时，每项新能力都应记录稳定 ID、主来源、文章归属、当前/历史状态、视觉组件和验证方式。旧笔记可以帮助发现问题，但不能替代当前规范；“已经写进文章”也不能替代构建、浏览器和真实环境证据。

## 常见问题

### 面试中应该先讲 OSI 七层还是先讲请求链路？

先确认题目要解释的现象，再用链路定位证据，必要时用 OSI/TCP-IP 模型补充边界。死背七层名称不能替代“请求是否解析、连接、握手、返回 HTTP”的事实。

### QUIC 的 UDP 失败后会自动变成 TCP 吗？

通常由客户端、浏览器、服务器和部署提示决定是否回退到 HTTP/2 或 HTTP/1.1，不是 UDP 协议本身自动把数据转换成 TCP。验证时记录协议提示、UDP 可达性、QUIC 错误和最终协商结果。

### 看到 502/504 还能继续抓 TCP 吗？

可以，但问题已经至少到达某个 HTTP 网关。下一步应同时检查客户端到网关的连接证据和网关到上游的 DNS/TCP/TLS/超时日志；只在客户端重复抓包可能看不到真正故障段。

### 课程还要继续加入更多协议吗？

只有新主题能回答明确问题并有稳定来源、视觉模型和验证路径时才加入。否则先完成当前能力的闪卡复习和真实排障，比继续堆名词更有收益。
