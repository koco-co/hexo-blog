## 从一次局域网通信开始

假设主机 A 的配置是：

| 项目 | 主机 A |
| --- | --- |
| IPv4 地址 | 192.168.10.10/24 |
| MAC 地址 | 02:00:00:00:00:0a |
| 默认网关 | 192.168.10.1 |

主机 B 的配置是：

| 项目 | 主机 B |
| --- | --- |
| IPv4 地址 | 192.168.10.20/24 |
| MAC 地址 | 02:00:00:00:00:14 |

{% note info flat %}
A 执行 ping 或访问 B 的服务时，应用最先知道的是“我要访问 192.168.10.20”。但网卡发送以太网帧时，需要一个目的 MAC。这里出现了两个不同的问题：
{% endnote %}

1. **IP 层问题：**目标 192.168.10.20 是否与本机处于同一前缀？
2. **链路层问题：**如果目标在本地，192.168.10.20 对应哪个 MAC？

{% note info flat %}
因此，IP 地址不是“网卡最终看见的地址”，MAC 地址也不是“跨互联网永久标识”。IP 负责跨网络的逻辑寻址，MAC 负责当前链路上的一跳交付。
{% endnote %}

{% note primary flat %}
判断二层问题时，先问“这一跳的下一跳是谁”，再问“下一跳的 MAC 是什么”。本地目标的下一跳是目标主机；远端目标的下一跳通常是默认网关。
{% endnote %}

## 分层与封装

### 发送端逐层加头

{% note info flat %}
下图使用从上到下的方向，是因为层级和封装节点较多；移动端不需要横向压缩文字。
{% endnote %}

{% mermaid %}
flowchart TD
  A[应用数据] --> B[传输层段<br/>TCP 或 UDP]
  B --> C[网络层包<br/>源 IP 与目标 IP]
  C --> D[链路层帧<br/>源 MAC 与目标 MAC]
  D --> E[物理介质上的比特]
{% endmermaid %}

每一层只处理自己关心的字段：

| 层次 | 数据单元 | 典型字段 | 这一层回答的问题 |
| --- | --- | --- | --- |
| 应用 | 数据 | HTTP 方法、DNS 查询 | 要表达什么 |
| 传输 | 段/数据报 | 端口、序列号、确认号 | 交给哪个进程，是否需要可靠性 |
| 网络 | 包/数据报 | 源 IP、目标 IP、TTL | 下一跳往哪里走 |
| 链路 | 帧 | 源 MAC、目标 MAC、类型 | 当前链路交给哪块网卡 |
| 物理 | 比特 | 电/光/无线信号 | 如何在介质上传输 |

### 接收端逐层解封装

接收端的顺序相反：

1. 网卡根据目的 MAC 和链路规则接收帧；
2. 链路层校验帧并根据类型字段交给 IPv4、IPv6 或其他上层协议；
3. 网络层确认目标 IP 属于本机、广播或需要继续处理；
4. 传输层根据端口把数据交给监听的进程；
5. 应用层解析 HTTP、DNS 或其他应用协议。

{% note info flat %}
“解封装”不是把所有头字段删除后再交给应用，而是每层读取并消费自己的字段，同时把载荷交给上层。中间交换机通常只需要看到以太网帧的源/目的 MAC 和 VLAN 上下文，不会把 HTTP 内容当成转发依据。
{% endnote %}

{% mermaid %}
flowchart TD
    A[发送端<br/>判断本地或远端<br/>确定下一跳及其 MAC] --> B[交换机<br/>按链路上下文与目的 MAC 查询 FDB]
    B --> C[接收端<br/>确认本机 IP<br/>把端口交给监听进程]
{% endmermaid %}

{% note info flat %}
这三个角色是同一条通信链路中的连续步骤，不是三种可替换方案。排障时沿着“下一跳 → 二层转发 → 本机协议栈”逐段验证，才能确定故障落在哪个边界。
{% endnote %}

## 以太网帧与 MAC

### 帧字段

以太网帧的字段可以先用一个教学级抽象理解：

| 字段 | 作用 | 面试时的边界 |
| --- | --- | --- |
| 目的 MAC | 当前链路要交付给谁 | 不等于最终远端服务器的 IP |
| 源 MAC | 当前发送网卡的链路地址 | 每经过路由器转发，链路层源/目的 MAC 会重写 |
| 类型/长度 | 指示载荷解释方式 | 例如交给 IPv4、IPv6 或 ARP |
| Payload | 上层协议载荷 | 可能是 IP 包，也可能是 ARP 消息 |
| FCS | 帧校验序列 | 用于链路层检测传输错误，抓包位置和网卡卸载可能影响观察 |

{% note info flat %}
MAC 地址通常写成 6 个十六进制字节。目的地址全为 1，即 FF:FF:FF:FF:FF:FF，表示链路广播。广播不是“发给所有互联网主机”，而是在当前广播域内扩散；交换机也不会把二层广播自动路由到另一个三层接口。
{% endnote %}

### 单播、广播与组播

- **已知单播：**交换机可以根据 FDB 只从目标端口发送；
- **未知单播：**目标 MAC 不在 FDB 中时，交换机通常在同一广播域内泛洪，但不从入端口发回；
- **广播：**目的 MAC 为全 1，通常向同一广播域的多个端口泛洪；
- **组播：**是否精确转发取决于设备和组播控制能力，不能简单等同于广播。

{% note info flat %}
这里的“泛洪”是转发行为，不代表帧一定已经到达最终主机。接收端网卡仍会根据目的 MAC、混杂模式和上层协议决定是否交付。
{% endnote %}

## 交换机转发

### FDB 转发

交换机可以把 FDB 想成一张“最近从哪个端口看见过哪个源 MAC”的表：

| 事件 | FDB 动作 | 后续决策 |
| --- | --- | --- |
| 从端口 1 收到源 MAC A | 学习 A → 端口 1 | 更新已有位置或新增条目 |
| 目的 MAC B 在端口 2 | 查表得到端口 2 | 只向端口 2 转发 |
| 目的 MAC 与入端口相同 | 查表结果指向入端口 | 过滤，不重复发回 |
| 目的 MAC 不在表中 | 暂时没有确定端口 | 在同一广播域内泛洪 |
| 目的 MAC 是广播地址 | 不依赖具体 FDB 条目 | 在同一广播域内泛洪 |

完整的转发动作可以表示为：

{% mermaid %}
flowchart TD
  A[收到以太网帧] --> B[学习源 MAC 与入端口]
  B --> C{检查目的 MAC}
  C -->|广播或未知单播| D[同广播域泛洪<br/>不从入端口发回]
  C -->|已知且是其他端口| E[只向目标端口转发]
  C -->|已知但仍是入端口| F[过滤]
{% endmermaid %}

{% note info flat %}
FDB 是动态状态，不是永久事实。主机换端口、链路发生故障、设备重启或条目老化后，第一次通信可能经历未知单播泛洪；这并不自动表示交换机坏了。
{% endnote %}

### 环路和广播域边界

{% note info flat %}
如果多个交换机通过二层链路形成物理环路，广播和未知单播泛洪可能不断绕圈。生成树类机制用于避免二层环路带来的持续复制；路由器则通过三层边界阻止普通二层广播直接跨接口扩散。
{% endnote %}

{% note info flat %}
VLAN 可以把一台交换机划分为多个广播域，但本文只使用“广播域隔离”的概念，不把 VLAN 配置命令当作当前主线的前置操作。面试回答时要区分：
{% endnote %}

- 交换机端口之间的二层转发；
- VLAN 内的广播扩散；
- 路由器或三层交换接口之间的三层转发；
- 防火墙策略对三层或四层流量的额外限制。

### 冲突域与广播域

冲突域和广播域描述的是两个不同的扩散边界：

| 概念 | 关注的问题 | 典型边界 | 现代以太网中的注意点 |
| --- | --- | --- | --- |
| 冲突域 | 哪些设备共享同一发送介质，可能同时发送而发生碰撞 | 传统共享总线或 Hub 下的共享介质 | 全双工交换机端口通常各自隔离碰撞，冲突域概念更多用于解释旧式半双工网络和异常协商 |
| 广播域 | 二层广播帧能够传播到哪些接口 | VLAN/二层广播域，通常由三层接口隔开 | 同一交换机不代表只有一个广播域，VLAN 会切分广播域 |

{% mermaid %}
flowchart TD
  HUB[共享介质/Hub] --> HOST_A[主机 A]
  HUB --> HOST_B[主机 B]
  HUB --> HOST_C[主机 C]
  HUB -.共享冲突域.-> COLLISION[半双工可能碰撞]
  SW[交换机] --> VLAN_A[VLAN 10 广播域]
  SW --> VLAN_B[VLAN 20 广播域]
  VLAN_A --> ROUTER[三层接口边界]
  VLAN_B --> ROUTER
{% endmermaid %}

{% note info flat %}
因此“交换机能隔离冲突域、路由器能隔离广播域”是有前提的教学口诀：前者依赖交换端口和双工语境，后者描述普通二层广播不会自动穿过三层接口。排障时，碰撞/双工问题应看接口协商、错误计数和链路质量；广播泛洪问题则应看 VLAN、环路、未知单播和广播速率。
{% endnote %}

## ARP 与 IPv6 邻居发现

### ARP 交换

{% note info flat %}
当 A 不知道 B 的 MAC 时，A 会发送 ARP 请求。请求的以太网目的 MAC 是广播地址，ARP payload 中会写出“谁拥有 192.168.10.20，请告诉 192.168.10.10”。
{% endnote %}

{% mermaid %}
sequenceDiagram
  participant A as 主机 A
  participant LAN as 广播域
  participant B as 主机 B
  A->>LAN: Ethernet broadcast + ARP request
  LAN-->>B: 交付广播帧
  B->>A: ARP reply: 192.168.10.20 is at MAC-B
  A->>B: 目的 MAC-B 的单播帧
{% endmermaid %}

ARP 过程至少会留下三类可观察状态：

| 证据 | 观察点 |
| --- | --- |
| ARP 请求 | 广播帧、目标协议地址是待解析 IP |
| ARP 应答 | 源 IP/MAC 与目标 IP/MAC 反转 |
| 邻居缓存 | 后续数据帧不必每次重新广播 |

{% note info flat %}
在 Linux 上可以用下面的命令查看预期证据：
{% endnote %}

~~~bash
ip neigh show
sudo tcpdump -ni any arp
~~~

{% note info flat %}
这里的命令是观察路径，不宣称已经在你的机器上执行。接口名、权限和系统网络栈可能不同。
{% endnote %}

### 默认网关

{% note info flat %}
如果 A 的目标是 203.0.113.20，而 A 的地址是 192.168.10.10/24，A 通过前缀判断目标不在本地网段。它不会对 203.0.113.20 发 ARP，而是查路由表得到默认网关 192.168.10.1，再解析网关的 MAC：
{% endnote %}

{% mermaid %}
flowchart TD
  A[应用目标 203.0.113.20] --> B[检查本地前缀]
  B -->|不在 192.168.10.0/24| C[查路由表]
  C --> D[选择下一跳 192.168.10.1]
  D --> E[ARP 解析网关 MAC]
  E --> F[帧目的 MAC=网关 MAC]
  F --> G[路由器继续三层转发]
{% endmermaid %}

{% note warning flat %}
这也是“能 ping 网关但不能访问远端”与“ARP 失败”的区别所在：前者说明本地链路和一跳邻居可能正常，后续问题仍可能在路由、NAT、传输或应用层。
{% endnote %}

### IPv6 邻居发现

{% note info flat %}
IPv6 不使用 IPv4 ARP，而使用 ICMPv6 Neighbor Discovery。ND 不只是“IPv6 版本的 ARP”，它同时覆盖邻居地址解析、邻居不可达检测、路由器发现和前缀/参数通告。
{% endnote %}

解析一个邻居的链路地址时，典型路径是 NS → NA：

{% mermaid %}
sequenceDiagram
  participant A as IPv6 主机 A
  participant M as Solicited-Node 组播
  participant B as IPv6 邻居 B
  A->>M: Neighbor Solicitation: target=B
  M-->>B: 组播组成员接收，再由目标地址匹配的邻居响应
  B->>A: Neighbor Advertisement: target=B, link-layer=B-MAC
  Note over A: 邻居缓存进入可达/陈旧等状态，后续帧使用 B-MAC
{% endmermaid %}

{% note info flat %}
主机不需要像 IPv4 ARP 那样把请求广播给整个链路，而是根据目标 IPv6 地址构造 solicited-node multicast。多个 IPv6 地址可能映射到同一个组播组，因此组成员会先收到报文，再由目标地址匹配的邻居决定是否发送 Neighbor Advertisement；它不是“组播地址直接等于唯一目标”的单播替代。邻居公告可以携带目标链路层地址；缓存条目还会经历 reachable、stale、delay、probe 等状态，发送方在需要时通过 NUD 检查邻居是否仍可达。
{% endnote %}

{% note info flat %}
路由器发现是另一条重要路径：主机可以发送 Router Solicitation，路由器用 Router Advertisement 通告默认路由、前缀和接口参数。于是 IPv6 的自动配置和默认网关学习也属于 ND 相关能力，不应把 ND 只画成“地址换 MAC”。
{% endnote %}

| ND 机制 | 解决的问题 | 观察点 |
| --- | --- | --- |
| NS/NA | 邻居地址解析或确认 | ICMPv6 类型 135/136、目标 IPv6、链路层地址选项 |
| RS/RA | 发现路由器和前缀参数 | ICMPv6 类型 133/134、Router Lifetime、Prefix Information |
| NUD | 发现缓存中的邻居是否仍可达 | 邻居状态变化、单播探测、重新发送 NS |
| Solicited-Node Multicast | 缩小邻居解析的二层/三层接收范围 | 目标组播地址和网卡组播订阅 |

{% note info flat %}
只读验证可以使用：
{% endnote %}

~~~bash
ip -6 addr
ip -6 route
ip -6 neigh show
sudo tcpdump -ni any 'icmp6'
~~~

{% note warning flat %}
不要把“看不到 ND”直接解释成 IPv6 没有邻居发现；缓存可能已经存在、抓包接口可能不对、网卡卸载或过滤器也可能改变观察结果。不要为了学习随意关闭 IPv6 或清空邻居缓存。
{% endnote %}

## 失败边界与验证

| 现象 | 优先检查 | 不要直接下的结论 |
| --- | --- | --- |
| 本地目标第一次访问延迟 | ARP/邻居缓存、交换机学习 | 不要直接说 TCP 慢 |
| 同网段主机无法互通 | 网卡状态、ARP、FDB、广播域 | 不要直接清空所有缓存 |
| 能访问网关但不能访问远端 | 路由、NAT、防火墙、远端服务 | 不要把问题归因于 ARP |
| 只在第一次访问失败 | 条目老化、邻居状态、服务冷启动 | 不要认为链路一定断开 |
| 抓包中看到请求却没有应答 | 对端、广播域、策略或返回路径 | 不要只看发送端日志 |

{% note info flat %}
安全验证时，优先只读命令：
{% endnote %}

~~~bash
ip addr
ip route
ip neigh
ss -lntup
~~~

{% note info flat %}
如果需要清理邻居缓存，必须先确认目标接口和影响范围，并把它当成会改变本机网络状态的操作；学习文章不把清理缓存作为默认修复步骤。
{% endnote %}

{% folding blue, 展开查看交换机四种动作 %}
1. 学习：从收到帧的源 MAC 建立或更新 FDB；
2. 转发：目的 MAC 已知且在其他端口；
3. 过滤：目的 MAC 已知但就在入端口；
4. 泛洪：目的 MAC 未知、是广播或由设备策略要求扩散。

这个抽象解释的是透明桥接的核心动作，不覆盖所有厂商硬件、VLAN、生成树、组播侦听或安全策略细节。
{% endfolding %}

## 分层复习

{% flashcard basic id:CN-NET-001 deck:"计算机网络" priority:1 tags:"分层,网络模型" %}
--- question
学习网络分层时，为什么要同时看寻址、可达性和应用语义三条轴？
--- answer
寻址说明目标是谁，可达性说明数据能否沿路径交付，应用语义说明交付后请求是否按协议完成。
--- explanation
同一个“页面打不开”可能分别卡在 DNS/IP、TCP/TLS 或 HTTP/CORS。把三条轴分开，才能选择下一条证据，而不是把所有问题都叫作网络不通。
{% endflashcard %}

{% flashcard basic id:CN-NET-002 deck:"计算机网络" priority:1 tags:"OSI,TCP/IP,分层" %}
--- question
OSI 七层模型和 TCP/IP 分层模型应该怎样使用？
--- answer
把它们当作定位职责和边界的抽象，不要把现实协议机械地一一塞进唯一层。
--- explanation
OSI 便于描述物理、链路、网络、传输和应用等职责；TCP/IP 更接近互联网协议族的组织方式。排障时先说明观察对象，再指出层间依赖。
{% endflashcard %}

{% flashcard basic id:CN-NET-003 deck:"计算机网络" priority:1 tags:"封装,解封装" %}
--- question
发送端和接收端的封装、解封装分别做什么？
--- answer
发送端逐层为载荷增加本层字段，接收端按协议栈逐层读取并消费字段，再把剩余载荷交给上层。
--- explanation
交换机通常只需读取当前帧的链路字段，路由器会处理 IP 和下一跳，最终主机才把应用数据交给 HTTP、DNS 等应用协议。
{% endflashcard %}

{% flashcard basic id:CN-NET-004 deck:"计算机网络" priority:1 tags:"协议边界,排障" %}
--- question
为什么“能看到某一层的字段”不能直接证明整个请求成功？
--- answer
每层只能证明相应观察点存在；后续层仍可能失败。
--- explanation
看到 ARP 只说明链路地址解析发生，看到 TCP 建立只说明传输连接建立，看到 HTTP 404 才说明某个 HTTP 服务返回了响应；结论必须标明已验证的层。
{% endflashcard %}

{% flashcard basic id:CN-NET-005 deck:"计算机网络" priority:2 tags:"交换机,路由器,设备边界" %}
--- question
普通交换机和路由器的转发依据有什么不同？
--- answer
普通交换机主要根据当前链路的目的 MAC 和 FDB 转发，路由器根据 IP 前缀和路由表选择下一跳并重新封装链路帧。
--- explanation
三层交换机、防火墙和网关可能同时具备多层能力；回答时要说明正在讨论的是哪种转发功能，不能把 FDB 和路由表混为一谈。
{% endflashcard %}

{% flashcard basic id:CN-NET-006 deck:"计算机网络" priority:2 tags:"广播域,失败边界" %}
--- question
分层模型在排障中最有用的产出是什么？
--- answer
把现象映射到可验证的层和字段，并明确下一步要观察的证据。
--- explanation
例如“本地网关可达但远端失败”应继续看路由、NAT、TCP 或 HTTP，而不是反复清理 ARP；“收到 404”则应转向资源、路由、Host 和应用响应。
{% endflashcard %}

## 局域网复习

{% flashcard basic id:CN-L2-001 deck:"计算机网络" priority:2 tags:"分层,局域网" %}
--- question
一次同网段通信中，IP 地址和 MAC 地址分别解决什么问题？
--- answer
IP 决定逻辑目标和是否需要经过路由，MAC 负责当前链路上的一跳交付。
--- explanation
主机先根据前缀判断目标是本地还是远端，再为当前下一跳获取 MAC。MAC 会在每一跳重写，不能当作跨互联网的最终地址。
{% endflashcard %}

{% flashcard basic id:CN-L2-002 deck:"计算机网络" priority:2 tags:"以太网,帧" %}
--- question
以太网帧中目的 MAC、源 MAC、类型字段和 FCS 分别有什么作用？
--- answer
目的/源 MAC 标识当前链路交付双方，类型字段指示载荷协议，FCS 用于检测帧传输错误。
--- explanation
帧字段服务于链路层；IP、TCP、HTTP 字段不应与它们混为一谈。抓包还可能受网卡校验和卸载影响。
{% endflashcard %}

{% flashcard basic id:CN-L2-003 deck:"计算机网络" priority:1 tags:"交换机,FDB" %}
--- question
交换机如何学习 FDB？
--- answer
它从收到帧的源 MAC 和入端口建立或更新映射。
--- explanation
目的 MAC 用于查找转发方向，源 MAC 用于学习位置。FDB 会老化、变化或在设备重启后丢失，所以它是动态状态。
{% endflashcard %}

{% flashcard basic id:CN-L2-004 deck:"计算机网络" priority:1 tags:"交换机,泛洪" %}
--- question
未知单播为什么会泛洪？泛洪是否会从入端口发回？
--- answer
因为交换机暂时不知道目的 MAC 所在端口，会在同一广播域内扩散，但通常不从入端口发回。
--- explanation
未知单播泛洪是学习过程的正常边界，不等于广播，也不等于帧一定会被目标主机接受。
{% endflashcard %}

{% flashcard basic id:CN-L2-005 deck:"计算机网络" priority:1 tags:"ARP,邻居发现" %}
--- question
ARP request 为什么通常使用广播，而 ARP reply 通常可以使用单播？
--- answer
请求方还不知道目标 MAC，只能在广播域询问；目标收到请求后知道请求方 MAC，可以直接单播回复。
--- explanation
ARP 缓存会减少重复广播。观察 ARP 时应同时看 Ethernet 目的 MAC 和 ARP payload 中的协议地址。
{% endflashcard %}

{% flashcard basic id:CN-L2-006 deck:"计算机网络" priority:1 tags:"ARP,网关" %}
--- question
访问远端 IP 时，为什么解析的是默认网关 MAC 而不是远端服务器 MAC？
--- answer
因为远端 IP 不在本地前缀内，当前链路的下一跳是默认网关。
--- explanation
IP 目标保持为远端地址，但当前帧目的 MAC 是网关 MAC；路由器收到后重新封装下一跳帧。
{% endflashcard %}

{% flashcard basic id:CN-L2-007 deck:"计算机网络" priority:2 tags:"IPv6,Neighbor Discovery" %}
--- question
IPv6 Neighbor Discovery 如何完成邻居解析，并且为什么不只是 ARP 的改名？
--- answer
主机通过 ICMPv6 Neighbor Solicitation/Advertisement 解析邻居，使用 solicited-node 组播；ND 还包括 Router Advertisement 和 Neighbor Unreachability Detection。
--- explanation
NS/NA 对应地址解析，RS/RA 对应路由器和前缀发现，NUD 负责缓存可达性。验证时可看 ICMPv6 类型 133～136 和邻居缓存状态。
{% endflashcard %}

{% flashcard basic id:CN-L2-008 deck:"计算机网络" priority:2 tags:"FDB,故障排查" %}
--- question
FDB 条目老化或主机换端口时，可能出现什么现象？
--- answer
第一次通信可能经历未知单播泛洪或短暂延迟，随后交换机重新学习位置。
--- explanation
应结合端口、MAC、广播域和抓包证据判断；不要因为一次泛洪就清空所有网络状态。
{% endflashcard %}

{% flashcard basic id:CN-L2-009 deck:"计算机网络" priority:2 tags:"广播域,交换机" %}
--- question
冲突域和广播域有什么区别？交换机、Hub、VLAN 和路由器分别影响哪个边界？
--- answer
冲突域关注共享介质上的同时发送和碰撞，广播域关注二层广播的传播范围；Hub 共享冲突域，交换机端口通常隔离冲突，VLAN 切分广播域，路由器三层接口通常隔离广播。
--- explanation
“交换机隔离冲突域、路由器隔离广播域”是带双工、VLAN 和设备功能前提的口诀。碰撞问题看双工/接口错误，广播问题看 VLAN、环路和泛洪。
{% endflashcard %}

{% flashcard basic id:CN-L2-FAQ-001 deck:"计算机网络" priority:1 tags:"交换机,IP,MAC" %}
--- question
为什么普通交换机不能直接根据 IP 转发以太网帧？
--- answer
普通二层交换机依据当前链路中的目的 MAC 和 FDB 转发；根据 IP 做三层转发需要路由表、最长前缀匹配和 TTL 等网络层逻辑。
--- explanation
三层交换机可以同时具备路由功能，但那是设备启用的另一种转发能力，不能把二层 FDB 与三层路由表混为一谈。
{% endflashcard %}

{% flashcard basic id:CN-L2-FAQ-002 deck:"计算机网络" priority:2 tags:"ARP,缓存,排障" %}
--- question
ARP 缓存越多越好吗？
--- answer
不是。缓存可以减少广播，但过期、错误或欺骗性条目会导致错误交付。
--- explanation
排障时先观察条目状态和请求/应答，再在明确接口范围内刷新；清空缓存不是解释故障原因的证据。
{% endflashcard %}

{% flashcard basic id:CN-L2-FAQ-003 deck:"计算机网络" priority:2 tags:"以太网,FCS,抓包" %}
--- question
抓包看不到 FCS 是否说明网卡损坏？
--- answer
不能这样推断。硬件校验和卸载、抓包点和驱动行为都可能使 FCS 不出现在主机看到的帧中。
--- explanation
应结合网卡错误计数、对端抓包和链路状态验证；单个抓包视图缺少 FCS 不能直接归因于硬件故障。
{% endflashcard %}
