{% note primary flat %}
流式响应不是“收到一段文字就算成功”。客户端还要处理事件顺序、部分文本、工具调用、usage、完成事件、错误事件和连接结束。本节用本地 SSE fixture 注入乱序、断流、429、超时和取消，建立不会重复显示文本或重复执行工具的状态机。
{% endnote %}

<!-- concept-story:start -->
一个聊天页面在收到前三个 token 后断线，前端把已有文本显示成最终答复；重连时又从头拼接，用户看到了两遍开头。另一个请求在工具调用事件之后断开，重试逻辑没有记住调用 ID，库存查询被执行了两次。

团队把“正在生成”“已完成”“可重试失败”“已取消”分开，并让文本展示和工具执行各自拥有去重策略。于是部分结果可以保留给用户看，但只有完成事件才会进入成功路径；工具重试则依据调用 ID 决定重放还是拒绝冲突。
<!-- concept-story:end -->

## 事件状态

### 流式事件与最终消息

SSE 的传输层只负责把事件帧送到客户端，业务层还要定义事件状态：

| 状态 | 可以观察到 | 可以做什么 | 不能做什么 |
| --- | --- | --- | --- |
| `open` | 已收到创建或首个增量 | 展示“生成中”，暂存文本 | 不能宣布请求成功 |
| `partial` | 文本增量、工具增量或 usage | 更新临时界面，记录序号 | 不能把临时文本当最终消息 |
| `completed` | Provider 完成事件或明确结束标记 | 固化文本、Usage 和结果 | 不能再把重连内容追加一次 |
| `failed` | HTTP/事件错误、断流或解析错误 | 分类、记录、决定是否重试 | 不能无条件重试所有错误 |
| `cancelled` | 调用方取消并关闭连接 | 停止消费和后续副作用 | 不能在取消后自动补发请求 |

Chat 风格接口常见 `choices[].delta`、finish reason 和 `[DONE]`；Responses 风格接口可能使用 `response.output_text.delta`、工具事件和 `response.completed`；Gemini 的不同入口又有各自的 candidate/step 事件。不要用一个“只取 text”的循环跨越所有 Provider。

### 部分文本与工具

文本和工具事件要分开累积：

```text
SSE frame
   │
   ├─ text.delta ───────> 临时文本缓冲区
   ├─ tool.call.delta ──> 工具调用缓冲区
   ├─ usage  ───────────> 统计记录
   ├─ error ────────────> 失败状态与重试判断
   └─ completed/[DONE] ─> 成功提交
```

工具调用在流中可能被拆成名称、ID 和参数片段；只有参数完整并通过第八篇的 schema、权限、幂等和超时门禁后，才能执行。连接在工具事件之后断开时，重试前要把调用 ID 交给执行账本，不能只依据显示文本判断是否执行过。

如果 Provider 发送未知事件，兼容层应保留 raw 事件或事件名并继续执行已知分支；如果未知事件影响完成判定，则应保守地保持未完成，而不是猜测成功。

## 恢复策略

### 错误与取消

{% note warning flat %}
429、401/403、4xx 参数错误、5xx 服务不可用、解析失败、连接断开、超时和用户取消不是同一种错误。只有明确可重试的错误才进入退避；重试还必须受总截止时间、最大次数和幂等策略约束。
{% endnote %}

| 错误 | 是否通常重试 | 必须保留 | 首选动作 |
| --- | --- | --- | --- |
| 401/403 | 否 | 脱敏状态和认证域 | 修复凭据/权限，不重试原请求 |
| 400/422 | 否 | 字段和 Provider 错误类型 | 修复请求或降级，不隐藏参数错误 |
| 429 | 有条件 | `Retry-After`、尝试次数、截止时间 | 退避到指定时间后重试，超过预算则失败 |
| 5xx | 有条件 | request ID、attempt、部分结果 | 有界退避，避免风暴 |
| 断流 | 有条件 | 已收事件、调用 ID、是否完成 | 先判定幂等与预算，再决定续接或重发 |
| 超时 | 有条件 | 总耗时、阶段、部分结果 | 取消连接；仅在剩余预算足够时重试 |
| 用户取消 | 否 | 取消原因和时间 | 传播取消、关闭连接、停止后续副作用 |

`Retry-After` 是 Provider 给出的等待证据，不应被固定的“重试三次”覆盖。退避计时器也不能突破总 deadline；单次连接 timeout 与整个用户请求的 deadline 是两个不同的控制量。

### 避免重复输出和重复执行

重试有两条独立的去重线：

- **文本线**：每次 attempt 有自己的缓冲区；未完成 attempt 的部分文本不能与新 attempt 无条件拼接。只有最终提交时选择一份经过完成判定的结果，或使用 Provider 明确支持的续接游标。
- **工具线**：使用稳定的 `call_id`/幂等键和参数指纹。同 ID 同参数可以重放已记录结果；同 ID 不同参数必须报冲突。

重试报告至少记录 `request_key`、`attempt`、`event_seq`、`status`、`partial_length`、`tool_call_ids` 和 `retry_after`。这样“页面看到了两次”与“工具执行了两次”可以分别定位。

## 最小实践

### 准备输入

{% note info flat %}
以下代码只解析本地 SSE 字符串，不访问任何 Provider，不安装依赖，也不使用真实凭据。事件名、`[DONE]` 和响应完成事件只是合成 wire fixture；不同 Provider 的正式事件名仍需以其当前文档和实际响应为准。
{% endnote %}

### 执行步骤

```python
import copy
import json


def sse(event, data, seq=None, delay_ms=0):
    payload = {"type": event, "data": data, "delay_ms": delay_ms}
    if seq is not None:
        payload["seq"] = seq
    return "data: " + json.dumps(payload, ensure_ascii=False) + "\n\n"


NORMAL = [
    sse("response.created", {"id": "resp_001"}, 1),
    sse("text.delta", {"text": "库存"}, 2),
    sse("text.delta", {"text": "为 12"}, 3),
    sse("vendor.note", {"trace": "fixture-only"}, 4),
    sse("response.completed", {"status": "completed"}, 5),
]
OUT_OF_ORDER = [NORMAL[0], NORMAL[2], NORMAL[1], NORMAL[3], NORMAL[4]]
DISCONNECTED = NORMAL[:-1]
RATE_LIMITED = [
    sse("response.created", {"id": "resp_429"}, 1),
    sse("error", {"status": 429, "type": "rate_limit", "retry_after": 2}, 2),
]
TIMEOUT = [
    sse("response.created", {"id": "resp_timeout"}, 1),
    sse("text.delta", {"text": "部分"}, 2, delay_ms=80),
]
CANCELLED = [
    sse("response.created", {"id": "resp_cancel"}, 1),
    sse("text.delta", {"text": "不应提交"}, 2),
    sse("response.completed", {"status": "completed"}, 3),
]
TOOL_PARTIAL = [
    sse("response.created", {"id": "resp_tool"}, 1),
    sse("text.delta", {"text": "查询"}, 2),
    sse("tool.call", {"call_id": "call_weather_001", "name": "get_weather"}, 3),
]
TOOL_RETRY = TOOL_PARTIAL + [sse("response.completed", {"status": "completed"}, 4)]


def parse_frame(raw):
    if not raw.startswith("data: ") or not raw.endswith("\n\n"):
        raise ValueError("parse_error:invalid SSE frame")
    return json.loads(raw[6:-2])


def consume(frames, deadline_ms=50, cancel_at=None):
    state = {
        "status": "open", "text": [], "last_seq": 0,
        "tool_calls": [], "unknown": [], "retry_after": None, "error": None,
    }
    for index, raw in enumerate(frames):
        if cancel_at == index:
            state["status"] = "cancelled"
            state["error"] = "caller_cancelled"
            break
        try:
            frame = parse_frame(raw)
        except ValueError as error:
            state["status"], state["error"] = "failed", str(error).split(":", 1)[0]
            break
        if frame.get("delay_ms", 0) > deadline_ms:
            state["status"], state["error"] = "timeout", "deadline_exceeded"
            break
        seq = frame.get("seq")
        if seq is not None and seq <= state["last_seq"]:
            state["status"], state["error"] = "out_of_order", "event_sequence_regressed"
            break
        if seq is not None:
            state["last_seq"] = seq
        kind, data = frame["type"], frame["data"]
        if kind == "text.delta":
            state["status"] = "partial"
            state["text"].append(data["text"])
        elif kind == "tool.call":
            state["status"] = "partial"
            state["tool_calls"].append(data)
        elif kind == "error":
            state["status"] = "rate_limited" if data.get("status") == 429 else "failed"
            state["retry_after"] = data.get("retry_after")
            state["error"] = data.get("type", "provider_error")
            break
        elif kind == "response.completed":
            state["status"] = "completed"
        elif kind != "response.created":
            state["unknown"].append(kind)
    else:
        if state["status"] in {"open", "partial"}:
            state["status"] = "disconnected"
    state["text"] = "".join(state["text"])
    return state


def commit_tool(call, ledger):
    fingerprint = json.dumps(call, sort_keys=True)
    if call["call_id"] in ledger:
        old_fingerprint, old_result = ledger[call["call_id"]]
        if old_fingerprint != fingerprint:
            return {"status": "conflict"}
        return {"status": "replayed", "result": old_result}
    result = {"city": "Shanghai", "temperature_c": 22}
    ledger[call["call_id"]] = (fingerprint, result)
    return {"status": "executed", "result": result}


normal = consume(NORMAL)
out_of_order = consume(OUT_OF_ORDER)
disconnected = consume(DISCONNECTED)
rate_limited = consume(RATE_LIMITED)
timeout = consume(TIMEOUT)
cancelled = consume(CANCELLED, cancel_at=2)
partial_tool = consume(TOOL_PARTIAL)
retry_tool = consume(TOOL_RETRY)
ledger = {}
first_tool = commit_tool(partial_tool["tool_calls"][0], ledger)
replayed_tool = commit_tool(retry_tool["tool_calls"][0], ledger)

retry_decision = {
    "status": rate_limited["status"],
    "action": "retry_after_seconds",
    "seconds": rate_limited["retry_after"],
}
result = {
    "normal": {key: normal[key] for key in ("status", "text", "unknown")},
    "failures": {
        "out_of_order": out_of_order["status"],
        "disconnected": disconnected["status"],
        "rate_limited": retry_decision,
        "timeout": timeout["status"],
        "cancelled": cancelled["status"],
    },
    "tool": {
        "partial_status": partial_tool["status"],
        "retry_status": retry_tool["status"],
        "first": first_tool["status"],
        "replayed": replayed_tool["status"],
        "executions": len(ledger),
    },
}

assert result["normal"] == {"status": "completed", "text": "库存为 12", "unknown": ["vendor.note"]}
assert result["failures"]["out_of_order"] == "out_of_order"
assert result["failures"]["disconnected"] == "disconnected"
assert result["failures"]["rate_limited"]["seconds"] == 2
assert result["failures"]["timeout"] == "timeout"
assert result["failures"]["cancelled"] == "cancelled"
assert result["tool"] == {
    "partial_status": "disconnected", "retry_status": "completed",
    "first": "executed", "replayed": "replayed", "executions": 1,
}

print(json.dumps(result, ensure_ascii=False, sort_keys=True))
```

### 观察输出

{% note success flat %}
预期结果显示：正常流只有在 `response.completed` 后才提交；未知事件被保留；乱序、断流、429、超时和取消进入不同状态。工具流在重试后再次看到同一 `call_id`，只重放结果，执行账本仍只有一次。429 的等待时间来自 fixture 的 `retry_after=2`，不是通用固定值。
{% endnote %}

## 取消传播

### 避免重复输出和重复执行

{% note warning flat %}
取消是控制信号，不是普通 Provider 错误。应用收到用户取消后，应停止读取 SSE、关闭连接、停止排队中的工具和后续重试；已经完成的只读操作要记录结果，尚未执行的副作用不能因为重连而自动补发。
{% endnote %}

| 层 | 取消动作 | 验收信号 |
| --- | --- | --- |
| UI/请求层 | 触发 `AbortSignal`、任务取消或等价机制 | 调用方记录取消原因和时间 |
| HTTP 层 | 中止 response body 读取并关闭连接 | 不再消费后续事件 |
| 解析层 | 状态改为 `cancelled`，保留已收事件 | 不产生 `completed` |
| 工具层 | 取消未开始任务，已开始任务按工具协议停止或收尾 | 不新增未经授权的执行 |
| 重试层 | 清除待重试计划 | 取消后没有新 attempt |
| 展示层 | 可以展示“已取消”和部分文本 | 部分文本不被标为最终答案 |

文本提交和工具提交应当分别具备事务边界：文本只有完成时写入最终消息，工具只有授权且执行账本提交后才回传结果。若业务必须支持断点续接，要使用 Provider 明确提供的游标或响应 ID，并验证事件不会被重复消费。

## 结果验证

### 验收证据

| 验收项 | 通过证据 | 失败信号 | 复测动作 |
| --- | --- | --- | --- |
| 事件顺序 | 序号单调，乱序进入明确状态 | 乱序文本仍被静默拼接 | 交换两个增量帧 |
| 完成判定 | 有 Provider 完成事件或明确结束标记 | 收到首段文本就成功 | 删除完成事件，断言不是 `completed` |
| 部分结果 | 临时文本与最终文本分离 | 断流内容被当最终答复 | 在完成前断开连接 |
| 限流 | 读取 `Retry-After` 并受 deadline/次数约束 | 固定次数无等待地重试 | 注入 429 和不同等待时间 |
| 断流/超时 | 状态分别记录，重试前检查预算 | 无限重试或连接悬挂 | 注入无完成事件和延迟帧 |
| 取消 | 停止消费、工具和重试 | 取消后仍创建新请求 | 在首个增量后取消 |
| 工具幂等 | 同一调用 ID 只产生一次执行 | 重试造成重复副作用 | 断在工具事件后再重放 |
| 未知事件 | raw 类型被保留或保守处理 | 未知事件被丢弃且误判完成 | 插入 vendor event |

### 复测动作

1. 针对每个 Provider 记录正常事件、完成事件、错误事件、Usage 和结束标记的实际形状。
2. 为解析器准备增量、乱序、空 choices、未知事件、断流、429、超时和取消 fixture。
3. 把文本缓冲、状态提交和工具账本分开测试；不要只断言最终字符串。
4. 真实请求前确认连接取消、工具副作用、重试预算和日志脱敏策略；本地 SSE 通过不代表 Provider 在线可用。

## 常见问题

{% flashcard basic id:llm-stream-success-boundary deck:"大模型应用开发" priority:1 tags:"流式与错误,SSE" %}
--- question
流式响应什么时候才算成功？
--- answer
只有观察到 Provider 明确的完成证据并通过解析、业务和工具门禁后，才应提交为成功；已经收到的部分文本不等于最终成功。
--- explanation
成功判定至少检查四类证据：

1. **传输证据**：SSE 帧可解析，连接没有在完成前断开。
2. **顺序证据**：事件序号或 Provider 的顺序规则没有回退，增量没有被重复消费。
3. **完成证据**：例如 Chat 风格的结束标记/finish reason，或 Responses 风格的完成事件；具体名字必须按 Provider 适配器定义。
4. **业务证据**：工具调用已通过 schema、权限、超时和幂等门禁，Usage/错误字段没有表明请求失败。

如果只有“已收到文本”，状态应保持 `partial`。断流、超时和取消可以保留部分结果供界面展示，但必须和最终消息分开存储。
{% endflashcard %}

{% flashcard basic id:llm-stream-tool-retry-idempotency deck:"大模型应用开发" priority:1 tags:"流式与错误,工具调用" %}
--- question
为什么重试工具调用可能造成副作用？
--- answer
流在工具调用事件之后断开时，客户端无法仅凭连接状态判断工具是否已经执行；如果重试没有使用调用 ID 和参数指纹，可能把同一个动作执行两次。
--- explanation
安全重试应保留以下记录：

- `call_id` 或应用定义的幂等键。
- 工具名、版本和规范化参数指纹。
- 授权决定、开始/完成状态和结果摘要。
- 原始 attempt、事件序号、断开原因和重试时间。

同 ID 同参数可以返回已提交的结果（`replayed`）；同 ID 不同参数应返回 `conflict`，不能把它当成新的调用。若工具不支持幂等或无法确认执行状态，应暂停自动重试并转人工/业务补偿流程。文本可以重新生成，退款、写入和发送通知不能用同样的无状态拼接策略。
{% endflashcard %}
