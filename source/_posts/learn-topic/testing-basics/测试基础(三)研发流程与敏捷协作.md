借阅功能排了两周开发，测试却到最后一天才拿到环境：此时才发现“每人最多借三本”没有说明续借、逾期和并发借阅的规则。问题不只是测试时间短，需求歧义已经进入设计和代码。把同一个借阅需求放进不同研发流程，可以看清测试应当在哪里提供反馈、留下什么证据，以及谁来处理反馈。
{% endnote %}

## 研发模型

### 瀑布与V模型

{% note primary flat %}
研发模型描述活动之间怎样衔接。瀑布侧重阶段顺序，V 模型强调开发工作与相应测试之间的关系；选择模型后，仍应让每项开发活动有相应的测试活动，并尽早评审草稿、分析测试条件，而不是等软件全部完成才思考怎么测。
{% endnote %}

![W模型中的工作产品评审与测试设计](/img/learn-topic/testing-basics/w-model.png "W模型：在形成工作产品时评审和设计测试")
{% endgallery %}

| 模型 | 借阅需求中的安排 | 能提早发现什么 | 使用边界 |
| --- | --- | --- | --- |
| 瀑布 | 需求评审通过后进入设计，验收条件随需求交付 | “最多三本”是否包含已逾期但未归还的书 | 阶段结束不代表不再变化；变更仍需影响分析 |
| V 模型 | 分析业务需求时考虑验收；设计系统时考虑系统测试；设计接口时考虑集成测试 | 不同测试层级分别检查什么，接口如何被观察 | 图中的四层是简化表示，不是 CTFL 五个测试层级的完整清单 |
| W 模型 | 需求、设计、代码各自接受静态评审，并提前设计后续动态检查 | 规则遗漏、不可测设计和代码问题 | “提前设计”不等于软件尚未存在时已经执行并通过 |

### W模型与迭代

{% note info flat %}
同一产品可以先交付“正常借阅”，再加入“归还”和“预约”。增量强调每次增加可用能力，迭代强调根据反馈反复调整已有成果；两者可以同时发生。每个增量都要验证新增功能及受影响的旧行为，例如加入归还后，原来的借阅数量限制是否仍正确。
{% endnote %}

![多轮迭代中的开发、测试与反馈](/img/learn-topic/testing-basics/agile-iterations.png "每轮都形成反馈，不把测试推到全部迭代之后")

{% note warning flat %}
这些图帮助比较反馈位置，不规定组织必须照抄图中的岗位、阶段或发布节奏。图中单列“测试阶段”只表示集中测试的安排，不能据此把评审、测试分析和组件检查都推迟到该阶段。迭代短也不自动意味着质量高：缺少明确预期时，只会更快重复同一个错误。
{% endnote %}

{% note warning flat %}
测试过程要适应上下文。支付系统可能要求独立复核、严格追踪和受控环境；内部低风险小工具可以采用更轻的记录。需求清晰度、团队技能、技术架构、资源限制和监管要求都会改变活动的深度与顺序，但“团队小”不是省略可判定预期的理由。
{% endnote %}

## 测试活动

### 分析到完成

{% note info flat %}
每个测试层级应有自己的目标：组件检查聚焦局部借阅计算，系统检查聚焦完整借阅流程，验收检查聚焦业务能否实际使用。分析和设计测试的时机与对应开发活动相配合，例如需求形成时先讨论验收例子、接口设计时先考虑集成检查；草稿一旦可用就可以评审，不必等待正式签字才反馈。
{% endnote %}

{% note primary flat %}
测试分析回答“测什么”，测试设计回答“怎么测”，测试实现把设计变成可执行的测试过程和数据。执行只占其中一部分；计划、监控与控制贯穿这些活动，发现新信息时可以回到分析或设计重新调整。
{% endnote %}

{% timeline 借阅迭代的测试安排, blue %}
<!-- timeline 计划与监控控制 -->
假设目标是允许正常会员借阅有库存的书，本轮上限为三本。先列出权限、数量限制和库存一致性的风险，约定测试环境、人员与完成条件。每天比较实际进展和计划；若环境晚到两天，控制措施可以是提前评审规则、先验证可用接口并公开剩余风险，不能把未执行用例改成通过。
<!-- endtimeline -->
<!-- timeline 分析 -->
从需求识别可测试条件：账户有效、已借数量小于三、库存大于零。遇到“逾期是否冻结账户”的歧义时记录问题，由业务负责人澄清后再确定预期，不能由测试人员自行发明产品规则。
<!-- endtimeline -->
<!-- timeline 设计 -->
把条件组合成检查：已借两本且库存为一时借阅，应成功；已借三本时应拒绝且库存不变。选择覆盖条件、输入数据和结果观察点，同时明确环境需要能查询借阅记录和库存。
<!-- endtimeline -->
<!-- timeline 实现 -->
准备两个独立会员和可恢复库存，排列用例执行顺序，写成可执行步骤或脚本。记录环境版本与数据恢复方式；用例能被别人照着执行，而不依赖作者临时口述。
<!-- endtimeline -->
<!-- timeline 执行 -->
记录实际提示、借阅记录和库存变化，与预期比较。出现差异先核对需求、数据和环境，再提交可复现缺陷；修复后重新验证，同时检查受影响的限制规则。
<!-- endtimeline -->
<!-- timeline 完成 -->
汇总覆盖范围、通过与失败结果、未执行原因和未解决风险；归档可复用测试资产，恢复环境，并把规则遗漏等问题带入回顾。完成活动不只发生在整个项目结束，也可以发生在测试层级或迭代结束时。
<!-- endtimeline -->
{% endtimeline %}

### 测试工作产品

{% note info flat %}
测试工作产品（testware）是上述活动使用或产生的资料，包括计划、条件、用例、数据、脚本、日志与报告。它们不必各占一份文档，但必须能追踪“这个结论来自哪个规则、哪个版本和哪次检查”。需求变更时，这条关系帮助找出需要重做的测试。
{% endnote %}

| 活动 | 借阅示例的工作产品 | 检查产物是否可用 |
| --- | --- | --- |
| 计划 | 范围、风险、人员、时间与退出条件 | 能说明为什么先检查权限和库存 |
| 监控与控制 | 进度摘要、风险变化、调整决定 | 能看到阻塞由谁处理，未执行项没有消失 |
| 分析 | 需求 R-03 对应的数量限制测试条件 | 三本是否含逾期未还已澄清 |
| 设计 | 两本和三本等数据、预期和环境要求 | 既检查提示，也检查借阅与库存副作用 |
| 实现 | 执行顺序、数据集、测试过程和脚本 | 换一个执行者仍能复现并恢复数据 |
| 执行 | 版本、实际结果、日志和缺陷记录 | 失败证据可以关联到具体测试与需求 |
| 完成 | 测试完成报告、未解决项、改进建议 | 没测到的范围和接受风险的人都明确 |

## 敏捷协作

### Scrum团队

{% note primary flat %}
全团队方法让具有不同技能的人共同对质量负责。Scrum 2020 的 Scrum Team 包含 Product Owner、Scrum Master 和 Developers 三类责任；Developers 指共同构建可用增量的人员，不只指程序员。测试技能可以存在于 Developers 中，也需要与业务和其他专业人员合作。
{% endnote %}

| 责任 | 主要关注 | 借阅迭代中的具体动作 |
| --- | --- | --- |
| Product Owner | 产品价值、产品目标和产品待办的有效管理 | 澄清限制规则，排序借阅与预约需求 |
| Developers | 创建可用增量、维护 Sprint 计划、遵守完成定义 | 测试、开发、分析人员一起把规则变为设计、实现和证据 |
| Scrum Master | 建立 Scrum、提高团队有效性、促成障碍移除 | 帮助解决环境长期阻塞，促进团队检查协作方式 |

{% note info flat %}
团队跨职能，表示整体具备交付所需技能；自管理表示团队内部决定谁做什么、何时做和怎样做，不代表每个人都必须熟练掌握全部技能。全团队质量也不排斥独立测试：安全关键场景可能需要额外独立性，不能用“大家都负责”取消必要制衡。
{% endnote %}

### 事件与工件

{% note info flat %}
假设本轮 Sprint 目标是“会员能可靠完成借阅”。团队在规划时选择相应待办，并把实现、测试和修复一起纳入交付计划。Sprint 是不超过一个月的固定时长容器，规划、每日 Scrum、评审和回顾都发生在其中；不是先做一个开发 Sprint，再做一个测试 Sprint。
{% endnote %}

{% mermaid %}
flowchart TD
  P[产品待办] --> S[Sprint 规划]
  S --> B[Sprint 待办<br/>目标、条目、计划]
  B --> W[协作实现与测试]
  W --> D[每日检查与调整]
  D --> W
  W --> I[满足完成定义的增量]
  I --> R[Sprint 评审]
  R --> P
  R --> T[Sprint 回顾]
  T --> N[下一轮改进]
{% endmermaid %}

| 事件 | 要检查或决定什么 | 借阅示例 |
| --- | --- | --- |
| Sprint | 容纳朝目标推进的全部工作，保持节奏 | 两周内交付满足完成定义的借阅增量 |
| Sprint Planning | 为什么有价值、做什么、怎样完成 | 选入借阅规则，安排设计、实现、测试和修复 |
| Daily Scrum | Developers 检查目标进展并调整近期计划，限时 15 分钟 | 库存检查阻塞时先协作解决，不只是向经理报工时 |
| Sprint Review | 团队与利益相关者检查成果，讨论接下来如何适应 | 展示真实借阅结果，讨论规则反馈和待办调整 |
| Sprint Retrospective | 改进质量与有效性 | 找到规则迟澄清的原因，并确定下一轮改进动作 |

| 工件 | 对应承诺 | 例子 |
| --- | --- | --- |
| Product Backlog：有序的产品待办 | Product Goal：产品目标 | 提供可信赖的自助借阅服务 |
| Sprint Backlog：目标、选入条目和交付计划 | Sprint Goal：Sprint 目标 | 会员能可靠完成借阅 |
| Increment：可用增量 | Definition of Done：完成定义，简称 DoD | 符合团队共同质量标准、可使用的借阅能力 |

{% note warning flat %}
Sprint Backlog 是 Developers 使用和更新的计划；范围可以随学习与 Product Owner 澄清、重新协商，但不能危及 Sprint 目标，也不能降低质量。某项未满足 DoD，不能只因为演示能点通就把它算作已完成增量。Sprint Review 也不是发布审批门，满足条件的增量可以在 Sprint 内提前交付。
{% endnote %}

![Scrum迭代中的待办、协作与反馈循环](/img/learn-topic/testing-basics/scrum-cycle.jpeg "历史示意图：时间与职责以 Scrum 2020 的定义为准")

{% note info flat %}
图中的“1—4 周”和站会标记是简化画法。准确边界是 Sprint 不超过一个月、Daily Scrum 为 Developers 检查目标进展的 15 分钟事件，形式不强制站立；评审是共同检查成果，回顾是改进工作方式。图中循环不表示其他时间不能交流、测试或交付。
{% endnote %}

## 反馈与改进

### 左移与DevOps

{% note primary flat %}
左移是把适合的测试活动放到更早能产生有效反馈的位置，例如评审需求、检查设计可测性、运行组件检查。它不会取消后面的系统测试和验收：规则文字正确，仍不能证明运行中的借阅和库存是一致的。
{% endnote %}

| 反馈点 | 具体动作 | 得到的证据 | 仍不能证明 |
| --- | --- | --- | --- |
| 需求形成时 | 用“已借两本/三本”示例共同澄清限制 | 经确认的规则与例子 | 实现已经正确 |
| 设计时 | 讨论借阅记录与库存失败时怎样保持一致 | 可测试的设计和观察入口 | 异常路径实际可恢复 |
| 代码变化时 | 评审改动，快速检查相关组件和接口 | 某个版本的检查结果 | 全部用户流程已通过 |
| 运行后 | 结合用户反馈、日志与关键业务指标 | 真实环境中的行为线索 | 没人投诉就没有缺陷 |

{% note info flat %}
DevOps 强调开发、测试与运维协作，让构建、集成、交付和运行反馈形成较短循环。持续集成会频繁合并并检查小改动，流水线可重复准备环境和执行检查；代价是需要维护工具、环境和自动化。流水线全绿只说明其中配置的检查通过，不能替代遗漏的验收条件，也不能把生产环境当成任意试错的测试场。
{% endnote %}

### 回顾

{% note info flat %}
回顾要把“测试总是太晚”变成可执行的改进。假设本轮 12 个借阅待办中有 4 个进入实现后才澄清关键规则，返工集中在数量限制；团队可以先修正示例评审的时机，而不是笼统要求测试人员下次更努力。
{% endnote %}

| 记录项 | 示例决定 |
| --- | --- |
| 事实 | 12 项中有 4 项晚澄清规则，记录具体待办与等待时间 |
| 原因假设 | 讨论需求时只确认页面，未用正反例检查规则 |
| 改进动作 | 下一轮选入的借阅待办，在实现前共同评审一个允许例与一个拒绝例 |
| 负责人 | 产品与具备测试技能的 Developers 协作准备例子，由团队检查执行情况 |
| 复查时间 | 下次回顾检查同类晚澄清项数量和返工原因 |
| 结果边界 | 数量下降是改进线索；待办复杂度不同，不能直接归因于单一动作 |

{% note success flat %}
一份可用的迭代测试安排，应能沿着“需求规则 → 测试条件与数据 → 执行结果 → 风险决定”找到记录，并能说明反馈由谁处理、何时复查。用这条链检查自己的借阅计划，比只检查是否填写了测试计划模板更有效。
{% endnote %}

## 其他实践

### Kanban与XP

{% note primary flat %}
Kanban 关注工作流和在制品控制，让团队在有容量时拉取新工作；XP 关注结对、测试、重构和持续集成等工程实践。前者帮助看见排队，后者改善小步交付的技术反馈，都不能代替准确的业务规则和测试预期。
{% endnote %}

![工作项在不同状态间流转的看板](/img/learn-topic/testing-basics/kanban-board.jpeg "看板需要明确流转策略和在制品限制，不只是几列卡片")
![XP技术实践之间的联系](/img/learn-topic/testing-basics/xp-practices.jpeg "经典 XP 实践示意，不是所有组织必须照抄的完整规范")

### 使用边界

{% folding open, 借阅团队的看板与技术实践 %}
在制品（WIP）是已经开始但尚未完成的工作。假设测试中最多容纳两项，目前两项都因环境阻塞，继续开五个新开发任务只会扩大排队；更合理的动作是协作排除阻塞、完成已有工作，再依据容量拉取新项。限制不能通过随意把卡片移到“等待”列而绕过，开始与完成的边界必须明确。

XP 的结对可以让两个人及时检查实现，持续集成让小改动尽早接触其他代码，测试和重构帮助维持可修改性。但自动化断言若采用了错误规则，执行再频繁也会重复确认错误。因此技术实践与业务示例评审需要配合，不能从“采用 XP”直接推出软件质量达标。
{% endfolding %}

## 常见问题

{% flashcard basic id:testing-basics-a03-concept-1 deck:"测试基础" priority:2 tags:"敏捷,测试职责" %}
--- question
敏捷是否意味着不需要测试人员？
--- answer
不意味着。测试技能与活动融入全团队，质量共同负责，但专业分工和必要的独立测试仍然存在。
--- explanation
借阅功能需要澄清规则、设计正反例、准备数据、检查结果和说明风险。缩短迭代只改变这些活动的协作节奏，不会让活动自动消失。在 Scrum 2020 中，Developers 是创建可用增量的人员，包含所需专业技能，不等同于“只写代码的人”。

| 做法 | 对质量的影响 |
| --- | --- |
| 产品、测试、开发共同检查“三本上限”的例子 | 在规则进入代码前发现理解差异 |
| 开发结束后只把质量交给测试人员 | 风险集中到末尾，容易把未验证项当成完成 |
| 对安全关键部分保留独立验证 | 增加不同视角，补充全团队方法 |

全团队负责不等于取消个人专业职责，也不要求每个人具备相同技能。是否需要额外独立性，要看风险和适用要求。
{% endflashcard %}

{% flashcard basic id:testing-basics-a03-concept-2 deck:"测试基础" priority:2 tags:"Scrum,Sprint" %}
--- question
Sprint 待办能否调整？
--- answer
能。Developers 更新计划；范围可与 Product Owner 澄清和重新协商，但不能危及 Sprint 目标或降低质量。
--- explanation
Sprint Backlog 包含 Sprint 目标、选入的产品待办和交付计划，它会随学习而更新。假设目标是可靠借阅，执行时发现库存一致性问题，就要把修复与复查纳入计划；必要时与 Product Owner 协商缩减不影响目标的范围。

| 变化 | 判断 |
| --- | --- |
| 为完成可靠借阅增加失败恢复检查 | 调整实现计划，检查目标是否仍可达到 |
| 为赶时间取消必要检查并宣称 Done | 降低质量，不应把未满足 DoD 的工作算作完成 |
| 临时插入完整营销模块 | 评估是否危及目标，不能以“敏捷拥抱变化”为由直接塞入 |

改变计划不等于随意改变目标。评审用于检查成果和适应后续工作，不是把未完成测试事后补成通过的地方。
{% endflashcard %}

{% flashcard basic id:testing-basics-a03-concept-3 deck:"测试基础" priority:2 tags:"测试左移,反馈" %}
--- question
测试左移是否只是把测试提前执行？
--- answer
不是。它把评审、分析、设计和适合的动态检查前移，让缺陷更早暴露；后续系统与验收测试仍然需要。
--- explanation
对于“每人最多借三本”，在需求讨论时询问逾期书是否计入，是静态反馈；在设计时约定库存与借阅记录的观察入口，是提高可测性；代码形成后运行数量限制检查，是动态反馈。这些活动的可执行时机不同，不能统一理解为提前跑 UI 脚本。

需求歧义被澄清 → 设计和用例采用一致规则 → 实现后检查实际行为，是一条较短的反馈链。若只把脚本提前运行，却仍没有正确预期或独立数据，错误结论不会因为出现得早就变可靠。早期检查通过也不证明集成后的完整借阅流程已通过。
{% endflashcard %}
