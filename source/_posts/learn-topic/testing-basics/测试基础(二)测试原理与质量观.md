{% note info flat %}
登录页显示“登录成功”，并不等于登录功能已经正确实现。还要确认进入的是谁的账户、是否建立会话、退出后会话是否失效，以及错误密码是否被拒绝。测试的工作，是把这些问题变成可观察的证据，并说明证据能支持多大范围的结论。以下登录规则与数据均为教学假设。
{% endnote %}

## 测试目标

### 验证与确认

{% note primary flat %}
测试既要检查实现是否符合约定，也要判断约定能否满足实际使用需要。前者称为验证（verification），后者称为确认（validation）。发现缺陷、评价质量、降低风险和帮助决策可以同时发生，不能把其中任何一个排除在测试目标之外。
{% endnote %}

| 观察目标 | 登录案例中的动作 | 能留下的证据 |
| --- | --- | --- |
| 评价工作产品 | 评审“连续失败后限制登录”的需求，追问次数与恢复条件 | 歧义记录与修订后的规则 |
| 检查约定与覆盖 | 按规则设计正确密码、错误密码、锁定账户的检查 | 规则与用例的对应关系、实际执行结果 |
| 触发失效并发现缺陷 | 锁定账户输入正确密码，观察是否仍获得会话 | 可复现步骤、账户状态、响应与会话记录 |
| 检查真实使用需要 | 请目标用户完成登录及找回账户，观察是否能完成任务 | 任务完成情况与阻碍，不只看页面是否出现 |
| 建立信心并降低风险 | 优先验证误登录他人账户、锁定失效等高影响问题 | 已控制与仍未验证的风险 |
| 支持约定与决策 | 根据适用合同、规则检查必要行为，将剩余风险交给责任人 | 满足项、未满足项、适用范围与发布建议 |

{% note success flat %}
一条可判断的教学规则是：“账户状态为锁定时，无论密码是否正确，均不得建立新会话。”测试前保存账户锁定状态，提交正确密码，检查拒绝提示及没有新会话；如果只检查页面文案，就还没有证明拒绝登录这一业务结果。
{% endnote %}

### 测试与调试

| 环节 | 具体行动 | 产物与边界 |
| --- | --- | --- |
| 测试发现异常 | 用锁定账户提交正确密码，仍进入首页 | 记录实际结果与预期的差异；此时不能凭现象断言是哪一行代码错了 |
| 调试定位与修复 | 重现现象，检查条件分支，发现锁定检查被跳过并修复 | 原因分析与修复版本；修复成功不能由修改代码这一动作证明 |
| 确认修复 | 在修复版本重跑原失败条件 | 原问题不再出现的证据 |
| 检查其他影响 | 再检查正常账户、错误密码及解锁后的登录 | 判断变更有没有破坏其他行为；范围按影响分析选择 |

{% note info flat %}
测试与调试是活动的区别，不是岗位边界。同一个人可以先测试再调试，开发人员也可以测试自己的代码。静态评审若已经直接发现需求矛盾或代码缺陷，修正它不需要先人为制造一次运行失效。
{% endnote %}

{% image /img/learn-topic/testing-basics/testing-and-checking.png, alt=概念示意：测试包含学习与实验，人工和机器检查位于其中, width=720px, bg=#ffffff %}

{% note info flat %}
这张概念图把“按已有标准检查结果”放在更广的学习、提问、建模和观察活动中。对应登录案例：脚本可以检查“错误密码返回拒绝”，但仍要有人判断拒绝规则是否充分、遗漏了哪些账户状态。它不是测试与自动化的严格分类标准，也不能据此认定机器只能检查、人工不会机械检查。
{% endnote %}

## 质量与职责

### QA与质量控制

{% note primary flat %}
质量控制面向产品当前表现，测试是其中的重要活动；质量保证（QA）面向研发与测试过程的预防和改进。团队共同对质量负责，测试人员不能独自保证产品无缺陷，也不应替所有业务责任人接受剩余风险。
{% endnote %}

{% folding open, 从登录缺陷反推过程改进 %}
锁定失效被发现后，产品侧需要修正规则或实现，并验证具体行为，这是对当前产品的质量控制。同类问题多次出现时，团队应追查为什么账户状态总被遗漏：需求模板是否缺少状态字段？评审是否没有相关业务人员？用例是否只保留成功路径？

把“评审必须检查账户状态”加入检查单，并在后续迭代观察是否减少同类遗漏，才形成可检验的过程改进。增加一个审批人却不观察实际效果，不能自动等同于质量提高。测试结果既能支持产品修复，也能作为过程改进的输入。
{% endfolding %}

### 独立性与协作

| 独立程度 | 登录案例中的安排 | 收益与代价 |
| --- | --- | --- |
| 作者自测 | 实现者检查密码分支 | 熟悉代码、定位快；可能沿用实现时的错误假设 |
| 同团队同伴测试 | 同事按规则重新设计账户状态 | 增加视角；仍可能共享团队盲点 |
| 组织内独立团队 | 独立测试人员检查完整登录链路 | 更容易质疑假设；需要同步业务背景 |
| 组织外独立测试 | 外部人员按明确范围评价系统 | 更高独立性；沟通、环境与领域知识成本更大 |

{% note warning flat %}
独立性不等于隔离。只在交付末尾接收一个安装包，测试人员可能错过需求讨论；开发人员也可能误以为“质量由测试兜底”。可同时安排作者自测、同伴评审和独立系统测试，让不同视角相互补充。安全关键场景可能要求更高独立性，不能直接套用普通 App 的协作安排。
{% endnote %}

### 通用技能与测试角色

| 职责 | 登录案例中的工作 | 检查工作是否完成 |
| --- | --- | --- |
| 测试管理角色 | 明确范围、安排资源、监控进度、调整计划、汇总结束结论 | 谁处理锁定规则未确认的问题？未执行风险是否有责任人？ |
| 测试实施角色 | 分析规则、设计用例、准备数据和环境、执行并记录结果 | 其他人能否按记录重做，并得到可判断的结果？ |

{% note info flat %}
角色不等于职位：小团队可以由同一人承担两类职责，大团队也可以多人分担。会用工具不足以完成这些工作。测试方法帮助选择数据，细致与好奇心帮助发现异常，分析和批判思维帮助质疑假设，业务知识帮助判断预期，技术知识帮助获取证据，沟通与倾听帮助团队就规则达成一致。报告“锁定账户仍建立会话，见步骤与记录”比评价“开发没有认真做”更有用。
{% endnote %}

## 错误与失效

### 根因链路

{% note primary flat %}
人作出错误判断，可能在需求、设计、代码或用例中引入缺陷；缺陷在特定条件下被触发，才可能表现为失效。一次测试失败还可能来自错误预期、失效数据或环境问题，不能自动归因于产品代码。图中假定本次提交的是正确密码，锁定状态决定该缺陷是否暴露。
{% endnote %}

{% mermaid %}
flowchart TD
  A["根因<br/>规则未澄清"] --> B["错误<br/>误判登录条件"]
  B --> C["缺陷<br/>遗漏锁定检查"]
  C --> D{账户是否锁定}
  D -->|否| E[正常放行]
  D -->|是| F["失效<br/>错误放行"]
  C --> G["静态评审<br/>发现缺陷"]
{% endmermaid %}

| 对象 | 本例证据 | 不能直接推出的结论 |
| --- | --- | --- |
| 错误 | 实现者将“密码正确”误当成全部登录条件 | 不能只凭运行日志推断个人动机 |
| 缺陷 | 代码或设计中缺少账户状态检查 | 存在缺陷不代表每次登录都会失败 |
| 失效 | 已锁定账户实际取得可用会话 | 现象本身不一定能指出根因 |
| 根因 | 复盘确认状态规则未澄清且评审未覆盖 | “某人粗心”通常不足以指导预防措施 |

### 静态发现

{% note info flat %}
静态测试不执行被测软件，例如对照需求审查代码，直接发现锁定判断缺失；动态测试执行软件，通过输入和输出观察失效。两者互补：静态发现可以更早修复遗漏，动态执行则能检验代码、配置、依赖和数据组合后的实际行为。
{% endnote %}

| 看到的现象 | 进一步核查 | 可能的结论 |
| --- | --- | --- |
| “锁定账户”能够登录 | 数据初始化是否真的设置了锁定状态 | 若初始化失败，先修复测试数据，不能据此报产品缺陷 |
| 正确密码无法登录 | 环境中的身份服务是否可达、账户是否属于该环境 | 环境不可用时，登录行为结论可能是阻塞而非产品失败 |
| 代码缺少锁定分支 | 是否有其他必经层统一检查状态 | 需要核查完整职责分工，避免把局部缺省误报为遗漏 |

## 测试原则

### 七项原则

{% note info flat %}
原则的用途是帮助选择下一步行动。下面仍以登录为主，借一个简单借阅规则对照“实现正确”与“用户需要”的区别，不要求背诵固定措辞。
{% endnote %}

| 原则 | 案例与行动 |
| --- | --- |
| 能发现缺陷，不能证明完全无缺陷 | 发现锁定失效足以证明至少有一个问题；正常账户登录通过不能证明所有账户都正确 |
| 穷尽测试通常不可行 | 账户、密码、状态、设备、网络和历史操作组合巨大，按输入类别、规则和风险选择代表条件；极小有限模型可以枚举，但不能外推为完整系统穷尽 |
| 尽早测试可减少后续返工 | 在需求评审中补全解锁条件，比实现、用例和用户文档都写完后再改影响更小；具体成本仍取决于情境 |
| 缺陷常聚集 | 若账户状态模块反复出问题，应增加该区域检查；不能机械认定永远有固定“二八比例”，也不能放弃其他区域 |
| 测试会失去发现新问题的能力 | 只反复用同一正常账户，很难发现新状态问题，应补数据与场景；已有回归检查仍有防止旧问题复发的价值 |
| 测试依赖上下文 | 普通论坛登录和资金系统登录的风险不同，证据、独立性、投入应不同 |
| 没发现缺陷不等于满足需要 | 借阅系统严格实现“只允许工作日上午借书”，却让晚间到馆的目标用户无法借书，规格符合也可能没有解决真实问题 |

### 应用边界

{% note warning flat %}
“不可能穷尽”不能成为随意漏测的理由。应明确已经覆盖哪些规则、哪些条件没有执行，以及为何先处理某类风险。相反，“已有用例全部通过”也不能成为停止思考需求遗漏的理由：用例本身可能复制了需求或实现的盲点。
{% endnote %}

## 层级与类型

### 测试层级

{% note info flat %}
测试层级根据被测对象、目标、依据、典型问题和职责区分。同一条“锁定账户不得登录”的规则可以在不同层级检查，但各层发现的问题不同，不应把所有检查都挤到界面端。
{% endnote %}

| 层级 | 登录案例的对象与依据 | 关注的问题与常见参与者 |
| --- | --- | --- |
| 组件测试 | 单独的账户状态判断函数；依据详细规则或代码设计 | 锁定分支返回错误，通常由开发人员在隔离环境检查 |
| 组件集成测试 | 登录服务与账户仓储的交互；依据内部接口设计 | 状态字段传错、约定不一致，通常由开发人员检查组件协作 |
| 系统测试 | 完整应用的登录行为；依据系统需求 | 页面、会话和账户信息不一致，可由独立测试团队执行 |
| 系统集成测试 | 应用与外部身份提供方；依据系统间协议 | 令牌、错误映射或超时处理不一致，需要接近实际交互的环境 |
| 验收测试 | 面向用户与业务的登录任务；依据业务需要及验收约定 | 用户是否能完成业务、是否具备投入使用条件，适合业务代表、目标用户等参与 |

{% note info flat %}
验收不只有用户验收，还可能涉及运维验收、合同验收、法规验收，以及 alpha/beta 测试。这里需要识别各自的判断主体和依据，不把它们当作每个项目必须依次执行的固定阶段。层级可以重叠开展；组件通过不会自动使系统或验收通过。
{% endnote %}

### 分类维度

| 分类问题 | 维度 | 同一条登录检查如何描述 |
| --- | --- | --- |
| 检查什么质量特征 | 功能、非功能 | 是否正确拒绝锁定账户是功能；响应时间是否满足约定是非功能 |
| 用什么依据设计 | 黑盒、白盒 | 按业务规则选账户是黑盒；按状态分支安排覆盖是白盒 |
| 是否运行被测对象 | 静态、动态 | 评审状态规则是静态；实际提交登录请求是动态 |
| 从什么入口操作 | 界面、接口等 | 接口测试也可以检查业务功能，也可以测响应时间 |
| 由谁或什么执行 | 人工、自动化 | 人工请求和脚本请求都能检查同一业务规则 |

{% note primary flat %}
这些维度不是互斥菜单。一次“通过接口提交锁定账户并检查不建立会话”的检查，可以同时是系统层、功能、黑盒、动态、自动化测试。黑盒不等于只点界面，白盒也不等于只做组件测试；要说明对象边界与设计依据。
{% endnote %}

## 证据判断

### 结论范围

{% note primary flat %}
合格的结论应能回答“哪个版本、什么环境、哪些数据和条件、依据什么预期、实际观察到什么、还缺什么”。测试为质量与发布决策提供信息，不能把局部通过换成“系统没有问题”的保证。
{% endnote %}

| 教学记录 | 可支持的结论 |
| --- | --- |
| 版本 build-12，测试环境，正常账户 A，正确密码，页面与会话均属于 A | 已执行的正常登录条件符合预期 |
| 同版本，锁定账户 B，正确密码，被拒绝且无新会话 | 已执行的锁定条件符合预期 |
| 外部身份服务超时场景未执行 | 该风险没有本轮执行证据，不能从前两条推断通过 |

### 信息不足

{% note warning flat %}
面试官说“登录页测一下”，应先澄清登录方式、账户状态、会话规则、失败限制和被测边界。对方不给具体规则时，可以明确提出教学假设继续设计；不能一边自行假定锁定次数，一边把产品实际行为判为缺陷。没有确定预期时，先输出待澄清问题与风险，不编造通过或失败。
{% endnote %}

## 常见问题

{% flashcard basic id:testing-basics-a02-concept-1 deck:"测试基础" priority:2 tags:"测试原理" %}
--- question
测试和调试有什么区别？测试人员能不能调试？
--- answer
测试评价工作产品、发现缺陷或触发失效；调试定位原因并消除缺陷。它们是活动区别，同一人可以承担两者，修复后仍需验证。
--- explanation
锁定账户仍登录成功时，先记录账户状态、输入、实际会话与预期，这是测试证据。检查代码并修复遗漏分支属于调试。

| 时点 | 还缺的证据 |
| --- | --- |
| 已复现失败 | 原因仍需要分析 |
| 已提交修复 | 原失败条件是否通过 |
| 原条件已通过 | 相关正常登录和解锁行为是否受影响 |

静态评审直接发现需求矛盾时，修正矛盾不需要先复现运行失败。岗位名称不能替代对活动和证据的区分。
{% endflashcard %}

{% flashcard basic id:testing-basics-a02-concept-2 deck:"测试基础" priority:2 tags:"测试分类" %}
--- question
功能测试与接口测试是否互斥？黑盒测试是否只能操作界面？
--- answer
不互斥。功能描述检查目标，接口描述操作入口，黑盒描述按规格而非内部结构设计测试；三个维度可以同时成立。
--- explanation
对登录接口提交锁定账户，检查拒绝结果且没有新会话：这是通过接口检查业务功能，也可以完全按公开登录规则设计，不需要知道实现分支。

| 改变的观察目标 | 测试描述的变化 |
| --- | --- |
| 检查锁定账户被拒绝 | 功能检查 |
| 在约定负载下检查响应分位数 | 非功能中的性能检查 |
| 对照内部判断分支补数据 | 加入白盒设计依据 |

不能仅凭使用了接口工具，就判断用例采用黑盒还是白盒；要看数据和覆盖目标从哪里推导。
{% endflashcard %}

{% flashcard basic id:testing-basics-a02-concept-3 deck:"测试基础" priority:2 tags:"质量证据" %}
--- question
所有测试用例都通过，能否证明软件没有缺陷？应如何汇报？
--- answer
不能。通过只说明已执行条件符合既定预期；应报告版本、范围、执行结果、未覆盖条件和剩余风险。
--- explanation
若 20 条登录用例都只使用正常账户，20/20 通过并不包含锁定账户的证据。通过率的分母是这些用例，不是系统全部可能行为。

对这 20 条用例，更准确的汇报是：build-12 的已执行正常账户登录条件通过；锁定账户拒绝和外部身份服务超时尚未验证，相应风险未关闭。即便实现符合全部已知规格，规格本身也可能遗漏用户需要，所以还要检查业务任务是否真正可完成。
