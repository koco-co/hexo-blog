{% note info flat %}
测试点是待探索的风险或条件，用例是另一个人可以按相同前置、数据和步骤执行并判定结果的最小记录。本篇用密码登录、短信登录、购物车和搜索四个小场景，把“功能正常”改成有依据的功能证据。
{% endnote %}

## 用例构成

{% note primary flat %}
一条合格用例至少要能回答：测什么规则、在什么前置下、使用什么数据、做哪些动作、观察什么预期、失败后如何清理。唯一 ID 便于追踪，优先级用于排序，不代表缺陷严重程度。
{% endnote %}

| 字段 | 作用 | 登录示例 |
| --- | --- | --- |
| ID/关联规则 | 追踪需求与覆盖 | S01 / AUTH-01 |
| 标题 | 一句话表达目标 | 正确凭据建立会话 |
| 前置 | 固定环境和状态 | 账号已启用且未锁定 |
| 数据 | 可复现输入 | member@example.test / 合成密码 |
| 步骤 | 可重做动作 | 打开登录页、输入、提交 |
| 预期 | 可判定结果与副作用 | 页面进入账号 M，服务端会话属于 M |
| 优先级/清理 | 排序和恢复 | P1；退出并删除测试账号 |

![黑盒测试从输入、行为到可观察结果的关系](/img/learn-topic/testing-basics/black-box-model.jpeg "黑盒测试模型")

## 拆解规则

{% note primary flat %}
先列规则，再识别条件和观察点；界面文案只是证据的一部分，业务状态、接口响应、数据变化和审计记录也可能是必要观察。黑盒从规格推导输入，白盒从代码结构补充覆盖，经验法用于发现未知风险，三者不是互斥选项。
{% endnote %}

{% mermaid %}
flowchart LR
  R[规则] --> C[条件与状态]
  C --> D[代表数据]
  D --> A[动作与依赖]
  A --> O[界面/接口/数据预期]
  O --> T[追踪与复核]
{% endmermaid %}

## 编写用例

| ID | 前置与数据 | 步骤 | 预期 | 优先级 |
| --- | --- | --- | --- | ---: |
| S01-01 | 启用账号；正确密码 | 输入账号密码并提交 | 建立属于该账号的会话，进入首页 | 1 |
| S01-02 | 启用账号；错误密码 | 提交一次错误密码 | 拒绝登录，提示不泄露账号存在性；无新会话 | 1 |
| S01-03 | 空账号或空密码 | 直接提交 | 指出具体缺失字段，请求未提交或被业务拒绝 | 1 |
| S02-01 | 验证码有效期 300 秒（教学规则） | 获取并输入一次验证码 | 登录成功且验证码变为已使用 | 1 |
| S02-02 | 验证码已过期 | 输入过期验证码 | 明确过期，不能建立会话，可按规则重新获取 | 1 |

{% note warning flat %}
步骤要写动作和数据，预期要写状态和可观察证据。“登录成功”“接口返回 200”都不够：还要确认会话主体、错误状态、数据副作用和重复提交行为。一个用例可以有多个检查点，但检查点之间若能独立失败，通常应拆成多条。
{% endnote %}

## 预期结果

| 观察层 | 正向预期 | 失败边界 |
| --- | --- | --- |
| 界面 | 成功后显示当前账号；错误时提示可行动 | 不显示上一账号残留数据 |
| 接口 | 状态码、错误码和响应字段符合契约 | 错误不回显密码或令牌 |
| 业务数据 | 会话/库存/订单只产生一次变更 | 重复提交不重复扣减 |
| 日志审计 | 记录关联 ID 和结果，不记录秘密 | 失败仍能追到版本和请求 |

![接口检查点从请求、响应到业务状态的证据链](/img/learn-topic/testing-basics/interface-checkpoints.jpeg "接口测试检查点")

## 组织用例

- 让每条用例有单一目标和自足前置，避免依赖上一条用例留下的脏状态；
- 先按风险分 P1/P2/P3，再按需求或模型建立稳定顺序；
- 用关联规则、数据集和执行结果追踪覆盖，不用用例数量代替覆盖理由；
- 为购物车准备“新增、数量边界、删除最后一项”三条独立用例，为搜索准备“有结果、无结果、组合筛选”三条；
- 每次执行后恢复库存、会话和临时数据，失败时保留最小可诊断证据。

## 用例评审

{% note success flat %}
评审按可执行、可判定、可追踪、可维护四个维度检查。发现“功能正常”“准备好数据”这类不可判定语句时，补上具体值、观察点和清理动作；发现多个规则混在一条用例时，按独立失败成本重新拆分。
{% endnote %}

## 常见问题

{% flashcard basic id:testing-basics-scenario-password-login deck:"测试基础" priority:1 tags:"场景,账号密码登录" %}
--- question
给定账号密码登录，如何设计功能测试用例？先澄清需求，再给出方法、数据、步骤和预期。
--- answer
先确认账号状态、错误限制和会话规则，再用正向、错误凭据、缺字段三条可复现用例验证页面、会话和服务端状态。
--- explanation
教学假设：账号存在且启用，正确凭据建立会话，错误凭据不建立会话；锁定、验证码和多端登录先向需求方确认。代表用例：

| 用例 | 前置/数据 | 预期 |
| --- | --- | --- |
| 成功 | 启用账号+正确密码 | 进入账号 M，会话主体为 M |
| 错误 | 启用账号+错误密码 | 拒绝且不泄露账号存在性，无新会话 |
| 缺失 | 空账号或空密码 | 指出字段缺失，不发送或拒绝请求 |

覆盖理由是规则和风险，不是三条就声称穷尽。追问取消登录、已登录再进入、连续失败锁定和重试清理。
{% endflashcard %}

{% flashcard basic id:testing-basics-scenario-sms-login deck:"测试基础" priority:1 tags:"场景,验证码登录" %}
--- question
给定短信验证码登录，如何设计功能测试用例？先澄清需求，再给出方法、数据、步骤和预期。
--- answer
把验证码有效期和一次性规则固定成可控时钟，覆盖成功、过期、重复使用，并记录时间起点、会话结果和清理。
--- explanation
教学假设：验证码有效 300 秒、使用一次即失效，不调用真实短信服务。代表用例应冻结生成时间：有效窗口内输入正确码并建立会话；时间推进到 300 秒后输入同一验证码并被拒绝；成功使用后再次输入同码并被拒绝。还要检查重发是否废弃旧码、验证码是否绑定手机号、多次点击发送是否限流。验证时同时看页面提示、接口错误码和会话状态。
{% endflashcard %}

{% flashcard basic id:testing-basics-scenario-cart-edit deck:"测试基础" priority:1 tags:"场景,购物车" %}
--- question
给定购物车增删改，如何设计功能测试用例？先澄清需求，再给出方法、数据、步骤和预期。
--- answer
以单一商品为夹具，分别验证新增、数量更新和删除最后一项，预期写明数量、总价、库存和空状态。
--- explanation
教学假设：库存为 5，每项购买量允许 1～5，没有额外优惠规则。新增一项后数量为 1、总价等于单价；从 1 改为 5 后总价重新计算且不能超过库存；删除最后一项后列表为空、总价为 0 并显示空状态。每条用例独立创建购物车并清理。追问刷新/重新登录是否保留、不同账号是否隔离、库存变化和重复点击是否幂等。
{% endflashcard %}

{% flashcard basic id:testing-basics-scenario-search-filter deck:"测试基础" priority:1 tags:"场景,搜索筛选" %}
--- question
给定搜索结果筛选，如何设计功能测试用例？先澄清需求，再给出方法、数据、步骤和预期。
--- answer
用可枚举的商品夹具覆盖有结果、无结果和组合筛选，直接比较期望商品集合、计数、排序和页码。
--- explanation
教学假设：筛选条件按 AND 组合，排序和缺省值已定义。准备确定的商品集合，先验证关键词命中集合，再验证一个筛选条件和多个条件的交集；输入不存在的关键词时，显示空状态且计数为 0；切换筛选后检查结果集合、页码和总数是否按规则更新。不要只看“列表有内容”，也要核对边界值、重复商品、排序稳定性。追问快速输入、清空筛选和切换条件是否重置页码。
{% endflashcard %}

{% flashcard basic id:testing-basics-a06-concept-1 deck:"测试基础" priority:1 tags:"测试点,测试用例" %}
--- question
测试点和测试用例有什么区别？
--- answer
测试点表达要探索的风险或条件；测试用例把它落实为可复现的前置、数据、步骤、预期和清理。
--- explanation
“验证登录失败限制”是测试点，仍不能由另一位执行者直接判定。补上账号状态、失败次数、输入、动作、预期锁定状态和恢复方式后，才成为一条或多条测试用例。测试点适合做范围清单，用例适合执行和追踪；不要用几十个模糊测试点宣称覆盖完整。
{% endflashcard %}

{% flashcard basic id:testing-basics-a06-concept-2 deck:"测试基础" priority:1 tags:"预期结果,功能测试" %}
--- question
预期写“功能正常”为什么不合格？
--- answer
它没有说明可观察的状态、数据或副作用，执行者无法一致判断成功与失败。
--- explanation
把“功能正常”改成具体契约，例如“输入有效会员和库存为 1 的图书，提交后借阅记录新增 1 条、库存变为 0、页面显示书名与到期日”。如果页面和接口结果冲突，还要说明以哪个业务状态为准。可判定预期应尽量包含对象、值、范围、错误提示和清理条件，而不是只写一个主观形容词。
{% endflashcard %}

{% flashcard basic id:testing-basics-a06-concept-3 deck:"测试基础" priority:1 tags:"用例粒度,检查点" %}
--- question
多个检查点什么时候应该合并，什么时候应该拆开？
--- answer
只有检查点共享前置、目标和失败解释且失败后仍能定位时才合并；独立风险或独立清理通常应拆开。
--- explanation
登录成功后同时检查页面账号名、会话主体和审计记录，可以保留在同一业务目标下，但预期要逐项列出。若“错误密码被拒绝”和“锁定账户被拒绝”需要不同数据、风险或责任，拆成两条更容易复跑和统计。用例粒度应服务失败隔离、证据诊断和维护成本，而不是追求固定条数。
{% endflashcard %}
