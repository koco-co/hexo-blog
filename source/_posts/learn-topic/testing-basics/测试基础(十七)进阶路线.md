{% note info flat %}
进阶路线用于在主线方法不够时选择下一步，不是把更多术语堆进基础用例。先确认触发条件、风险和交付目标，再选择组合测试、模型维护、跨团队协作或专项质量路线；核心实战不依赖本篇。
{% endnote %}

## 组合测试

### 交互强度

{% note primary flat %}
Pairwise/t-wise 只保证选定交互强度，例如每一对参数组合至少出现一次；它不会自动覆盖所有业务组合、时序或状态。业务约束、禁用组合和高影响规则必须显式保留。
{% endnote %}

### 约束与覆盖

| 触发信号 | 选择 | 仍需补充 |
| --- | --- | --- |
| 参数多且交互风险有限 | pairwise/t-wise | 约束、边界和关键规则 |
| 状态/规则频繁变化 | 模型驱动维护 | 模型版本和追踪 |
| 多团队共享产品 | 依赖与交付协调 | 单团队可交付证据 |
| 专项风险明确 | 性能/安全/行业评审 | 专项指标和授权 |

{% note warning flat %}
组合算法输出的是选择集，不是质量保证。先检查生成器是否保留业务约束、ID 是否稳定、关键规则是否被代表，再与边界和场景用例合并。
{% endnote %}

## 复杂建模

### 模型维护

{% note primary flat %}
当规则、状态和需求变更增多时，维护模型版本、需求追踪和跨模型一致性比再画一张图更重要。继续使用已学的等价类、判定表和状态模型即可；不要为了显得“进阶”引入没有风险依据的第二套框架。
{% endnote %}

### 多模型协作

{% folding open, 模型维护检查 %}
- 每次需求变更标注受影响的条件、状态、转换和用例；
- 保留模型版本、生成参数和不可行组合的理由；
- 检查需求、判定表、状态图和实现对同一规则是否一致；
- 发现模型无法表达业务时，先澄清规则，再决定是否升级方法。
{% endfolding %}

## 规模化协作

### 跨团队依赖

{% mermaid %}
flowchart LR
  A[团队 A：功能与用例] --> I[共同集成/依赖检查]
  B[团队 B：服务与数据] --> I
  C[团队 C：平台与发布] --> I
  I --> E[统一增量证据]
  E --> R[风险与交付决定]
{% endmermaid %}

{% note info flat %}
跨团队协作的核心是依赖、接口、版本和交付边界，不是照搬某个规模化框架的角色图。每个团队仍要交付可复现的局部证据，集成层再验证跨边界状态、数据和发布风险；框架名称本身不能替代责任。
{% endnote %}

### 交付边界

{% note primary flat %}
进阶方法的交付仍须回到可追踪的功能证据：说明需求版本、模型/生成参数、约束、覆盖集合、未覆盖项和责任人。方法输出不是质量保证书；如果生成结果无法解释或复现，就先回到等价类、判定表、状态模型和代表用例。
{% endnote %}

## 专项路线

### 性能安全

- 性能：先定义负载、分位数、吞吐、资源和恢复目标，再选择基准/负载/压力/稳定性实验；
- 安全：在授权隔离环境确定资产、威胁、角色和证据，先脱敏再留存；
- 行业约束：把法规、合同和审计要求转为可追踪验收条件，邀请领域责任人评审；
- 硬件或危险实验：不在普通功能测试中破坏设备，交给具备设施和资质的专项方案。

### 行业约束

{% note warning flat %}
行业约束包括法规、合同、审计和硬件安全要求；它们会改变数据留存、权限、证据和验收条件。先让领域责任人确认适用范围，再把约束写成可追踪用例或专项评审，不把通用功能测试结论包装成合规认证。
{% endnote %}

## 选择练习

{% note success flat %}
如果主要风险是 8 个字段的两两交互，先考虑约束感知的组合测试；如果主要风险是订单状态竞争，优先完善状态模型和并发证据；如果主要风险是上线延迟，先补指标和性能环境。选择理由要能回到风险，而不是工具流行度。
{% endnote %}

## 常见问题

{% flashcard basic id:testing-basics-a17-concept-1 deck:"测试基础" priority:2 tags:"组合测试,pairwise" %}
--- question
Pairwise 能否覆盖所有业务组合？
--- answer
不能。它只覆盖选定的两两交互（或更高强度），仍需补边界、约束、时序和业务关键组合。
--- explanation
四个参数各有多个取值时，pairwise 可以显著减少选择集，但三元或更高阶交互、互斥条件和状态转换可能仍未出现。生成后检查不可行组合、关键规则和稳定 ID，并把高影响组合单独列为用例。不要用生成用例数量或算法名称宣布穷尽。
{% endflashcard %}

{% flashcard basic id:testing-basics-a17-concept-2 deck:"测试基础" priority:2 tags:"模型驱动,状态" %}
--- question
什么时候需要模型驱动测试？
--- answer
当状态、规则或路径较多且频繁变化，手工维护组合容易遗漏时，模型驱动可以用显式模型生成和追踪用例；模型成本必须低于遗漏风险。
--- explanation
先确认已有等价类、判定表和状态图是否能表达风险，再评估模型版本、生成工具、约束和团队维护能力。模型驱动适合可枚举状态和清晰转换，不适合把需求歧义自动变成正确规则。生成后仍要人工评审关键路径、边界、非法转换和结果证据，并把模型变更纳入评审。
{% endflashcard %}
