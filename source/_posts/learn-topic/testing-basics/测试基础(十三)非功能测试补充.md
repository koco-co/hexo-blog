{% note info flat %}
非功能测试关注系统“如何工作”：性能、可靠性、安全、兼容、本地化、易用性和无障碍。它们不是功能用例的装饰，也不能在没有指标、威胁或支持声明时凭感觉判定通过；先从业务风险决定要补哪一类检查。
{% endnote %}

## 补充范围

| 风险问题 | 补充质量属性 | 需要的依据 |
| --- | --- | --- |
| 高峰期能否及时响应 | 性能 | 并发模型、SLO、负载和分位数 |
| 依赖失败能否恢复 | 可靠性 | 重试、超时、RTO/RPO、数据不变量 |
| 未授权者能否读取数据 | 安全与隐私 | 角色、资产、威胁和合规约束 |
| 支持哪些环境与语言 | 兼容与本地化 | 产品支持矩阵、时区和格式规则 |
| 用户能否完成任务 | 易用与无障碍 | 用户目标、键盘、读屏和替代文本 |

{% note primary flat %}
同一个“下单”功能可以同时有功能、性能和安全检查，但每一类的目标、数据和结论不同。接口返回 200 不能证明在目标并发下延迟达标，也不能证明越权请求被拒绝。
{% endnote %}

## 性能与可靠性

![性能测试从目标、负载、观测到分析的流程](/img/learn-topic/testing-basics/performance-process.jpeg "性能测试流程")
![基准、负载、压力、容量和稳定性测试的类型区别](/img/learn-topic/testing-basics/performance-types.jpeg "性能测试类型")

| 类型 | 目标 | 主要指标 | 失败后追问 |
| --- | --- | --- | --- |
| 基准 | 单用户/小负载基线 | 延迟、资源、错误率 | 环境是否可比 |
| 负载 | 目标并发下行为 | p50/p95/p99、吞吐、错误率 | 依赖和数据是否饱和 |
| 压力 | 超过目标后的退化 | 拒绝、排队、恢复 | 是否安全降级 |
| 稳定性 | 长时间运行 | 资源泄漏、错误趋势 | 重启/恢复是否可控 |

![性能与可靠性指标从负载到恢复的关系](/img/learn-topic/testing-basics/performance-reliability.jpeg "性能可靠性")
![高可用性测试关注故障期间的服务能力](/img/learn-topic/testing-basics/high-availability.jpeg "高可用性")
![可扩展性测试比较规模增长与资源/性能变化](/img/learn-topic/testing-basics/scalability.jpeg "可扩展性")
![可恢复性测试中的故障、恢复和数据验证](/img/learn-topic/testing-basics/recoverability.jpeg "可恢复性")

{% note warning flat %}
并发功能测试验证业务不变量，例如最后一件库存只能被一个订单占用；性能测试验证延迟、吞吐和容量。可靠性测试还要验证故障后的恢复时间、数据完整性和降级策略，不能用“压测跑完没有崩”概括全部结论。
{% endnote %}

## 安全与隐私

| 检查点 | 功能问题 | 证据与边界 |
| --- | --- | --- |
| 认证 | 未登录能否进入受保护操作 | 会话、过期和重放结果 |
| 授权 | 角色能否读取/修改他人数据 | 资源 ID、响应和审计记录 |
| 输入处理 | 恶意输入是否改变语义 | 编码、错误、日志和存储 |
| 秘密保护 | 密码、令牌是否进入页面/日志 | 脱敏扫描、访问权限和保留期 |

{% note danger flat %}
安全验证必须在授权的隔离环境中进行；不要把真实账号、令牌或个人数据放入教学夹具和报告。发现敏感信息泄露时，先限制传播并通知责任人，再保留最小可审计证据。
{% endnote %}

## 兼容与本地化

| 维度 | 矩阵示例 | 观察点 |
| --- | --- | --- |
| 运行环境 | 产品声明的浏览器、系统、设备 | 功能、布局、输入和存储 |
| 语言 | 简体中文、英文等支持语言 | 翻译、截断、排序和回退 |
| 区域格式 | 时区、日期、数字、货币 | 解析、展示、跨日边界 |
| 数据迁移 | 旧版本数据→新版本 | 兼容读取、升级和回滚 |

{% note info flat %}
兼容性结论必须绑定产品支持声明和具体版本；不能从一次浏览器成功推断所有环境。语言和时区变化也会改变等价类、边界和状态，必要时把它们加入原功能用例的追踪。
{% endnote %}

## 易用与无障碍

{% note primary flat %}
以用户任务为中心检查目标是否可理解、可完成、可恢复：标签是否说明输入、错误是否给出下一步、键盘是否能到达并操作控件、读屏是否能获得相同信息、动态变化是否被感知。无障碍不是只看颜色对比度。
{% endnote %}

| 任务 | 键盘 | 读屏/语义 | 恢复 |
| --- | --- | --- | --- |
| 登录 | Tab 顺序和焦点可见 | 标签、错误关联输入 | 错误后保留可安全字段 |
| 上传 | 可打开文件选择与取消 | 进度、成功/失败状态 | 断线可重试且不重复 |
| 下单 | 可修改数量和提交 | 金额、状态和焦点变化 | 结果未知可查单 |

## 交付边界

{% note primary flat %}
非功能检查要给出进入条件：指标或支持矩阵已确认、环境可控、数据和授权合适、结果消费者明确。没有指标时先推动需求澄清；无法在本轮执行时记录风险和责任人，不用主观“感觉够快”关闭问题。
{% endnote %}

## 常见问题

{% flashcard basic id:testing-basics-a13-concept-1 deck:"测试基础" priority:2 tags:"并发,性能,功能" %}
--- question
并发功能测试与性能测试有什么区别？
--- answer
并发功能测试验证并发条件下的业务结果和不变量；性能测试验证负载下的延迟、吞吐、资源和容量指标。
--- explanation
两个用户同时领取最后一份库存时，目标是只有一个成功且库存不为负，这是功能正确性；逐步增加并发并测 p95 延迟和错误率，是性能目标。工具和执行方式可能相同，但预期、指标和结论不同。报告应分开写，不能用“压测通过”代替业务一致性证据。
{% endflashcard %}

{% flashcard basic id:testing-basics-a13-concept-2 deck:"测试基础" priority:2 tags:"兼容性,版本" %}
--- question
如何判断前向兼容和后向兼容？
--- answer
前向兼容看旧消费者能否使用新版本提供的数据/接口；后向兼容看新版本能否读取或处理旧版本数据/请求，均需绑定支持声明和契约。
--- explanation
先固定版本方向、接口字段、数据迁移和弃用策略，再构造旧客户端→新服务、新客户端→旧数据等矩阵。观察解析、默认值、错误和回滚；“能启动”不等于兼容，字段语义、权限和时区也可能破坏业务。没有明确支持矩阵时，先把兼容性当作待确认风险。
{% endflashcard %}

{% flashcard basic id:testing-basics-a13-concept-3 deck:"测试基础" priority:2 tags:"性能指标,SLO" %}
--- question
没有性能指标时，能否直接判定达标？
--- answer
不能。应先确认目标用户、负载模型、延迟分位数、吞吐、错误率和资源/恢复边界，再设计可重复基线。
--- explanation
“页面很快”缺少环境、数据和统计口径。至少需要目标并发、p95/p99、成功率、稳定时长和依赖条件；SLO 或产品承诺决定是否达标。没有指标可以报告测量结果和风险，但不能凭单次本地运行宣布通过，也不能用平均值掩盖长尾。
{% endflashcard %}
