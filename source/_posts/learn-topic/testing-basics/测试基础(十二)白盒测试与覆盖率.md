{% note info flat %}
白盒测试从代码结构、控制流和数据流补充测试设计，覆盖率衡量“执行到了哪里”，不直接证明业务规则正确。本篇用一个有短路条件的资格函数手工推导语句与分支覆盖，再说明为什么仍需黑盒用例。
{% endnote %}

## 代码基础

{% note primary flat %}
先识别语句、条件、分支和短路求值。`and`/`or` 可能在左侧已经决定结果时不执行右侧表达式，因此“写在同一行”不等于“两个条件都被观察”。
{% endnote %}

```python
def can_borrow(member: dict, book: dict) -> bool:
    if member["enabled"] and member["borrowed"] < 3:
        return book["stock"] > 0
    return False
```

{% note warning flat %}
这段代码至少有两个判定：会员是否启用、借阅数是否小于 3，以及库存是否大于 0。要观察第二个条件的独立影响，必须准备能让第一个条件为真和为假的输入；当会员未启用时，借阅数可能根本没有被求值。
{% endnote %}

## 结构覆盖

{% mermaid %}
flowchart TD
  A[进入 can_borrow] --> B{enabled?}
  B -->|否| F[return False]
  B -->|是| C{borrowed < 3?}
  C -->|否| F
  C -->|是| D{stock > 0?}
  D -->|是| T[return True]
  D -->|否| F
{% endmermaid %}

| 指标 | 计算方式 | 能说明 | 不能说明 |
| --- | --- | --- | --- |
| 语句覆盖 | 执行语句数 / 可执行语句数 | 哪些语句运行过 | 条件的每个结果是否出现 |
| 分支覆盖 | 已执行分支 / 分支总数 | if/else 路径是否走过 | 输入是否代表业务边界 |
| 条件覆盖 | 条件真/假结果是否出现 | 子条件结果的变化 | 组合关系是否完整 |
| MC/DC | 每个条件能独立影响判定 | 高完整性场景的独立影响 | 业务需求和外部依赖 |

{% note info flat %}
例如只用“启用会员、借阅数 1、库存 1”可能命中 True 路径，但没有执行三个拒绝分支。覆盖率报告应和测试输入、版本及排除规则一起保存，不能只贴一个百分比。
{% endnote %}

## 条件与组合

| 用例 | enabled | borrowed < 3 | stock > 0 | 结果 | 观察 |
| --- | :---: | :---: | :---: | :---: | --- |
| W1 | T | T | T | True | 全部条件为真 |
| W2 | T | T | F | False | 库存分支 |
| W3 | T | F | — | False | 短路不读库存 |
| W4 | F | — | — | False | 更早短路 |

{% note warning flat %}
表中的“—”表示该条件在此用例中未求值，不是把它当作任意真或假。要达到条件覆盖，需要额外设计能让每个已求值条件分别取真和假；要达到 MC/DC，还要证明只改变一个条件就能改变整体判定。
{% endnote %}

## 业务边界

{% note primary flat %}
白盒覆盖发现代码路径缺口，黑盒方法验证需求、输入域、状态和用户结果。代码可能完整覆盖了“库存大于 0”的判断，却把业务上限写错为 3；因此覆盖率应作为风险导航，与需求追踪、边界和状态用例一起解释。
{% endnote %}

| 现象 | 可能的误读 | 更稳的行动 |
| --- | --- | --- |
| 语句 100% | 以为没有 Bug | 检查断言、规则、数据和异常路径 |
| 分支 100% | 以为组合穷尽 | 检查条件交互、状态和外部依赖 |
| 低覆盖 | 直接补无意义脚本 | 先定位高风险未覆盖代码和不可达原因 |
| 报告有排除项 | 认为指标可比 | 说明版本、范围、排除理由和变化 |

## 常见问题

{% flashcard basic id:testing-basics-a12-concept-1 deck:"测试基础" priority:2 tags:"覆盖率,质量证据" %}
--- question
为什么 100% 覆盖仍可能有 Bug？
--- answer
覆盖率只说明执行路径，不能证明断言有效、业务规则完整、输入真实或外部依赖正确。
--- explanation
测试只调用函数而不检查返回值也能提高语句覆盖；错误的预期同样可能让测试通过。即使语句、分支都覆盖，需求可能漏了锁定状态，数据库事务可能错误，接口字段可能不符合契约。覆盖率应帮助寻找未执行区域，再与黑盒边界、状态、集成证据和业务验收共同判断。
{% endflashcard %}

{% flashcard basic id:testing-basics-a12-concept-2 deck:"测试基础" priority:2 tags:"短路求值,条件覆盖" %}
--- question
短路求值导致右侧条件未执行时，覆盖率该怎么算？
--- answer
把未求值条件与“已求值为假/真”区分记录；它不应被伪装成已经覆盖的真假分支。
--- explanation
在 `enabled and borrowed < 3` 中，enabled 为假时右侧不会执行。报告通常按工具的分支/条件口径计算，但设计者要理解该路径没有观察右侧副作用或结果。补一条 enabled 为真、borrowed 达到上限的用例，才能真正执行并覆盖右侧假分支；若依赖短路是安全要求，也要写成明确的断言。
{% endflashcard %}

{% flashcard basic id:testing-basics-a12-concept-3 deck:"测试基础" priority:2 tags:"语句覆盖,分支覆盖" %}
--- question
语句覆盖和分支覆盖是什么关系？
--- answer
语句覆盖关注语句是否执行，分支覆盖关注控制流出口是否都走过；分支通常比单纯语句覆盖提供更强的路径信息，但仍不等于业务完整。
--- explanation
一条只走 True 的路径可能执行 if 内语句，却没有走 else 分支；因此语句覆盖可以很高而分支覆盖仍不足。分支覆盖也不自动覆盖多条件的独立影响、边界数据、状态迁移和外部失败。报告时写清指标口径、可执行代码范围和排除项，并把缺口转成有业务理由的测试。
{% endflashcard %}
