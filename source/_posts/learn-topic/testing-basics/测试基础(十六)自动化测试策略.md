{% note info flat %}
自动化不是把人工步骤逐字翻译成脚本，而是用稳定、可重复的检查降低反馈成本。候选选择要同时考虑规则稳定性、失败诊断、执行频率、环境成本和维护收益；探索、评审和需要人判断的体验仍保留人工职责。
{% endnote %}

## 适用判断

### 稳定规则

| 候选特征 | 自动化价值 | 需要警惕 |
| --- | --- | --- |
| 规则稳定、频繁回归 | 高 | 需求变动导致维护债务 |
| 输入可生成、结果可判定 | 高 | 断言过弱只测页面存在 |
| 环境可隔离、数据可重建 | 高 | 共享环境造成偶发失败 |
| 视觉/体验/探索判断 | 较低或辅助 | 自动化无法替代人的观察 |
| 一次性复杂迁移 | 取决于成本 | 脚本开发成本高于手工 |

{% note primary flat %}
先从高频、稳定、可观察的 P1 规则开始，例如接口层的登录资格和库存不变量；不要因为使用了浏览器工具就把所有检查推到 UI 层。自动化的目标是更快得到可信反馈，不是脚本数量最大化。
{% endnote %}

### 观察成本

{% note info flat %}
自动化的收益不只看执行速度，还要扣除数据准备、失败诊断、环境隔离和维护成本。一个每周只运行一次、失败后仍需人工重做全部步骤的脚本，未必比稳定的人工检查更划算；先把可判定预期和证据接口写清。
{% endnote %}

## 分层组合

### 测试金字塔

{% mermaid %}
flowchart TD
  UI[系统/UI：少量·粗粒度·低隔离·慢反馈]
  API[接口/服务：中等·业务契约·可隔离·中速反馈]
  U[单元/组件：较多·细粒度·高隔离·快反馈]
  UI -->|层级更细、数量增加、反馈变快| API
  API -->|层级更细、数量增加、反馈变快| U
{% endmermaid %}

### 金字塔维度

| 层级 | 数量趋势 | 粒度 | 隔离度 | 执行时间与反馈 |
| --- | --- | --- | --- | --- |
| 系统/UI | 少 | 粗，覆盖完整用户旅程 | 低，依赖浏览器、网络和环境 | 慢，适合关键门禁 |
| 接口/服务 | 中 | 业务契约、状态和数据 | 中，可替身或受控集成 | 中速，适合组合回归 |
| 单元/组件 | 多 | 规则、分支和边界 | 高，依赖少 | 快，适合提交反馈 |

{% note info flat %}
分层不是固定比例，而是对数量、粒度、隔离度和反馈速度的取舍。单元测试适合纯规则与边界，接口测试适合状态、权限和数据契约，系统/UI 只保留关键用户旅程；测试象限是另一种观察测试目的的透镜，不能把象限直接当成测试层级。
{% endnote %}

### 测试象限

{% note info flat %}
测试象限用两个轴安排反馈：一条轴区分业务导向与技术导向，另一条轴区分支持开发与评价产品。Q1～Q4 是测试目的的四个区域；同一个接口用例可以属于某个象限，也可以同时落在测试金字塔的接口层。
{% endnote %}

| 象限 | 两个轴的定位 | 借阅场景示例 | 与自动化的关系 |
| --- | --- | --- | --- |
| Q1 | 技术导向 × 支持开发 | 单元检查上限、金额和状态分支 | 高度适合快速自动化 |
| Q2 | 业务导向 × 支持开发 | 接口/验收示例检查登录、库存和借阅契约 | 可自动化，断言业务结果 |
| Q3 | 业务导向 × 评价产品 | 探索新需求、可用性、关键旅程评审 | 自动化只能辅助，保留人工判断 |
| Q4 | 技术导向 × 评价产品 | 性能、安全、可靠性和兼容性检查 | 需专项工具与受控环境 |

{% note primary flat %}
象限不是质量等级，也不是“Q1 必须单元、Q2 必须接口”的硬性映射。先按风险决定检查内容，再选择最能提供证据的层级与工具；例如 Q2 的业务契约可以在接口层自动化，Q3 的同一旅程仍要由人工探索体验。
{% endnote %}

## 工具支持

### 活动与工具

| 活动 | 可自动化的部分 | 不应自动假定 |
| --- | --- | --- |
| 数据准备 | 固定夹具、工厂、清理 | 所有环境共享同一账号 |
| 执行 | 规则、接口、回归和收集 | 通过等于业务正确 |
| 诊断 | 日志、请求 ID、截图、趋势 | 附件天然没有秘密 |
| 发布 | 门禁、报告、回退触发 | 失败后自动重试到绿色 |

{% note warning flat %}
替身（stub、mock、fake）用于隔离外部依赖，必须说明与真实服务的差异；过度 mock 可能让测试只证明替身行为。关键集成和契约仍需在受控环境验证，失败时保留真实响应边界。
{% endnote %}

### 替身边界

| 替身对象 | 可以隔离什么 | 不能替代什么 |
| --- | --- | --- |
| 时间/支付服务 | 超时、成功、失败和边界时刻 | 真实服务的协议与结算最终一致性 |
| 数据库/文件存储 | 固定夹具、清理和异常返回 | 真实迁移、权限和并发锁语义 |
| 外部客服/消息 | 乱序、重复和不可达 | 真实网络质量与第三方限流 |

{% note warning flat %}
替身必须保留与真实依赖有关的契约断言；否则脚本可能只证明“替身按预设回答”。关键链路至少安排少量真实集成或候选环境证据，并把替身边界写进报告。
{% endnote %}

## 持续反馈

### 流水线与失败

| 流水线阶段 | 反馈 | 稳定性策略 |
| --- | --- | --- |
| 提交 | 单元/静态检查 | 秒级、无网络依赖 |
| 合并 | 接口与组件集成 | 隔离数据、稳定夹具 |
| 候选构建 | 关键系统旅程 | 小矩阵、证据归档 |
| 发布后 | 监控、抽样和探索 | 阈值、回退、问题复盘 |

{% note primary flat %}
自动重试只能缓解可证明的瞬态故障，不能把偶发失败无限重试成通过。记录首失败、重试原因、环境和最终结果；若失败无法定位，应先改善可观察性或隔离，而不是降低门禁。
{% endnote %}

### 维护成本

| 成本来源 | 典型信号 | 处理动作 |
| --- | --- | --- |
| 需求频繁变更 | 失败集中在定位器/流程差异 | 重审候选，删除无价值脚本 |
| 数据污染 | 重跑结果依赖执行顺序 | 工厂化夹具、隔离账号、明确清理 |
| 断言过弱 | 通过但业务结果错误 | 断言状态、金额、记录和可观察副作用 |

## 选择练习

### 候选排序

- 先自动化：稳定的金额计算、资格规则、接口幂等和数据守恒；
- 延后自动化：频繁改版的视觉细节、一次性迁移、需要专家判断的体验；
- 每个候选写预期、层级、运行频率、数据策略、失败诊断和维护负责人；
- 每季度根据失败成本和变更频率删除无价值脚本，保持套件可解释。

### 延后理由

{% note info flat %}
延后自动化不是放弃测试，而是说明当前人工更有收益：预期尚未稳定、外部依赖无法隔离、结果需要专家判断或一次性脚本成本过高。记录延后原因、风险补偿、重新评估时间和负责人，条件成熟后再按同一排序规则复审。
{% endnote %}

## 常见问题

{% flashcard basic id:testing-basics-a16-concept-1 deck:"测试基础" priority:2 tags:"自动化,候选" %}
--- question
哪些用例不适合自动化？
--- answer
规则不稳定、结果难判定、环境无法隔离、一次性成本过高或需要人的探索/体验判断的用例不应直接自动化。
--- explanation
自动化前计算开发与维护成本、执行频率和失败诊断收益。频繁变化的 UI 细节可能每天修选择器却没有新风险；探索新功能需要根据学习实时改变路径；外部依赖无法隔离时脚本会产生大量假失败。可以保留人工检查或把稳定的子规则下沉到接口/单元层，而不是简单“全自动/全手工”二选一。
{% endflashcard %}

{% flashcard basic id:testing-basics-a16-concept-2 deck:"测试基础" priority:2 tags:"自动化,探索式测试" %}
--- question
自动化能否代替探索式测试？
--- answer
不能。自动化重复已知规则，探索式测试通过学习和启发式寻找模型遗漏，两者发现的问题类型不同。
--- explanation
脚本可以稳定检查冻结账户不得登录，但无法主动理解新需求、发现流程不符合用户目标或提出未建模的状态。探索发现可复用规则后，可以把稳定检查沉淀为自动化回归；反过来，脚本全绿也不能阻止探索继续寻找未知风险。团队应同时安排可重复回归和有目标的时间盒探索。
{% endflashcard %}

{% flashcard basic id:testing-basics-a16-concept-3 deck:"测试基础" priority:2 tags:"测试金字塔,UI自动化" %}
--- question
为什么不把所有测试都做成 UI 自动化？
--- answer
UI 链路慢、脆弱且失败定位成本高；稳定规则应优先在单元或接口层验证，UI 只保留代表性用户旅程。
--- explanation
所有检查都走 UI 会共享环境、数据和选择器，导致运行慢、偶发失败和难以解释。金额、权限和状态不变量在接口/单元层更接近根因；关键登录到借阅旅程仍需少量 UI 证据。分层组合不是追求固定比例，而是让每个风险在最便宜且可信的层得到反馈。
{% endflashcard %}
