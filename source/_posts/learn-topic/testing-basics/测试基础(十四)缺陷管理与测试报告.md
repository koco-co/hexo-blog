{% note info flat %}
缺陷报告把“实际观察”与“预期规则”连接起来，测试报告则把执行范围、结果和剩余风险交给不同消费者。两者都要可复现、可追踪、不过度推断；发现问题不等于已经定位根因，测试通过也不等于可以发布。
{% endnote %}

## 缺陷判断

### 预期与实际

| 要素 | 例子 | 不能省略 |
| --- | --- | --- |
| 预期 | 冻结会员不得建立会话 | 依据哪条规则/版本 |
| 实际 | 冻结会员进入首页且产生会话 | 真实观察与数据 |
| 差异 | 状态和会话不符合约定 | 是否可重复 |
| 分类 | 产品缺陷、环境阻塞、需求未决 | 归因证据 |

{% note primary flat %}
先确认前置和预期，再判断是否是产品缺陷。数据初始化失败、环境服务不可达或需求尚未决定时，应分别标记阻塞或待澄清，不能为了让统计表有一条缺陷而强行归因。
{% endnote %}

### 问题分类

| 分类 | 判断依据 | 处理出口 |
| --- | --- | --- |
| 实现缺陷 | 在固定版本、数据和环境下稳定违反已确认规则 | 建立缺陷并保留复现证据 |
| 环境阻塞 | 依赖不可达、夹具损坏或权限不足导致无法执行 | 标记阻塞，记录责任人与恢复条件 |
| 需求疑问 | 预期规则尚未批准或多个文档冲突 | 发起澄清，不用猜测结果判缺陷 |

## 缺陷报告

### 复现与证据

| 字段 | 好的写法 | 边界 |
| --- | --- | --- |
| 标题 | 冻结会员提交正确密码仍建立会话 | 包含对象、条件、结果 |
| 环境 | build-12、测试环境、账号状态 frozen | 不贴真实密钥/个人数据 |
| 步骤 | 创建账号→冻结→提交→检查会话 | 另一人能重做 |
| 预期/实际 | 无会话；实际有会话 | 使用可判定值 |
| 证据 | 请求 ID、响应摘要、日志位置 | 附件先脱敏 |
| 严重度/优先级 | 影响与处理时机分别说明 | 不混成同一标签 |

![测试执行结果、日志和附件组成可追踪证据](/img/learn-topic/testing-basics/test-execution-outputs.png "测试执行输出")
![缺陷从新建到关闭、拒绝或重新打开的状态](/img/learn-topic/testing-basics/defect-statuses.png "缺陷状态")

{% note info flat %}
图示作用：第一张图提醒把版本、步骤、日志和附件放在同一证据链；第二张图提醒状态会因复现结果和责任决定而分流。图片是记忆辅助，不替代下面的可执行字段和状态判据。
{% endnote %}

{% note warning flat %}
“无法复现”不是结论终点。先补版本、时间、数据、随机种子、网络和日志，再区分偶现、环境差异、竞态或修复后不再出现；不要要求测试者凭感觉把所有偶现都改写成稳定缺陷。
{% endnote %}

| 复现字段 | 固定示例 | 可核对结果 |
| --- | --- | --- |
| 版本/环境 | `build-12`、测试环境、UTC、Chrome 128 | 另一位测试者可使用同一环境 |
| 合成数据 | 账号 `M2` 状态 frozen，使用测试夹具提供的有效凭据（不记录凭据值），会话为空 | 前置快照与清理步骤可重做 |
| 步骤 1 | 清理旧会话，确认账号 `M2` 状态为 frozen | 前置快照显示冻结状态 |
| 步骤 2 | 在登录表单输入夹具提供的有效凭据并提交，请求 ID `req-401` | 记录响应码、正文摘要和时间 |
| 步骤 3 | 查询登录会话并尝试进入受保护入口 | 预期：无会话且不能进入；实际：若建立会话则记录 session ID |
| 重复与证据 | 同一夹具连续执行 3 次，保存脱敏日志 `evidence/defect-401.log` | `3/3` 重现才标稳定；偶现写概率和触发条件 |

### 严重度与优先级

| 维度 | 要回答的问题 | 例子 |
| --- | --- | --- |
| 严重度 | 影响范围、数据损害和可用性有多大 | 支付重复扣款为高影响 |
| 优先级 | 在当前发布窗口何时处理 | 低概率但合规阻断可排 P1 |
| 证据 | 为什么这样判断 | 受影响用户、复现概率和业务负责人 |

## 处理闭环

### 状态与沟通

{% mermaid %}
flowchart LR
  N[新建：预期≠实际] --> T[分派与澄清]
  T --> F[修复或决定不修]
  F --> R[修复确认：原步骤]
  R --> G[回归：受影响范围]
  G --> C{结果}
  C -->|通过| K[关闭并保留证据]
  C -->|失败| O[重新打开并补充差异]
  T --> D[拒绝/重复/环境阻塞]
{% endmermaid %}

| 状态 | 进入判据 | 退出或处理判据 |
| --- | --- | --- |
| 新建 | 固定前置下实际结果违反已确认规则 | 分派、澄清或补充复现证据 |
| 拒绝/不修 | 重复、超出范围、预期规则不成立，且有责任人决定 | 记录理由和关联项，不计作已修复 |
| 环境阻塞 | 依赖不可达、数据/权限夹具损坏，无法判断产品行为 | 环境恢复后重跑，或由责任人接受风险 |
| 延后 | 已确认问题但当前发布窗口不处理 | 记录版本、补偿措施、截止时间和负责人 |
| 待澄清 | 需求冲突或验收规则未批准 | 产品/领域责任人确认后再判定 |
| 重新打开 | 原步骤仍失败，或回归发现同一问题/新差异 | 关联新证据，回到分派与澄清 |

{% note info flat %}
修复确认只回答原问题是否消失，回归还要检查变更影响的相关行为。状态转换应记录决定人和证据；关闭缺陷时保留版本、环境、执行结果和未覆盖条件，而不是只改一个状态字段。
{% endnote %}

### 修复确认

{% note info flat %}
修复确认重跑原失败步骤和同一前置数据，确认实际结果回到预期；随后按影响范围执行回归。若原问题仍存在或出现新的可复现差异，重新打开并关联新证据，不以开发者口头说明替代执行结果。
{% endnote %}

## 测试报告

### 进展与完成

| 报告部分 | 应回答 | 不应声称 |
| --- | --- | --- |
| 范围与环境 | 测了什么版本、入口、数据和限制 | 覆盖了所有行为 |
| 进展与结果 | 执行/通过/失败/阻塞的定义和数量 | 通过率等于质量分数 |
| 风险与缺陷 | 高影响问题、未决项、责任人 | 根因已经确定（若未分析） |
| 发布建议 | 条件、证据和剩余风险 | “没有缺陷”或无条件放行 |

{% note primary flat %}
面向开发者突出可复现步骤，面向管理者突出风险和决定，面向发布者突出准出条件和回退方案。同一组结果可以有不同摘要，但底层版本、范围和证据必须一致。
{% endnote %}

| 固定报告样例（`build-12`） | 数量 | 统计口径 |
| --- | ---: | --- |
| 计划用例 | 24 | 含所有本轮计划项 |
| 已执行 | 20 | 分母只计实际执行；环境阻塞 3 条单列 |
| 通过/失败 | 18 / 2 | 执行通过率 `18/20=90%`，不是质量分数 |
| 环境阻塞/未执行 | 3 / 1 | 不放进通过率分母，写明依赖和未测范围 |
| 发布风险 | 1 个高影响失败 + 3 个阻塞 | 指向缺陷 ID、责任人和风险接受状态 |

{% note warning flat %}
报告必须同时写分子、分母、排除项和未测范围：上例的 `90%` 只回答 20 条已执行用例中有多少通过，不能推出 24 条计划项全部安全，更不能掩盖 1 个高影响失败和 3 个环境阻塞。
{% endnote %}

### 指标与受众

| 受众 | 优先信息 | 指标边界 |
| --- | --- | --- |
| 开发者 | 最小复现、接口/日志和实际差异 | 不把通过率当根因 |
| 管理者 | 高风险、阻塞、剩余风险和决定 | 说明分母、范围和时间 |
| 发布者 | 准出条件、回退点和责任人 | 未测项必须显式列出 |

## 沟通取舍

### 证据不足

{% note success flat %}
当信息不足时，最诚实的结论是“当前证据不足以判定”。给出下一步：补环境、澄清规则、增加用例或由责任人接受风险。明确不确定性比用一个绿色状态掩盖失败更能帮助决策。
{% endnote %}

### 风险接受

{% note primary flat %}
测试者可以提出风险与证据，不能代替产品或发布责任人授权放行。若决定接受未修复问题，记录风险描述、影响、补偿措施、接受者和失效条件；没有明确接受者时保持“待决定”，不要写成通过。
{% endnote %}

## 常见问题

{% flashcard basic id:testing-basics-a14-concept-1 deck:"测试基础" priority:2 tags:"缺陷报告,复现" %}
--- question
开发说无法复现时，测试者怎么办？
--- answer
补齐版本、环境、数据、步骤和证据，尝试最小复现并区分偶现、环境阻塞和真实产品差异。
--- explanation
先保存原始失败的时间、构建、账号状态、输入、日志和请求 ID，再在同一条件重跑；若只在并发或特定时区出现，记录触发条件和可控种子。无法再次出现不等于缺陷不存在，也不等于一定是产品问题；应把复现概率、已排除条件和下一步观察写进报告。敏感附件先脱敏。
{% endflashcard %}

{% flashcard basic id:testing-basics-a14-concept-2 deck:"测试基础" priority:2 tags:"严重度,优先级" %}
--- question
缺陷严重程度和处理优先级怎么区分？
--- answer
严重程度描述影响大小，优先级描述在当前资源、风险和发布目标下何时处理；二者可以不同。
--- explanation
数据泄露通常严重度高且优先级高；低概率但必须支持的旧环境问题可能严重度中等、当前优先级高；仅影响内部测试文案的问题可能严重度低但被发布窗口暂缓。报告分别给出影响、发生条件、修复时机和决定人，不用标签替代理由。
{% endflashcard %}

{% flashcard basic id:testing-basics-a14-concept-3 deck:"测试基础" priority:2 tags:"发布,风险" %}
--- question
通过率高为什么不一定能发布？
--- answer
通过率只描述已执行用例的结果；关键风险可能未覆盖，阻塞项、严重缺陷或环境差异仍可能使发布不安全。
--- explanation
如果 100 条低风险用例通过，却没有执行冻结账户、支付超时或数据恢复，分子/分母都不能代表发布风险。发布判断应结合高风险证据、严重缺陷处置、未测范围、环境和回退能力；剩余风险需要明确接受者。通过率可作为趋势指标，不能单独作为放行门槛。
{% endflashcard %}
