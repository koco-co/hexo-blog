{% note info flat %}
需求分析的产物不是一段更漂亮的文字，而是可被不同角色理解、质疑和验证的约束。本篇以“图书借阅资格”为例，把角色、规则、例外和验收条件拆开，再用静态评审与追踪关系把歧义在执行前暴露出来。
{% endnote %}

## 需求拆解

{% note primary flat %}
先分离角色、目标、触发条件、业务规则和例外，再标出“已知事实、教学假设、待确认项”。没有给出的规则不能自行当成真实产品约束；假设可以用于练习，但必须在用例和结论中显式标记。
{% endnote %}

![需求分析从来源识别到形成可验证约束的步骤](/img/learn-topic/testing-basics/requirements-analysis.png "需求分析步骤")

| 项目 | 教学借阅需求 | 需要追问 |
| --- | --- | --- |
| 角色 | 会员、图书管理员、访客 | 访客能否预约或只可检索 |
| 目标 | 会员借阅可借图书并在期限内归还 | 逾期是否影响续借和新借 |
| 规则 | 账号启用、图书可借、借阅上限为 3 本（教学假设） | 上限按册数还是种类计算 |
| 例外 | 图书已借出、账号冻结、库存状态未知 | 是否允许排队和何时释放 |

{% note warning flat %}
“系统应该方便”“借书成功后显示成功”不能直接成为预期。要继续追问对象、条件、可观察状态和失败后的恢复，直到另一位测试者能够在相同前置下得到同一判定。
{% endnote %}

![需求来源与利益相关者的识别关系](/img/learn-topic/testing-basics/requirements-sources.png "需求来源")
![需求从原始描述加工为规则与验收条件](/img/learn-topic/testing-basics/requirements-refinement.png "需求加工")

## 验收条件

{% note primary flat %}
用户故事描述谁在什么目标下获得什么价值；验收条件描述本需求必须满足的行为；Definition of Done 则是团队对增量质量的共同完成承诺。三者相互关联，但不能用 DoD 的“代码已评审”替代借阅规则的业务结果。
{% endnote %}

| 写法 | 借阅示例 | 可判定性 |
| --- | --- | --- |
| 规则式 | 当会员有效且图书可借时，提交借阅后库存减 1、借阅记录新增 1 条 | 条件、动作、状态都明确 |
| 示例式 | 给会员 M、图书 B（库存 1），借阅后再次借 B 应被拒绝并提示“无可借库存” | 数据与预期可复现 |
| 模糊式 | 借书流程友好、速度快 | 缺少指标和观察条件 |

{% mermaid %}
sequenceDiagram
  participant P as 产品
  participant T as 测试
  participant D as 开发
  P->>T: 说明会员借阅目标
  T->>P: 追问上限、库存、逾期与例外
  P->>D: 确认可实现规则
  D->>T: 提供可验证增量
  T->>P: 返回验收证据与未决风险
{% endmermaid %}

{% note info flat %}
ATDD 的价值在于先让产品、开发和测试对例子达成一致，再实现可运行的行为；本篇只演示推导过程，不要求先安装 BDD 框架。TDD 更关注开发者从测试驱动设计，BDD 更强调共享业务语言，三者可互补而非同义词。
{% endnote %}

## 静态评审

{% note primary flat %}
静态测试不运行被测软件，可以评审需求、设计、代码、测试用例和合同。它适合在成本较低时发现矛盾、遗漏、不可测和术语不一致；发现问题后仍要在修订版本中确认解决，而不是把评审意见当成运行通过。
{% endnote %}

![需求评审中检查术语、规则与可测试性的要点](/img/learn-topic/testing-basics/requirements-review.png "需求评审要点")
![软件设计输出与后续测试依据的关系](/img/learn-topic/testing-basics/design-artifacts.png "设计产物")

| 评审方式 | 适合场景 | 主要参与者 | 证据 |
| --- | --- | --- | --- |
| 非正式评审 | 早期草稿、快速澄清 | 作者、同伴 | 评论与待办 |
| 走查 | 作者带领团队理解工作产品 | 作者、跨职能成员 | 议程、问题、决定 |
| 技术评审 | 设计、接口、可维护性 | 技术专家、开发、测试 | 规则冲突和技术风险 |
| 审查 | 高风险或合规工作产品 | 具备独立性的评审者 | 正式入口/出口记录 |

## 评审闭环

{% note primary flat %}
一次有效评审包含准备、个人检查、会议或异步沟通、问题分类、修订和复核。问题记录要指向具体规则或段落，区分“必须修复”“需要澄清”和“建议改进”，并保留决定人和复核证据。
{% endnote %}

{% timeline 需求评审闭环, blue %}
<!-- timeline 准备 -->
冻结被评审版本、目标和入口条件，邀请真正能回答规则问题的人。
<!-- endtimeline -->
<!-- timeline 个人检查 -->
分别检查角色、例外、数据、可测性、术语和相互矛盾的约束。
<!-- endtimeline -->
<!-- timeline 沟通与修订 -->
把观察写成问题，确认责任人和决定，不用“看起来没问题”关闭疑点。
<!-- endtimeline -->
<!-- timeline 复核 -->
确认修改覆盖原问题，并更新受影响的验收条件、用例和追踪关系。
<!-- endtimeline -->
{% endtimeline %}

## 需求追踪

{% note info flat %}
最小追踪矩阵把需求、验收条件、用例、执行结果和缺陷连起来。它的用途是发现“有规则没用例”“有用例没依据”和变更影响，不是用一张大表制造虚假的完整性。
{% endnote %}

| 需求 | 条件 | 用例 | 结果 | 缺陷/决定 |
| --- | --- | --- | --- | --- |
| LBR-01 借阅 | 会员有效、库存可借 | LBR-01-01 正常借阅；LBR-01-02 冻结会员 | 待执行 | — |
| LBR-02 上限 | 当前借阅数 < 3 | LBR-02-01 第 3 本；LBR-02-02 第 4 本 | 待执行 | — |
| LBR-03 归还 | 记录存在、状态可变更 | LBR-03-01 正常归还；LBR-03-02 重复归还 | 待执行 | — |

{% note success flat %}
需求变更时先定位受影响的条件和用例，再决定补测、重跑还是接受剩余风险。若“上限按册数”改为“按种类”，不能只改一行文字，还要检查数据、预期、接口和报告中的结论。
{% endnote %}

## 常见问题

{% flashcard basic id:testing-basics-a04-concept-1 deck:"测试基础" priority:2 tags:"需求分析,预期" %}
--- question
需求没写清时，测试者能否自己定一个预期？
--- answer
可以提出明确的教学假设继续分析，但不能把假设冒充产品约定；应记录待确认项并让责任人决定。
--- explanation
没有“冻结规则”时，直接把自己的理解写成失败条件会把需求争议误报为产品缺陷。更稳的做法是列出角色、触发条件、状态和问题，例如“逾期会员是否允许续借”属于业务决定；在决定前，可以用假设演示用例结构，但报告必须标记结论范围和未决风险。
{% endflashcard %}

{% flashcard basic id:testing-basics-a04-concept-2 deck:"测试基础" priority:2 tags:"验收条件,DoD" %}
--- question
验收条件与 Definition of Done 有什么区别？
--- answer
验收条件描述某个需求的业务结果；DoD 描述团队对增量完成质量的共同承诺，不能互相替代。
--- explanation
“有效会员借阅后库存减 1”是该需求的验收条件；“代码已评审、自动检查通过、文档更新”可以是团队 DoD。验收条件回答“这个能力对不对”，DoD 回答“这个增量是否达到团队约定的完成标准”。发布前应同时检查两者，并明确谁负责接受业务结果和剩余风险。
{% endflashcard %}

{% flashcard basic id:testing-basics-a04-concept-3 deck:"测试基础" priority:2 tags:"静态测试,评审" %}
--- question
静态测试是否必须阅读代码？
--- answer
不必须。需求、设计、接口、测试用例和文档都可以静态评审；代码只是其中一种工作产品。
--- explanation
如果需求把“冻结账户”写成允许借阅，评审需求就能发现矛盾，无需执行程序；如果接口字段名与设计不一致，评审契约也能提前发现。代码静态分析和人工走查适合不同风险，静态测试的关键是“不运行被测对象仍能发现工作产品问题”，而不是“必须看源码”。
{% endflashcard %}
